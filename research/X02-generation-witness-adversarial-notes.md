## Question

What claims are valid when realtime/HAL state and userspace Python/NML status are observed at different rates, and what tempting correlations must be rejected?

## Source/documentation facts

1. LinuxCNC's Python status interface exposes `heartbeat` as the motion-controller heartbeat; current documentation describes it as incrementing every servo cycle.
2. `taskbeat` is a separate Task main-loop heartbeat whose cadence follows the Task cycle.
3. `stat.poll()` refreshes a userspace status object from the NML status channel. The act of polling is therefore an observation operation; the caller's monotonic timestamp is not a realtime production timestamp.
4. The X02 source trace establishes `motion.motion-type` and Python `stat.motion_type` as two published representations derived from `emcmotStatus.motionType`. The value can stay equal across arbitrarily many producer generations and therefore is not itself a freshness token.

## Adversarial cases and valid conclusions

### Repeated userspace observations of one publication

If two Python observations have increasing `time.monotonic_ns()` but identical `taskbeat`, observer time has advanced without evidence of a new Task generation. It is invalid to relabel the second row as a newer controller generation merely because its timestamp is later.

### Equal state across newer generations

If `taskbeat` or motion `heartbeat` advances while `motion_type` remains unchanged, the state is persistent across generations. Equality of the state value cannot establish that two rows came from the same generation.

### Slow observer

If adjacent Python observations show generation deltas greater than one, one or more producer generations were not represented by Python rows. This is expected sampling/observation behavior and is not itself evidence that LinuxCNC failed to execute those generations.

### Different heartbeat deltas

Motion `heartbeat` and Task `taskbeat` are generated by different loops. Their numeric equality or equal deltas are not a common-cycle identifier. Conversely, differing deltas are not necessarily a fault: publication/observation cadence can legitimately collapse multiple motion generations into one Task/Python-visible update.

### Nearest timestamp trap

A Python monotonic timestamp can order Python observations and measure observer-side intervals. A realtime sampler record has a deterministic cycle witness but no identical cross-surface generation ID. Joining a HAL row to the nearest Python timestamp can be a visualization heuristic, but it cannot prove same-cycle correspondence, causality, or simultaneity.

### Recorder-integrity trap

Even a visually plausible HAL transition sequence is unusable for exact correlation if its recorder-health evidence fails the X01 oracle. Producer overrun plus deterministic payload-cycle discontinuity proves recorder loss. `halsampler -t` continuity alone does not rescue the interval.

## X02-001 verification consequences

The preflight therefore records both generation counters and the selected state, retains Python monotonic time only as observer-order/time evidence, and independently validates the realtime recorder. Gate F is intentionally an ordered-subsequence test rather than a timestamp-equality test. Gate I excludes X01-invalid evidence by construction. Gate J explicitly rejects claims of simultaneity where no shared generation identity exists.
