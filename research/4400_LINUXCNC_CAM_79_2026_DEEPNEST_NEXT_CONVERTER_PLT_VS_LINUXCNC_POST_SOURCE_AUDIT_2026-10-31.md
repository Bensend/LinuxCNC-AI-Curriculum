## Source-confirmed current-fork differences and invariants

**C1 — The fork still uses a network conversion boundary for DXF (SOURCE-CONFIRMED).** `convertAndImport` reads DXF bytes, posts multipart `fileUpload` plus `format=svg` to `conversionServer`, then uses `dxfImportScale` and `processSvgData`. `exportToDxf` similarly posts generated SVG plus `format=dxf`. The default endpoint is now **HTTPS**, not the original 2018 `http://convert.deepnest.io`. The UI/service separation and error handling have changed, but the inspected DXF path is **still not an offline native DXF importer/exporter**. The README labels native DXF without online conversion as an upcoming change. Service availability, returned geometry, privacy and fidelity remain **UNKNOWN**. A disconnected runner cannot be used to claim a DXF conversion pass without a separately reviewed offline converter.

**C2 — A new local PLT/HPGL export is not G-code (SOURCE-CONFIRMED).** `exportToPlt` builds SVG, derives inches per SVG unit from `width` and `viewBox`, applies SVG transforms, flattens paths, polygonifies supported elements, flips Y to upward and invokes `generateHpgl(paths)` before writing a `.plt` file. This is useful as an **independent geometry export** for plotters, but it is not a LinuxCNC interpreter program and does not encode QtPlasmaC M190/M66/M3/M5, kerf, lead-in, pierce or torch timing. The UI's G-code option is still commented out. Do not substitute a PLT export for a QtPlasmaC postprocessor.

**C3 — Physical units now have an explicit PLT conversion path, with its own limits (SOURCE-CONFIRMED).** `getInchesPerSvgUnit` computes `widthInches/viewBoxWidth` from SVG width ending in `mm` (divides by 25.4) or otherwise assumes the numeric width is inches. `collectHpglPaths` multiplies XY coordinates by that factor and flips Y using the viewBox height. `applyDimensions` writes `in` or `mm` based on configured units. This establishes a **code-level dimensional conversion**, not measured PLT accuracy. If a source SVG was mis-scaled earlier, PLT conversion cannot recover the intended DXF dimensions. The PLT path uses flattened/tessellated polygons; it does not prove preservation of native circular arcs or feature IDs.

**C4 — The fork's actual current status is narrower than its feature labels (SOURCE-CONFIRMED; runtime UNKNOWN).** The source advertises DXF/DWG import/export and new PLT output, but DXF/DWG rely on a conversion service, and `tests/index.spec.ts` inspected here covers settings rather than an authoritative dimensional roundtrip. A UI label, GitHub commit title, workflow status or file extension is not evidence of geometric fidelity or LinuxCNC compatibility.


**C5 — HPGL integer quantization and path closure are explicit, independently testable (SOURCE-CONFIRMED; UPSTREAM-TEST-DEFINED).** The fork's [`main/ui/utils/hpgl.ts`](https://github.com/deepnest-next/deepnest/blob/e33e8889df40fed870dd4c2c68be27fd46ea0fdc/main/ui/utils/hpgl.ts), blob `8908cafbe2b1f777fb5ede3e8cfcd7ef8d9ef2ac`, defines `HPGL_UNITS_PER_INCH=1016` and `toPlotterUnits(x)=Math.round(x*1016)`. Thus one output grid step is **0.025 mm**, with a single-coordinate ideal rounding bound of **0.0125 mm** (two-axis Euclidean bound ≈0.01768 mm) *before* any earlier polygonization or physical plotter error. `generateHpgl` emits `IN; SP1; PU...; PD...; PU; SP0;`, appends the start point for a closed path, skips paths with fewer than two points and chunks PD coordinate lists at 50 points. A 0.01-mm displacement corresponds to 0.4 plotter units and can quantize to zero. The fork includes [`tests/hpgl.cjs`](https://github.com/deepnest-next/deepnest/blob/e33e8889df40fed870dd4c2c68be27fd46ea0fdc/tests/hpgl.cjs), blob `83f4f5f76cf2baf77ebc9c38c53e64a4f0a1af8c`, with expected open/closed/rounding/custom-scale/skipped-path/chunk cases. **Tests inspected, NOT RUN**; they test the HPGL utility, not the entire SVG→PLT path, DXF dimensions or LinuxCNC interpreter. This is a useful upstream independent oracle for a future isolated fixture, not measured accuracy.

## Practical LinuxCNC integration decision

Use **SVG as a documented intermediate** only after an independent physical-dimension witness, complete contour inventory, affine transform check, winding/hole topology validation and loss accounting. A geometry export (SVG, DXF or PLT) is **not** the NC post. For LinuxCNC v2.9.10 QtPlasmaC, inspect the actual machine `[FILTER]` mapping and post-specific material/feed/torch sequence; the [stable simulation INI](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/configs/sim/qtplasmac/qtplasmac_metric_ini.inc) maps NC to `qtplasmac_gcode`. Filtered NC and interpreter/canonical results need independent review; see [PLASMA-39](4400_LINUXCNC_PLASMA_39_QTPLASMAC_HOLE_FILTER_COORDINATE_STATE_SOURCE_AUDIT_2026-10-31.md) and [PLASMA-32](4400_LINUXCNC_PLASMA_32_QTPLASMAC_OVERCUT_M62_P3_TP_TIMING_AND_FILTER_SOURCE_AUDIT_2026-10-31.md). For OpenPressBrake, retain bend lines/datums separately and do not treat a nested blank as an executable bend sequence.
