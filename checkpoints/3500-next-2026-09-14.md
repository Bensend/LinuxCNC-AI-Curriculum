## Major decision

ROS and especially ROS 2 are not a side note in 3500. Treat them as a major robotics implementation competency alongside native LinuxCNC kinematics.

The curriculum must compare two first-class architectures rather than assuming one is canonical:

1. **Native LinuxCNC robot:** LinuxCNC interpreter/motion/kinematics -> HAL -> drives.
2. **ROS 2 robot:** MoveIt 2 -> ros2_control -> realtime HAL/hardware layer -> drives.

The primary current real implementation reference for architecture 2 is the Tormach ZA6 stack:

- `tormach/tormach_za_ros2_drivers`
- `tormach/hal_ros_control`
- `za6_hardware`
- `za6_moveit_config`

Do not mislabel the ZA6 architecture as LinuxCNC motion. It uses Machinekit HAL ancestry as the realtime hardware layer while ROS 2 / ros2_control owns trajectory-controller execution.

## Exact next deep work when 3500 is active

### ROS2-1 — current ros2_control source trace

Trace Resource Manager, hardware interfaces, controller manager read/update/write cycle, JointTrajectoryController, controller switching, action cancellation/tolerance behavior and realtime constraints.

### ROS2-2 — MoveIt 2 execution path

Trace URDF/SRDF -> planning scene -> IK/planner -> controller selection -> FollowJointTrajectory -> ros2_control. Include TF/tool/work frames, MoveIt Servo and external-axis/multi-group behavior.

### ROS2-3 — Tormach ZA6 real implementation

Trace exact command and feedback paths:

`MoveIt trajectory -> ros2_control controller -> HalSystemInterface -> HAL pins -> EtherCAT/drive`

and

`encoder/drive state -> EtherCAT/HAL -> HalSystemInterface -> ros2_control state -> MoveIt/ROS`

Also trace drive enable/fault ownership, brakes if exposed, startup/shutdown, sim versus real hardware and RT_PREEMPT/Docker assumptions.

### ROS2-4 — current LinuxCNC integration feasibility

After the ZA6 trace, compare Machinekit HAL APIs used by `hal_ros_control` with current LinuxCNC HAL/RTAPI. Determine whether a direct port is structurally reasonable, whether a bounded shared-memory/ringbuffer bridge is cleaner, or whether ROS should instead hand durable paths/programs to native LinuxCNC motion.

Do not build a production bridge as part of curriculum graduation. Small simulations/proofs are allowed only to resolve a specific uncertainty.

### ROS1 — historical lesson

Preserve ROS 1 / Machinekit / old LinuxCNC bridge work only to explain the evolution and failure modes. Do not teach ROS 1 as the preferred new-build architecture.

## Required comparison topics

- LinuxCNC kinematics versus MoveIt IK/planning;
- LinuxCNC world/joint frames versus URDF/TF/SRDF frame model;
- G-code trajectory execution versus FollowJointTrajectory;
- MoveIt Servo/reactive jogging versus LinuxCNC jog/world motion;
- deterministic realtime ownership;
- stale command/watchdog semantics;
- cancellation/abort/recovery;
- drive fault versus ROS process failure;
- external axes and robot-on-rail;
- multi-robot/machine-tending cells;
- collision planning versus safety-rated protective functions;
- simulation and visualization (QtVismach versus RViz/MoveIt).

## Promotion boundary

3500 should not claim ROS/ROS 2 competence until the AI can explain, from inspectable source/config evidence, exactly who owns planning, interpolation, kinematics, servo timing, hardware state and recovery in at least:

1. one native LinuxCNC articulated robot architecture, and
2. one real ROS 2 + ros2_control + HAL robot architecture (Tormach ZA6 is the current preferred reference).

The final playbook should help a future engineer choose the architecture appropriate to the machine rather than defaulting to ROS or LinuxCNC by habit.
