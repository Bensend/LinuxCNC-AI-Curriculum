## Why the new guards help, and exactly what they cannot prove
| Guard / evidence | What it prevents or records | What it does NOT prove |
|---|---|---|
| No automatic lab push trigger | Merely editing `lab-jobs/` or workflow YAML no longer schedules a lab job by this workflow | No other workflow can trigger; GitHub Actions is disabled; no external actor can manually dispatch |
| Local runner label | This job is **not** assigned to `ubuntu-latest`; no hosted fallback is specified | Runner exists/online; runner is physically disconnected; its account lacks I/O permissions |
| Explicit job path and reviewed SHA-256 | Accidental wrong script selection or script drift is detected at execution time | The script is benign, review was competent, transitive commands are harmless, or physical hardware cannot be reached |
| Manual boolean isolation attestation | The dispatch UI makes the operator acknowledge an explicit precondition; false/omitted input skips execution | Physical isolation actually exists. A checkbox is **NOT** an independent interlock, lockout, restraint or safety function |
| 70-minute inner timeout | Bounded duration of the directly launched shell process under ordinary OS behavior | All descendants terminate, hydraulic pressure dissipates, ram is held, guard access is safe, or external devices stop |
| Workflow result/exit code | Software process completed with recorded status and artifacts | Any safety-related function or physical final element passed validation |
| Lab `contents: read`, artifact-only result publication | Removes the lab runner's routine repository-write token and automatic result push; result artifact remains retrievable | Sandbox isolation, trusted dependencies, indefinite evidence retention, or write-token removal from other separate workflows |

**INFERENCE — conditional hazardous path:** If the panel PC can reach normal FPGA/HAL outputs, a script from a public repo executed by the local runner might load hardware drivers or send normal commands. A successful job or a timeout would not establish physical stopping/holding. A malicious/incorrect script could also run with the runner's privileges. This is a **risk to review**, not a claim of an installed OpenPressBrake bypass or actual actuation.

## Minimum safe-to-execute threshold for a future *disconnected* simulation
Before any future lab, a qualified local owner/reviewer must establish **outside GitHub and outside the same script**:
- **Identity/provenance:** exact runner machine/account, exact reviewed commit and script hash, installed software and config, and a frozen engineering question/oracle. Do not run a smoke test just to find whether the runner is alive.
- **Physical isolation:** demonstrate the script's LinuxCNC/HAL/FPGA/fieldbus paths cannot actuate the machine, using a qualified isolation arrangement appropriate to the actual electrical/hydraulic/mechanical system. Network namespace or process name alone is not proof if a second path remains. For a panel PC on an active machine, prefer a separately isolated compute environment or machine-offline bench; if neither is demonstrable, **do not execute**.
- **Stored energy and personnel:** if physical machinery could be affected, retain independent selected safety controller/final elements, guarding, gravity-load support and energy-isolation controls. An ordinary LinuxCNC software E-stop is not a substitute. Do not run with people exposed. Experimental physical operation, if ever authorized, requires a separate qualified isolated/remote plan with exclusion and stated residual risk.
- **Access/security:** review who can edit/dispatch public-repo workflows and job scripts, runner group/repository scope, process privileges, persistent secrets and network access. Consider an isolated dedicated runner rather than sharing the operational panel PC. A checkbox and SHA are process controls, not physical or security sandboxes.
- **Evidence:** after an authorized bounded job, inspect actual job logs/artifacts and authoritative job timestamps; distinguish process success, simulated behavior, safety-controller state and physical observations. Only then update `LAB_COMPUTE_LOG.md`. Never infer compute minutes from this source-only session.

## Adversarial review and human factors
- **Shortcut 1:** "It is self-hosted, so it is safe." False: this only selects a compute host; it is not a machine energy-removal boundary.
- **Shortcut 2:** "I checked the disconnected box." False: no independent measurement or physical isolation follows. The operator should be able to see a simple *DISCONNECTED SIMULATION ONLY* instruction and have an easy separate bench path, rather than pressure to bypass a difficult gate.
- **Shortcut 3:** "The SHA matches, so the job is safe." False: it only pins reviewed bytes of the top-level script. Nested scripts, shell commands, dependencies and device paths need review; a hash cannot stop malicious commands.
- **Shortcut 4:** "A job timeout stopped the experiment." False: Task/child-process and external-device completion are distinct; see [M1xx process-exit audit](4400_M1XX_EXIT_01_LINUXCNC_2910_USER_MCODE_ZERO_EXIT_BACKGROUND_CHILD_AND_SAFETY_BOUNDARY_2026-10-28.md).
- **Shortcut 5:** "One completed simulator is proof the press brake is safe." False: LinuxCNC simulation does not establish the installed Pilz/AKAS safety program, K1/K2/EDM, Y1/Y2 stop/hold, guards, isolation, or deliberate restart.

**Residual software-security limitations:** the public curriculum repository still has self-hosted workflows, including ledger append workflows with write permissions; this source change does not revoke all runner credentials or guarantee public-repo safety. The initial lab used moving `actions/checkout@v4` and `actions/upload-artifact@v4` tags; **same-session remediation** pinned those actions to full GitHub-source commit SHAs in all four curriculum workflows. Reinspect action dependencies/permissions before any future job; SHA pinning does not sandbox a runner or prove physical isolation. Artifact retention is currently 30 days, so an authorized job requires timely independent raw-artifact inspection and a separate reviewed GitHub commit for durable evidence. The manual checkbox and job SHA do not constrain transitive commands or machine hardware access. The lab workflow's concurrency group only serializes that workflow, **not** other jobs on the same runner.

**Study-method lesson:** eliminating prohibited hosted compute and avoiding uncontrolled local physical actuation are *two separate controls*. An explicit source change can remove the first trap while the second remains an external qualified physical precondition. No new unscored exam bank was created; this is a durable practical engineering/infrastructure boundary review, not a safety-function validation.

### Adversarial allowlist bypass correction — path-only is insufficient
The first allowlist iteration checked **filenames only**. A later change to the bytes at one of those filenames could still have passed if a dispatcher simply supplied the new SHA-256; this was a genuine review-authority weakness, not physical evidence. Corrected the workflow to pin the **exact reviewed Git blob SHA** in each of the four `case` branches and reject `git hash-object` mismatch before invoking the script. Reviewed blob identities: 086 `d2e64a3d8986a155dd09954774abf93902627a71`; 087 `2b89eaf26f01169ebb813df5891ddca6825fea5d`; 088 `c7485eec76eee76af5b75a7e3565e3fd7836aa21`; 089 `d75abc7ced3bf7e52f10a232b4b1c9f19daaec6e`. The separately entered SHA-256 remains an additional reviewed-script check. A legitimate script edit requires an explicit reviewed workflow change; a mere script-path edit cannot silently expand execution authority.

**Limit:** Git blob SHA-1 is a version-identity guard, **not a cryptographic safety certification**, and a malicious dependency, interpreter, runner process or machine connection remains outside this proof. No job was dispatched; no runtime validation or physical isolation evidence exists.

### Manual dispatch ref scope — do not assume main fixes every branch
Original GitHub [manual workflow documentation](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow) allows a dispatcher to select a branch/ref. The current main workflow therefore adds a job-level `github.ref == 'refs/heads/main'` condition in addition to isolation attestation. **SOURCE-CONFIRMED current main guard**; **UNKNOWN** whether old branches retain legacy hosted workflow YAML. A branch containing older workflow code may not inherit main's guard, so a true repository-wide zero-hosted guarantee requires auditing or restricting all dispatchable refs and repository Actions policy. **Do not dispatch older refs**; no branch-dispatch experiment was run. This is a source-configuration scope limit, not a reason to consume hosted minutes to test the guard.
