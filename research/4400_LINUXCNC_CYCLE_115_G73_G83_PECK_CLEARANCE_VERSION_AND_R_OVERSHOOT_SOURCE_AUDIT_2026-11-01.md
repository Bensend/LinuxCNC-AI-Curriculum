# CYCLE-115 — G73/G83 peck-clearance version delta and R-plane overshoot
**Status:** 4000 LinuxCNC implementation, 3100 mill/3400 router transfer; NON-GRADUATED; SOURCE-CONFIRMED static, numeric INFERENCE, TEST-CONFIRMED none. **Inspected:** stable v2.9.10 release `86cdca76fa2a36274c432caa21952b23c267989a` (2026-07-02) and development `06864e23559e70463fc7112d5ce77138bcbc288c` (2026-11-01). **Audit date:** 2026-11-01.

## Question and predecessor check
Does the interpreter guarantee that intermediate G73/G83 rapids remain below the programmed R plane, and is the clearance invariant across stable and development? A full `PROGRESS.md` search for G73, G83, canned cycles, G98/G99 and a repository research-filename scan found no previous peck-cycle source audit. Previous LATHE-107/108 concern G76; TOOL-113/114 concern G10. This is a **new motion-generation mechanism**, not a reopening of graduated 3100.

## Official behavior and versioned source
- Stable [G73 documentation](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/docs/src/gcode/g-code.adoc#L1887) specifies a fixed 0.010 in / 0.254 mm chip-breaking retract. Stable [G83 documentation](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/docs/src/gcode/g-code.adoc#L2501) specifies an R-plane retract followed by a rapid to the preceding peck bottom plus that fixed gap. [G98/G99 documentation](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/docs/src/gcode/g-code.adoc#L2851) distinguishes the **final** return level.
- Stable [`G83_RAPID_DELTA`](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/rs274ngc/interp_internal.hh#L55) is 0.010 inches. [`convert_cycle_g83`](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/rs274ngc/interp_cycles.cc#L140) and [`convert_cycle_g73`](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/rs274ngc/interp_cycles.cc#L204) multiply by 25.4 in metric mode and unconditionally command `current_depth + rapid_delta` when another peck remains.
- Development [`convert_cycle_g83`](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/rs274ngc/interp_cycles.cc#L140) and [`convert_cycle_g73`](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/rs274ngc/interp_cycles.cc#L202) instead use `block->d_flag ? block->d_number_float : _setup.parameter_g{83,73}_peck_clearance`. Development [`Interp::init`](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/rs274ngc/rs274ngc_pre.cc#L832) sets the metric default **1 mm** and imperial default **0.050 inches**; [INI lookup](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/rs274ngc/rs274ngc_pre.cc#L945) can override each. Equivalent XZ/YZ and UV/VW/UW helpers reuse the same peck algorithm.

## Source-derived discriminating calculation (metric, G17 G90 G99)
Take current Z=5 mm, R=2 mm, bottom Z=0 mm, Q=0.5 mm. The first feed peck is at Z=1.5 mm. Since more depth remains, the next canonical targets are:

| Revision / cycle | First feed | Subsequent rapid targets | Above R? |
| --- | ---: | --- | --- |
| stable G73 | 1.5 | 1.5 + 0.254 = **1.754** | no |
| development G73, no D/INI override | 1.5 | 1.5 + 1.0 = **2.5** | **yes, by 0.5 mm** |
| stable G83 | 1.5 | R=2, then 1.754 | no |
| development G83, no D/INI override | 1.5 | R=2, then **2.5** | **yes, by 0.5 mm** |

This is a *canonical-command prediction*, not a LinuxCNC execution result. A G98 initial Z of 5 mm does not itself bound the intermediate target: the G98/G99 selection controls the final clear position in the inspected algorithm. For any positive peck gap `c`, the first intermediate rapid target is `R-Q+c`, exceeding R exactly when **c>Q**. In stable metric, c=0.254 mm; in development without overrides, c=1 mm. The same geometric condition applies to later pecks only when the current peck remains shallower than `R+c`.

## Consequence, constraints and evidence
A CAM post that uses a shallow Q based on stable v2.9.10 can generate extra above-R rapids on development without any G-code change. If R is deliberately set close to clamps, this is a clearance-planning concern; no clamp collision or limit violation has been demonstrated. G83's extra intermediate R return is not equivalent to G73's local retract; neither routine clamps its `current_depth+c` rapid target to R. A conservative post should know the **actual configured clearance** and treat `0<c<=Q` as a *post-level geometry rule*, not a native LinuxCNC guarantee. Independently verify fixture clearance and the entire path; neither R nor G98 is personnel safety authority.
