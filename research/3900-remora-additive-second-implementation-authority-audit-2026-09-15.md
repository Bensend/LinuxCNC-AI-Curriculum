## Architecture found

This is not merely another host-side HAL thermistor example. Remora splits authority across LinuxCNC and a remote realtime MCU firmware:

1. LinuxCNC owns coordinated machine motion and supplies joint commands to the Remora HAL driver.
2. The sample Hypercube uses five joints with `trivkins coordinates=XYZZA`; joint 4 / A is explicitly the extruder and is commanded as an ordinary coordinated motion coordinate.
3. Remora firmware owns the physical step generation, ADC thermistor acquisition and heater PWM endpoints.
4. Firmware temperature measurements are returned through `remora.PV.N`; LinuxCNC PID components consume those PVs and produce heater commands through `remora.SP.N`.
5. SPI link status is connected to `iocontrol.0.emc-enable-in`, so communication status participates in machine-enable authority in the inspected Hypercube HAL.

This creates a clearer layered contract than the first LinuxCNC-RepRap implementation:

`LinuxCNC temperature command -> LinuxCNC PID -> Remora SP -> MCU PWM -> heater`

and

`thermistor -> MCU ADC/conversion -> Remora PV -> LinuxCNC PID feedback`.

## Temperature acquisition semantics

The firmware `Temperature` module deliberately updates thermistor temperature at **1 Hz**. The thermistor conversion reads a 16-bit ADC and converts resistance to temperature using the configured beta/R0/T0 relationship.

The temperature module contains one explicit disconnected/error behavior: if the calculated temperature is not greater than zero, it prints a sensor error and publishes `999` as the PV.

This is stronger than a completely unqualified scalar because at least one sensor-error class becomes an out-of-range sentinel. It is still not a complete process-validity contract:

- no independent sample-age/freshness output was found in the inspected temperature path;
- the 1 Hz update period means a previously published PV necessarily persists between measurements;
- the inspected thermistor conversion does not visibly clamp raw ADC endpoints before the resistance/log calculation;
- no source-visible rate-of-rise, failure-to-heat, thermal-runaway or independent overtemperature latch was found in this path.

Therefore preserve:

**a firmware-generated PV and even an error sentinel do not by themselves prove fresh/valid temperature or safe heater authority.**

## Heater authority

The Hypercube LinuxCNC HAL loads ordinary LinuxCNC PID components for the bed and extruder. Their enable inputs are driven from a `remora-status` signal, and their outputs are sent to Remora setpoints that drive MCU PWM modules.

The INI provides PID gains and maximum outputs; the extruder section also documents an intended temperature range up to 270 C. But in the inspected HAL the important authority is still essentially:

`Remora communication/status -> PID enable`

rather than a demonstrated production thermal-safety state machine.

No inspected logic established all of:

- sensor-freshness timeout;
- plausible sensor range as a separate boolean witness;
- failure-to-heat timer;
- runaway / excessive-rise logic;
- independent max-temperature latch;
- heater-output discrepancy/current proof;
- extrusion-ready qualification from stable in-band temperature.

The sample therefore improves transport/remote-I/O architecture without closing the thermal-process authority gap.

## Extrusion synchronization semantics

The Hypercube configuration explicitly makes extrusion joint 4 / axis A part of `TRAJ COORDINATES`. This is strong evidence for geometric coordination: extrusion is planned with the XYZ path rather than generated by an unrelated userspace feeder loop.

But geometric coordination is not the same as material correctness. The inspected configuration exposes no independent filament-flow/encoder witness, pressure model, jam detector or material-present proof. Pause/abort/restart may preserve LinuxCNC geometric state while still leaving thermal soak, nozzle pressure, ooze/retraction and material continuity as process-state questions.

Durable rule:

**coordinated A-axis extrusion proves trajectory coupling, not deposited-material correctness.**

## Communication boundary

The Hypercube HAL connects `remora.SPI-status` to `iocontrol.0.emc-enable-in`. That is materially better than leaving the remote controller link purely diagnostic: loss of the link participates in LinuxCNC machine-enable state.

However, that does not prove that every remote physical output is independently fail-safe under every MCU/transport failure mode. Firmware/driver shutdown behavior and electrical output defaults remain separate evidence questions.

## Comparison with first additive implementation

The second implementation changes the architecture but reinforces the earlier separation:

- LinuxCNC-RepRap: custom host/realtime temperature path and simple heater authority.
- Remora: remote MCU thermistor/PWM endpoints, LinuxCNC PID, explicit communication-status machine-enable coupling, and coordinated A-axis extrusion.

Neither inspected implementation supplies a complete production thermal-readiness/fault/recovery contract.

So the earlier durable rule survives and can be sharpened to:

`temperature scalar != fresh/valid temperature != heater authority != thermal readiness != extrusion/material-flow correctness`.

## Lab decision

No lab is justified yet. The source already resolves the important architecture question and exposes the remaining gaps. A future lab would only be useful if tied to a specific production claim, for example whether a stale-but-last-valid Remora PV can continue to command heat during a narrowly defined communication/measurement failure that does not drop `SPI-status`.

## Information-gain decision

Priority-1 additive work now has a credible second inspectable implementation. Further generic 3D-printer searching is likely to repeat the same architecture unless a source exposes real thermal-runaway/readiness or hybrid additive/subtractive switching.

Next 3900 work should therefore rotate to a genuinely different unusual-machine authority problem: winding/rotary synchronization if inspectable evidence is found; otherwise a bounded native `genhexkins` convergence/failure/switching trace.
