# 4000-LC-ARC-130 — M2/M30 program end does not explicitly reset IJK arc-center distance mode
**2026-11-01 | LinuxCNC stable v2.9.10 + pinned development | SOURCE-CONFIRMED local reset omission; conditional cross-program consequence UNKNOWN | NOT RUN | NON-GRADUATED**

## New evidence question and predecessor
[ARC-129](4400_LINUXCNC_ARC_129_G901_G911_XZ_CENTER_WORD_DOC_SOURCE_FREECAD_HANDOFF_2026-11-01.md) established G18 I/K center semantics and the FreeCAD default preamble's omission of G91.1. This follow-through tests the narrower claim that “M2 automatically resets all distance modes.” It does **not**: the inspected `convert_stop` resets ordinary `distance_mode` but does not assign `ijk_distance_mode`. That is a **distinct modal lifetime mechanism**, not an additional speculative CAM defect.

- Both official M2/M30 descriptions list G90 endpoint reset, G17 plane reset and G94 feed-mode reset, **but do not promise G91.1 reset**. Development additionally documents conditional G54/TWP behavior. The documentation omission is not itself a false statement.

## Execution path and limits
1. G90.1 sets `settings->ijk_distance_mode` to absolute through `convert_ijk_distance_mode`; G91.1 sets it incremental. G90/G91 change a separate `settings->distance_mode`.
2. For M2/M30, `convert_stop` resets `settings->distance_mode = MODE_ABSOLUTE`, plane to XY and feed mode to units/minute, plus other listed state; in the inspected reset branch there is **no write to `settings->ijk_distance_mode`**. `PROGRAM_END` is emitted afterward.
3. `rs274ngc_pre.cc` initialization **does** set IJK mode incremental. The standard Task close/open lifecycle was subsequently traced below: absent an explicit `interp.init()`, ordinary `close()/open()` and their `reset()` calls do **not** change IJK mode. This supports persistence in that bounded source path, not a universal GUI or runtime claim.
4. A CAM post whose preamble specifies G90 but omits G91.1 does not establish arc-center semantics **at the interpreter-conversion level**. The conservative fix for an incremental-IJK post is an explicit G91.1 in the generated file, after independently confirming that the post emits relative centers.

**Revised source-grounded conclusion:** In the inspected standard Task implementation, a same-interpreter **M2/M30 → close → open → run** path with no intervening `EMC_TASK_PLAN_INIT` does **not** restore G91.1. A preceding G90.1 can therefore survive ordinary file close/open and be inherited by a later program that omits G91.1. A fresh Task initialization or any explicit G91.1 changes this result. **The exact GUI command sequence, special/custom interpreter plugins, restart/reset paths, and actual runtime observation remain UNKNOWN/NOT RUN.** This is stronger than a mere `convert_stop` omission, but is not a claim about every controller or physical cutting event.

Under the **same Task interpreter with no `init()`**, B should fail (zero-radius or radius mismatch depending on exact center); after explicit `init()`, B should pass. ## Transfer and limits
This matters to lathe G18 arcs, mill/router G17 arcs and plasma DXF posts with IJK output. It does not prove any installed machine has cut an incorrect arc. A program that explicitly selects G91.1 for incremental centers remains robust against both a prior G90.1 state and an interpreter reinit. This is an implementation-contract improvement, not a safety-system substitute. Independent personnel safety and OpenPressBrake G0/G1 HOLD unchanged. No graduation or external evaluator result.
