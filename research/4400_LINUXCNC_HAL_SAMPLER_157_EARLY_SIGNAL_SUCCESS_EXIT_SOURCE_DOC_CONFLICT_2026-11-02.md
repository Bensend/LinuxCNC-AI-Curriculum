## Call flow and exact branch
1. Realtime `sampler.c::sample`, scheduled with `addf sampler.0 <thread>`, copies configured HAL inputs into the shared stream with `hal_stream_write` at the thread cadence; on FIFO full it records an overrun.
2. Userspace `sampler_usr.c::main` parses `-n` to set `samples` (positive finite count or `-1` indefinite), registers SIGINT/SIGTERM/SIGPIPE with `quit`, creates a HAL component and attaches to the sampler FIFO.
3. `quit` sets `stop=1` unless inside `ignore_sig` region. `main` calls `hal_stream_wait_readable(&stream,&stop)`; if `stop` is set, the loop executes `if(stop) break;`. If a sample was read, the finite `samples` counter decrements.
4. **After either natural `samples == 0` or early `break`, the code unconditionally executes `exitval = 0`** (stable source near lines 192–239). The initialized error status `exitval=1` is overwritten. Development retains the same sequence.
5. Result: a delivered SIGTERM/SIGINT/SIGPIPE during an active finite capture, outside the ignore region and before count completion, can lead to **process exit code zero with fewer than the requested number of records**. This is **SOURCE-CONFIRMED branch logic**, **INFERENCE for external process behavior until a qualified runtime test**. A default signal action or external wrapper's status (e.g., `timeout` without `--preserve-status`) can mask the child result; verify the actual child exit code, not just shell wrapper status.

## Why this matters
A capture orchestrator that accepts exit code 0 as proof of `-n` completeness can silently accept a truncated diagnostic trace. The official man page's finite-count termination promise is stronger than the inspected implementation. This is a **test-integrity and diagnostic reliability** concern; it is not evidence of a machine-motion or personnel-safety failure. Treat row count, timestamps/sample numbers, and FIFO-overrun markers as separate acceptance evidence, not just process success.

## Minimal correction candidate (NOT APPLIED)
[Stable-only one-line patch](../examples/4000_hal_sampler_157/halsampler_early_stop_exit_status_v2910.patch) adds `if (stop && samples != 0) goto out;` immediately before the successful-exit assignment. This preserves success on natural finite completion, returns the initialized failure code when stopped early, and makes indefinite capture stop return failure as documented. It does **not** address independent `fopen/open`, stdout `printf`/flush errors, or wrapper signal handling. A production fix should test normal completion, early SIGTERM/SIGINT, SIGPIPE, signal during the ignore region, finite zero count, indefinite mode, and missing output path. Do not claim the patch compiled or passed tests.

## Related source-only observation (not conflated)
Both inspected `streamer_usr.c` revisions open a named input file and immediately `close(0); dup2(fd,0)` without checking either return; `sampler_usr.c` likewise opens its output file and `close(1); dup2(fd,1)` without checking. File-open failure can therefore escape the intended initialization-error reporting, with exact subsequent effects depending on FD reuse and stdio behavior. This is a **separate source-confirmed error-handling gap**, not a guaranteed exit-code oracle and not part of the proposed one-line stop patch. Do not infer successful file delivery from `loadusr -w` alone.


## Additional cross-layer diagnostic discrepancy: HAL sample-num versus stream sequence
Development [`sampler(9)`](https://github.com/LinuxCNC/linuxcnc/blob/67437d8865e431a9a33f74cee912dbf891d3b4c5/docs/src/man/man9/sampler.9.adoc) (blob `04b8000b6c3f7ff09377d6a5f2328a43a07cb049`) says `sampler.N.sample-num` is automatically incremented for each sample and can be reset with `setp`. **The inspected stable and development `sampler.c` instead only export/initialize this HAL_IO pin; neither `sample()` callback increments it.** By contrast, `hal_lib.c::hal_stream_write` increments the stream's internal `fifo->this_sample` for every successful write, and `sampler_usr.c` obtains `this_sample` from `hal_stream_read` and prints it with `-t`. Thus a changing `halsampler -t` tag is **not evidence that `sampler.N.sample-num` is changing**, and setting the HAL pin does not demonstrably reset the FIFO sequence. This is a second **SOURCE/DOC-CONFIRMED discrepancy**, with runtime HAL pin behavior still **NOT RUN**. It is not evidence that stream sample tags are themselves broken; distinguish the two counters before using them for diagnostics.
