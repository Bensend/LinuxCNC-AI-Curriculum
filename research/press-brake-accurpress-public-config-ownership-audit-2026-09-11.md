# Press-brake public Accurpress config — ownership and timing audit

Date: 2026-09-11
Status: **DEPENDENCY-SAFE 4600 RESEARCH / PUBLIC COMMUNITY CONFIG AUDIT**

## Purpose

Close the current 4600 preparation checkpoint requiring at least one downloadable public press-brake LinuxCNC HAL/INI/config set, then map its actual signal ownership and realtime execution order against the machine-agnostic layered contract.

This is not a recommendation to copy the configuration onto a machine. The files were posted during an active retrofit/debugging thread and the architecture continued to evolve afterward.

## Community evolution before interpreting the files

The thread matters because the files are not a polished final reference design.

The initial `press.comp` was explicitly presented as a first attempt. Its `brake-pos-fb` pin is described as `Position feedback of the press`; the component emits a target position and speed, intended to feed `limit3` or `simple_tp`, then a PID. The state machine handles pedal down/up, approach, bend, tweak, return, backstop positioning, abort and an interlock. Andy Pugh immediately noted that the state machine probably needed timeouts and overload escape paths.

The attached `accurpress.hal`/`.ini` then came from the machine owner while trying to merge that concept into an existing PNCconf/MOTMOD setup. Andy's immediate integration advice was that the simple trajectory planner should feed the PID and that MOTMOD/KINS could be removed for the standalone custom-control approach; he also explicitly noted that his example did not yet provide homing, machine on/off or E-stop control.

As requirements for homing and generic jogging accumulated, Andy later wrote that he was starting to think the HAL-component approach had been a mistake because the machine increasingly looked like a conventional CNC machine, while still observing that pedal-controlled up/stop/down belongs in realtime rather than in a GUI. The machine owner then proposed keeping conventional CNC homing separate while retaining a ram-specific component.

**Evidence class:** COMMUNITY-REPORTED design evolution. It is strong evidence about what the participants tried and reconsidered, not proof of a universally correct press-brake architecture.

## What the downloadable configuration actually does

### 1. HostMot2 and nominal machine structure

The HAL loads:

- KINS and MOTMOD;
- `hostmot2` + `hm2_eth` for a Mesa 7i97;
- four PID instances (`pid.x`, `pid.y`, `pid.z`, `pid.s`);
- `press`, `limit3`, `simple_tp`, scaling/offset helpers and an E-stop latch.

The INI declares three joints with `trivkins coordinates=XYZ`. Joint 1 is the ram Y joint.

**Evidence class:** CONFIG-CONFIRMED from the public HAL/INI.

### 2. Physical Y feedback reaches PID and MOTMOD

The physical ram encoder path is:

```text
hm2_7i97.0.encoder.00.position
    -> signal y-pos-fb
       -> pid.y.feedback
       -> joint.1.motor-pos-fb
```

So the physical encoder is retained as both PID feedback and MOTMOD joint feedback.

**Evidence class:** CONFIG-CONFIRMED.

### 3. MOTMOD does not own the attached Y command path

The conventional PNCconf command connection is present but commented out:

```text
# net y-pos-cmd <= joint.1.motor-pos-cmd
```

Instead, the active Y command is:

```text
press.0.brake-pos-cmd -> simple-tp.0.target-pos
press.0.brake-vel-cmd -> simple-tp.0.maxvel
simple-tp.0.current-vel -> y-pos-cmd -> pid.y.command
pid.y.output -> hm2_7i97.0.pwmgen.00.value
```

This is a hybrid ownership topology: MOTMOD still exists, receives physical ram feedback and provides `joint.1.amp-enable-out`, but the active Y PID command does not come from `joint.1.motor-pos-cmd`.

**Evidence class:** CONFIG-CONFIRMED.

### 4. The press state machine is not observing the physical ram encoder in this attached HAL

This is the most important audit finding.

The `press.comp` pin was described in the forum source as:

```text
pin in float brake-pos-fb "Position feedback of the press";
```

But the attached machine HAL connects:

```text
simple-tp.0.current-pos -> brake-fb -> press.0.brake-pos-fb
```

It does **not** connect the physical `y-pos-fb` encoder signal to `press.0.brake-pos-fb`.

At the curriculum's pinned LinuxCNC revision, `src/hal/components/simple_tp.comp` defines `current-pos` as `position commanded at this point in time`. Its update function computes trajectory velocity and then integrates that velocity into `current_pos`:

```text
current_pos = current_pos + current_vel * period
```

Therefore, absent a historical semantic difference in `simple_tp`, the attached press state machine changes phase using the planner's internal command trajectory rather than directly using measured physical ram position.

That distinction is operationally important. A state-machine transition such as “reached bend target” can become true in the planner even if the physical ram lags, stalls, or otherwise fails to follow. PID/MOTMOD may still detect some physical tracking failures, but the press-cycle coordinator's own `brake-pos-fb` name is not evidence that it sees physical ram truth.

**Evidence class:**

- CONFIG-CONFIRMED for the actual net connection;
- SOURCE-CONFIRMED at pinned `8bf4605...` for `simple_tp.current-pos` semantics;
- version caveat remains because the attachment was generated against development 2.9 in 2021.

### 5. Servo-thread ordering inserts a deterministic command-age boundary

The attached servo-thread ordering is:

```text
hm2 read
motion-command-handler
motion-controller
pid.x
pid.y
pid.z
pid.s
hm2 write
...
press.0
limit3.0
simple-tp.0.update
...
```

LinuxCNC HAL documentation states that functions in a realtime thread execute in the order they were added.

Consequently, within one servo iteration:

1. HostMot2 reads fresh hardware feedback.
2. `pid.y` runs using the `y-pos-cmd` value left by the preceding `simple_tp` execution and the newly read encoder feedback.
3. HostMot2 writes that PID result.
4. Only afterward does `press.0` compute the next semantic target/velocity and `simple-tp.0.update` advance the next planned state/velocity.
5. That newly produced `simple_tp.current-vel` is consumed by `pid.y` on the next servo invocation.

This is a deterministic one-servo-period producer/consumer age relationship. It is not automatically a defect, but it must be recognized when debugging timing or comparing same-row/same-cycle observations. Moving functions casually would change the controller's temporal semantics.

**Evidence class:** CONFIG-CONFIRMED ordering + DOC-CONFIRMED LinuxCNC `addf` semantics.

### 6. The active Y PID command/feedback dimensions deserve explicit scrutiny

The active HAL connects:

```text
simple-tp.0.current-vel -> pid.y.command
physical encoder position -> pid.y.feedback
```

The attached INI sets Y `P=0`, `I=0`, `D=0`, `FF0=0`, `FF1=1`, `FF2=0`.

At pinned LinuxCNC source/documentation, PID computes:

```text
error = command - feedback
output = ... + command*FF0 + commandD*FF1 + commandDD*FF2 + ...
```

and `simple_tp.current-vel` is explicitly a velocity command while the encoder signal is position. With P/I/D and FF0 zero, the configured FF1 term is based on the derivative of that velocity command.

This is enough to flag a **unit/semantic ownership question**, but not enough to claim what the 2021 machine physically did or that the attachment is simply “wrong.” It may represent an incomplete merge, experimental tuning state, or historical component usage. The thread itself documents active integration/debugging around these files.

**Evidence class:** CONFIG-CONFIRMED wiring + DOC/SOURCE-CONFIRMED current PID/simple_tp semantics; historical intent/physical behavior **UNKNOWN**.

### 7. Pressure feedback existed but was not yet part of the shown press control path

The public HAL maps a Mesa analog input through a scale component to `y-press-fb` with gain 600. In the shown file, that pressure signal is not connected to `press.0` or a pressure-limit state.

The forum discussion later proposed placing pressure limits in the press component and adding an overpressure state that only allowed upward motion. That was a design proposal, not evidence that the attached file already implemented it.

**Evidence class:** CONFIG-CONFIRMED for acquisition; COMMUNITY-REPORTED for proposed integration.

### 8. The shown E-stop path is software loopback, not evidence of a safety function

The active lines are:

```text
ioControl.0.user-enable-out -> estop-out -> iocontrol.0.emc-enable-in
```

The physical/remote E-stop latch lines in that file are commented out.

Therefore this attachment cannot be cited as evidence of an external hardware E-stop chain, functional-safety architecture, or validated press safeguarding. The thread author/developer also explicitly noted that machine on/off and E-stop were not yet handled at that stage.

**Evidence class:** CONFIG-CONFIRMED plus COMMUNITY-REPORTED limitation.

## Source-grounded function / signal guide

Pinned LinuxCNC revision for implementation semantics: `8bf4605ae81042248add031e94c77300406e0413`.

| Surface | Producer / function | Consumer | Meaning in this config | Important timing / failure implication |
|---|---|---|---|---|
| physical ram position | `hm2_7i97.0.encoder.00.position` after HostMot2 read | `pid.y.feedback`, `joint.1.motor-pos-fb` | measured Y position | available before PID in same servo invocation |
| press target position | `press.0` | `simple-tp.0.target-pos` | semantic cycle target | produced after PID/HM2 write in this thread |
| press max velocity | `press.0` | `simple-tp.0.maxvel` | phase-specific speed | same ordering as above |
| planner position | `simple-tp.0.update` | `press.0.brake-pos-fb` on next invocation | internally integrated commanded position | not physical ram truth |
| planner velocity | `simple-tp.0.update` | `pid.y.command` on next invocation | internally planned velocity | command is one servo invocation old when PID consumes it |
| Y effort | `pid.y.do-pid-calcs` | Mesa PWM value | ordinary output request | written to hardware later in same invocation before next press/simple_tp update |
| Y enable | `joint.1.amp-enable-out` | `pid.y.enable`, Mesa PWM enable | MOTMOD-owned enable reused by custom command path | hybrid ownership must be explicit |
| pressure | Mesa analog input -> `scale.0` | `y-press-fb` only in shown file | measured pressure-like signal | acquisition exists but shown cycle logic does not consume it |

## End-to-end Y command / feedback call flow

```text
foot / ram-up / abort inputs
        |
        v
press.0 state machine
  - selects phase target and max velocity
        |
        v
simple_tp.0.update
  - plans current velocity
  - integrates an internal commanded current position
        |                       \
        |                        -> internal current-pos -> press.0 brake-pos-fb next cycle
        v
simple_tp.current-vel
        |
        v   [next servo invocation]
pid.y.command
        ^                  physical feedback
        |                        ^
        |                        |
        |              hm2 encoder.00.position
        |                        |
        +-------- pid.y.feedback +----> joint.1.motor-pos-fb
                  |
                  v
             pid.y.output
                  |
                  v
         hm2_7i97 pwmgen.00.value
                  |
                  v
             hardware write
```

The critical observation is that the cycle state machine and the PID do not use the same notion of “position feedback” in the attached configuration.

## Mapping to the layered ownership contract

| Contract layer | Public Accurpress evidence | Audit judgment |
|---|---|---|
| A — press-cycle coordinator | `press.0` owns approach/bend/tweak/return/backstop semantic state | Strong match in concept, but its shown position witness is planner state rather than direct plant state |
| B — LinuxCNC motion/joint owner | MOTMOD/KINS loaded; joint Y gets encoder feedback and supplies amp-enable | **Hybrid / ambiguous ownership** because active Y command bypasses `joint.1.motor-pos-cmd` |
| C — Y1/Y2 sync/final allocation | no tandem Y1/Y2 pair in these attachments | No evidence; must not be generalized to tandem-beam synchronization |
| D — hydraulic-mode decoder | direct PID-to-PWM path shown; no general discrete valve truth table here | Limited evidence only; machine-specific hydraulic decoding remains unresolved |
| E — electrical/drive interface | Mesa PWM generator is the Y output boundary | Concrete public example of an electrical command boundary, but output semantics/units need machine-specific validation |
| F — external safety | active LinuxCNC E-stop is a loopback; hardware latch lines commented | Explicitly **not** safety evidence |

## Corrections to generic 4600 reasoning

1. **Signal names are not evidence of physical truth.** A pin named `brake-pos-fb` can be driven by a planned command state. Trace the producer.
2. **Ownership must be established from active nets, not from the presence of MOTMOD.** A config can retain joint feedback and amp-enable while bypassing joint motor command.
3. **Thread order is part of the architecture.** In a mixed realtime pipeline, knowing the graph without knowing `addf` order is insufficient.
4. **A cycle-state coordinator should distinguish planned trajectory state from measured plant state.** If both are useful, give them separate names and explicit validity/freshness semantics.
5. **Do not infer tandem/Y1-Y2 competence from a single-ram retrofit.** This configuration is useful for sequencing/ownership lessons only.
6. **Do not infer safeguarding from ordinary E-stop nets.** The shown config itself demonstrates why public machine files require a separate safety audit.

## Adversarial architecture check

Scenario: a press-cycle component reports that the bend target has been reached because its `*-pos-fb` input is within tolerance. The physical ram encoder is still 8 mm away because the hydraulic actuator stalled. MOTMOD is loaded and the GUI displays an actual-position DRO.

A correct architecture review must **not** conclude that the component necessarily observed the physical ram or that loading MOTMOD guarantees command ownership. First trace the producer of the component's feedback signal and the producer of the Y PID command. In the audited Accurpress file, the cycle component sees `simple_tp.current-pos`, while the physical encoder feeds PID/MOTMOD separately. The two surfaces can therefore disagree.

This check is deliberately answerable from the public config plus LinuxCNC component semantics; no hydraulic simulation is required.
