## Hazardous false assumptions and normal-control design implications

| Assumption | What source/documentation actually supports | Consequence if mistaken |
|---|---|---|
| 'Feed Hold is asserted, so all jogs are blocked' | The **manual** says G-code-only, and current keyboard/halui jog command handlers use separate `jog-inhibit`; **however joint wheel-jog input processing checks `net_feed_scale`**. | Neither the broad manual statement nor the wheel exception establishes a universal jog inhibit or physical safety stop. Exact command family/enables/state matter. **SOURCE-CONFIRMED paths; selected runtime UNKNOWN.** |
| 'Feed Hold is always active' | `M53 P0` can disable `motion.feed-hold` effect. | An HMI light showing a HIGH pin does not prove commanded feed is inhibited. |
| 'Feed Inhibit stops every move immediately' | Documented spindle-synchronized move may complete; non-synchronized feed decelerates. | A lathe threading/tapping or analogous synchronized motion cannot use this as a universal personnel-safety stop. |
| 'Jog Inhibit stops an already active jog' | Source command handler rejects **new** jog requests; a **separate** jog-stop path addresses active jogging. | A retrofit may confuse prevention of initiation with termination of existing motion. Actual behavior requires design-specific validation. |
| 'Jog Stop Immediate is a safe E-stop' | Ordinary motion implementation warns of possible following errors. | A software command is not independent energy removal, gravity hold, or safety stop validation. |

**Practical OpenPressBrake transfer:** A normal controller may use feed/jog pins to improve setup ergonomics and avoid unintended normal commands. It must not treat them as independent AKAS muting, Y1/Y2 safe speed, safe stop, gravity-load holding or access protection. Actual installed safety PLC, hydraulic valve state and physical motion witnesses remain UNKNOWN. A builder tempted to jumper a sensor because `jog-inhibit` causes nuisance trips needs a usable safe setup mode and independently validated protective device, not a hidden bypass.

## Source-depth addendum: homing-inhibit is an initiation gate, not an active homing stop

[Development `motion.9.adoc` lines 202–205](https://github.com/LinuxCNC/linuxcnc/blob/c9a5a0a5034177c8db64cb44abf14d4f2eb166f7/docs/src/man/man9/motion.9.adoc#L202-L205) explicitly describes `motion.homing-inhibit` as **disallowing initiation** of joint homing, with an error. [`src/emc/motion/command.c` around lines 1520–1535](https://github.com/LinuxCNC/linuxcnc/blob/c9a5a0a5034177c8db64cb44abf14d4f2eb166f7/src/emc/motion/command.c#L1520-L1535) checks the pin before `do_home_joint`. A source search of the inspected motion control/command paths did not find a continuous active-homing cancellation check on that pin. **SOURCE/DOC-CONFIRMED:** it is a start-authorization gate; **INFERENCE:** changing it HIGH during active homing should not be relied on to stop that motion. Actual homing abort behavior for a selected configuration remains UNKNOWN and needs an independently defined protective stop if people can be exposed. This is a separate false-safety assumption from feed/jog but belongs to the same normal-motion command-authority family. No live test or extra paper bank.
