## Breadth conclusions

1. Conventional gantry routers are well served by existing LinuxCNC primitives rather than a dedicated router process component.
2. Public modern configs already demonstrate XYYZ gantry squaring, Mesa Ethernet motion, ATC spindles, rack toolchangers, fixed tool setters, work probes, Modbus VFDs, air-pressure monitoring and actuated dust shoes.
3. Industrial woodworking centers are the uniquely deep 3400 branch: drill banks, horizontal drills, multiple routing heads, aggregate saws, distributed pneumatics/I/O, vacuum pods and full-machine tool/head offsets.
4. Tool identity, mechanical toolchange state and tool-length offset state must remain separate.
5. Vacuum/dust/pneumatic state must be treated as production state with explicit manual/automatic authority and recovery, not merely spare outputs.
6. Commercial woodworking software shows a feature/workpiece-oriented workflow with drilling, routing, saw, clamp/pod and nesting concepts. LinuxCNC should own real machine state and trajectory while CAM/post carries manufacturing intent.

## Discovery targets

- **FreeCAD CAM** — open-source CAM integrated with FreeCAD. Inspect its LinuxCNC postprocessor, operation model, tool-controller model, probing/tool-length possibilities, nesting/woodworking suitability and extension points. Determine how much of a LinuxCNC router/woodworking workflow can remain inside an open-source CAD/CAM stack and what would need custom woodworking-specific operations or post extensions. Preserve license/provenance and inspect source rather than treating generated G-code behavior as a black box.
- **Open-source nesting engines** — evaluate embeddable irregular 2D nesting engines rather than assuming the LinuxCNC UI must launch a separate desktop CAM application. Current candidates include Deepnest/deepnest-next and other source-available nesting libraries. Prefer engines with a clean callable API/library boundary, offline/local operation, DXF/SVG/polygon support and licenses compatible with a LinuxCNC-integrated workflow.

## 3400 product-direction requirement — CAM and nesting inside LinuxCNC UI

The desired end-state is that a LinuxCNC QtVCP-based screen can expose a native-feeling **CAM / Nesting** workspace rather than forcing the operator to leave LinuxCNC for routine router or sheet-nesting work.

Target operator flow:

1. Import one or more part files or select existing job geometry.
2. Set quantity, material/sheet size, grain/rotation constraints, spacing and reusable remnant/stock where applicable.
3. Run automatic nesting and allow manual move/rotate/re-nest adjustments.
4. Assign or confirm tools, feeds/speeds, depths, tabs/bridges, drilling, pockets, contours and woodworking-specific features.
5. Generate LinuxCNC-targeted G-code locally.
6. Validate/post-process the program, show tool/operation summary and preview the final LinuxCNC path.
7. Load the generated program directly into the running LinuxCNC UI for operator review and execution.

Architecture preference:

- Use **QtVCP/PyQt integration** for the operator surface; LinuxCNC already supports custom QtVCP screens/panels and native panel embedding.
- Treat nesting and CAM computation as **userspace/offline planning**, never realtime HAL logic.
- Prefer calling reusable open-source engines/libraries directly from Python or a small local service/process instead of screen-scraping or automating an external GUI.
- Investigate using **FreeCAD CAM as a headless/programmatic toolpath and postprocessing engine** where practical, with its LinuxCNC postprocessor as a starting point rather than embedding the entire FreeCAD desktop UI.
- Keep the nesting engine replaceable behind an internal geometry/job interface so Deepnest or another engine can be swapped without rewriting the LinuxCNC UI.
- Preserve a machine profile describing available tools/heads, spindle limits, drill banks/aggregates, usable work envelope, vacuum/clamp restrictions and LinuxCNC post requirements.
- The generated artifact handed to LinuxCNC must be ordinary inspectable G-code plus durable job metadata; the controller should not depend on the CAM engine remaining alive while a program runs.

Research should explicitly compare two integration strategies:

1. **Library/service architecture (preferred):** QtVCP native UI -> local nesting/CAM engine -> LinuxCNC post -> preview/load.
2. **Embedded external application:** QtVCP embeds or launches an existing CAM application. Keep this only as a fallback or transitional path because it creates focus, lifecycle and workflow-integration problems and usually exposes more UI than an operator needs.

The first proof-of-concept should be intentionally narrow: import 2D DXF/SVG parts, nest them on sheet stock, generate simple profile/pocket/drill G-code with a LinuxCNC post, preview it, and load it directly from a QtVCP tab. Industrial woodworking extensions should follow after the basic geometry/post pipeline is stable.

### 3400-I2 — CAM/post, nesting and workholding boundary

Compare LinuxCNC machine-state needs against current woodworking workflows such as HOMAG woodWOP, Biesse B_SOLID/B_NEST and SCM Maestro.

Also inspect **FreeCAD CAM** as the primary open-source CAM discovery target. Source-trace its LinuxCNC postprocessor and extension model, then evaluate whether router/woodworking concepts such as drill-bank operations, multiple heads, saw aggregates, vacuum/clamp state and feature-oriented work preparation can be represented cleanly or would require custom operations/post logic.

Evaluate open-source nesting engines for direct QtVCP integration. The goal is a LinuxCNC-native operator flow for import -> nest -> toolpath -> LinuxCNC post -> preview -> load, with FreeCAD CAM or another source-available engine providing toolpath generation behind the UI where technically appropriate.

Do not copy proprietary controller behavior. Extract only domain concepts such as feature-oriented drilling/routing/saw operations, clamp/pod representation, nesting, tool management and collision-aware work preparation.

## Promotion boundary

Do not build a final 3400 playbook until at least one modern small-shop router config, one industrial woodworking drill/multi-head implementation and one real vacuum/pod/zone implementation have been source-traced deeply enough to preserve normal and recovery behavior.

The integrated CAM/nesting concept is not considered demonstrated until a prototype can take simple 2D part geometry through local nesting and toolpath/post generation into inspectable LinuxCNC G-code and load that program from a QtVCP-based UI without requiring the operator to switch to an external desktop application.
