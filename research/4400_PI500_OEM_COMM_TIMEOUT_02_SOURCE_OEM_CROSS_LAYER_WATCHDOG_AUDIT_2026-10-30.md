# 4400-PI500-OEM-COMM-02 — A frozen HAL heartbeat is not a VFD communications timeout
**2026-10-30 | exact LinuxCNC source + PI500 manufacturer-authored manual transcription | SOURCE/DOC cross-layer review | NON-GRADUATED | NO HARDWARE TEST**

## Question, predecessor and novelty
The preceding [PI500-VFD-01 source audit](4400_PI500_VFD_01_LINUXCNC_PIN_REMOTE_TRIP_CLAIM_VS_COMMENTED_OUT_SOURCE_PATH_AUDIT_2026-10-30.md) proves that `enable=0` does not transmit a trip or STOP when the last polled status has no alarm. **New question:** Could the driver's `watchdog_out` or the PI500's own communication timeout still make that a reliable ordinary stop? This audit connects **the LinuxCNC source's continuing status reads** to **the OEM's configurable timeout and fault-action options**. This is an incremental cross-layer failure discriminator, **not** a new scored safety competency and **not** a claim about an installed drive.

Predecessors: VFD-EXIT-01 covers process exit/retained commands; RST-01 covers deliberate restart; VFD-RESTART-01 covers Schneider retry; PI500-VFD-01 covers the missing trip. None of those earlier reports establishes the PI500 OEM `F9.04`/fault-action/command-word contract *composed with* this specific source branch.

## Pinned source and OEM evidence

1. **SOURCE-CONFIRMED:** [LinuxCNC `pi500_vfd.comp` at commit `e1c6a557c0e1c61961f17ee35a1ba188e7db275f`](https://github.com/LinuxCNC/linuxcnc/blob/e1c6a557c0e1c61961f17ee35a1ba188e7db275f/src/hal/user_comps/pi500_vfd/pi500_vfd.comp), blob `92cc57bdf5214bbb3fb92103837539e42a76d452`. `pi500_getStatus` makes successive Modbus reads of `0xF001`, `0xF002`, `0x3000`, `0x1000` and `0x8000`. On successful reads with `status.alarm=false` and `enable=false`, the main loop logs `failed to trip` and `continue`s, skipping the RUN/STOP write **and** the HAL `watchdog_out` toggle. It then loops back to status reads; the source does **not** stop polling or disconnect the Modbus link. `pi500_run(false)` would write `0x2000=6`, but that function is not called in this branch. The commented `pi500_trip` proposed `modbus_write_bit(ctx,0x002,TRUE)`, whose target semantics are **not established** by the inspected OEM command table.
2. **DOC-CONFIRMED at manufacturer-authored 2018 PI500 manual, third-party transcription:** [Powtran PI500 Series, March 2018, Appendix I, printed pp.90 and 92, hosted at ManualsLib pages 94 and 96](https://www.manualslib.com/manual/1658524/Powtran-Pi500-Series.html?page=94). Modbus holding command word `0x2000`: `1` forward RUN, `5` free stop, `6` deceleration-and-stop, `7` fault reset. The published list does **not** document a `0x0002` coil remote-trip command; absence from that list does not prove no firmware-specific remote trip exists. [F9.04 on mirrored page 96](https://www.manualslib.com/manual/1658524/Powtran-Pi500-Series.html?page=96): communication timeout default **0.0 s (disabled)**; a nonzero `0.1–60.0 s` setting reports Err.16 if the interval between communications exceeds the configured time. **Do not mistake an OEM error report for proof of a physical safe stop.**
3. **DOC-CONFIRMED at the same 2018 manual transcription:** [F8.18, mirrored page 52](https://www.manualslib.com/manual/1658524/Powtran-Pi500-Series.html?page=52) assigns communication-abnormal Err.16 to the ten-thousands digit, with the same choices as the units digit: `0` free stop; `1` change to V/F then stop in selected mode; `2` change to V/F and **continue running**. The table shows factory `00000` for F8.18; this is an **edition-specific documented default**, not an as-installed setting. The selected drive's fault logic, firmware and load response remain UNKNOWN.
4. **Manufacturer-hosted indexed corroboration, not full PDF inspection:** [Powtran PI500-S English Manual V1.0 (2020 URL)](https://www.powtran.com/upload/202005/19/202005190953281270.pdf) search-indexed passages separately show `0x2000` commands `1/5/6/7` and `F9.04=0.0` invalid by default. The direct PDF fetch returned 404 on 2026-10-30. The OEM's [PI500 V5.1 manual landing page, posted 2025-12-18](https://en.powtran.com/Download_1/33.html) was inspected, but its 7.4 MB PDF could not be retrieved directly. **Do not assert that the 2018/2020 parameters and defaults apply unchanged to V5.1, clones, or any installed unit.**
5. **SOURCE-CONFIRMED issue-search scope:** 2026-10-30 GitHub issue search `repo:LinuxCNC/linuxcnc is:issue pi500` found two unrelated issue titles (#2572, #1941), and exact `"failed to trip"` found none; PI500 PR #1172 is the historical addition. This is **not proof that no report, workaround, or maintainer rationale exists**. The component history lists subsequent 2026 changes (e.g. 2026-09-27 HAL API migration), but the inspected branch and blob remain the source snapshot.

## Four distinct stop/fault paths (not interchangeable)

| Scenario | What the LinuxCNC source does | What the OEM text supports | What is NOT established |
|---|---|---|---|
| `enable=0`, healthy serial replies, no alarm | Repeats status reads, skips stop/trip, freezes **HAL** heartbeat | F9.04 detects a *gap in communication* if enabled; ordinary successful polling is not a proven gap | That a downstream HAL heartbeat monitor exists, that the drive stops, or that a safety final element acts |
| Driver/process exits or cable fails | No further successful driver writes; stale HAL outputs may persist until an external consumer detects loss | 2018 F9.04 default disabled; if enabled, a communication fault is documented after its configured interval | Exact drive firmware/parameter, whether Err.16 causes free stop or continued operation, and physical deceleration |
| `run=0`, `enable=1`, status reported running | `pi500_run(false)` attempts `0x2000=6` | OEM defines **ordinary deceleration stop** | Torque removal, standstill, guard unlock or maintenance isolation |
| `status.alarm=1`, `enable=1`, `run=1` | Attempts `0x2000=7` fault reset, sleeps 1 s, then can issue normal RUN based on *pre-reset polled* status | OEM defines `7` as fault reset | That the drive accepts RUN, or that fresh deliberate restart is enforced |

**Cross-layer deduction (INFERENCE, not TEST-CONFIRMED):** When `enable=0` and status polling succeeds, the HAL `watchdog_out` stops toggling while Modbus requests **continue**. Thus a VFD watchdog based on *lack of communication* cannot simply be equated with the frozen HAL heartbeat; if the OEM counts the status requests as communications, the VFD timeout will not expire. Even if F9.04 is nonzero, this branch is not a guaranteed timeout-triggering stop. Conversely, on actual serial loss, F9.04 can be disabled or F8.18 can be configured to continue running on Err.16. The exact counting semantics, physical behavior and installation are UNKNOWN.

## Upstream review handoff — avoid a misleading one-line fix

**Question to maintainers:** Is `enable` intended to mean a Modbus remote trip, a normal RUN inhibit, or an operator-controlled fault reset/rearm? The documented promise and source disagree. A patch that merely uncomments `pi500_trip` would call an unverified `0x0002` coil and could still leave alarm/enable false paths able to issue RUN. The upstream review should specify a **non-safety-rated ordinary-control contract** first.

**Proposed acceptance questions, not an implemented patch:** (a) With `enable=0` and all alarm/run/status combinations, is any RUN write forbidden? (b) Is an ordinary STOP command sent when communication is healthy, and is failure explicitly observable? (c) Does clearing an alarm require an intentional reset request rather than an indefinitely held enable? (d) Are stale `is_running`/`is_ready`/watchdog values distinguishable from fresh replies? (e) Are startup, serial loss/recovery and held RUN rearm semantics specified? (f) Do selected exact-model OEM commands and F9.04/F8.18 settings match? These are **source/design review gates**; any executable fixture would need a frozen oracle and the qualified isolated local runner, not hosted compute or a live machine.

**Practical human factors:** Provide one clear normal spindle STOP and a separate independent protective stop. Show “RUN requested”, “drive-reported running”, “driver communications fresh”, “safety stop active” and “physically isolated” as different states. Do not encourage operators to use cable disconnection or software enable as a guard workaround.
