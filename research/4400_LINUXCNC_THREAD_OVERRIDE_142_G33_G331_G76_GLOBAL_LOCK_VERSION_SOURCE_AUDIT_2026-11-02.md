# 4000-LC-THREAD-142 — G33, G33.1 and G76 spindle override: versioned control path and global lock scope

**2026-11-02 ~01:37Z | 3200 lathe / 4000 LinuxCNC implementation | NON-GRADUATED.** Pinned-source and upstream expected-output inspection, **NOT EXECUTED**. This is not another discovery of the M51/inhibit bitmask: that was already established by [OVERRIDE-93](4400_LINUXCNC_OVERRIDE_93_FEED_INHIBIT_SS_BIT_COUPLING_SOURCE_AUDIT_2026-11-01.md), [OVERRIDE-94](4400_LINUXCNC_OVERRIDE_94_SPINDLE_INHIBIT_SS_BIT_SPEED_ON_SOURCE_AUDIT_2026-11-01.md) and [OVERRIDE-95](4400_LINUXCNC_OVERRIDE_95_M51_SELECTED_SPINDLE_DROPPED_AT_TASK_SOURCE_AUDIT_2026-11-01.md). ## Provenance and novelty boundary

Compared stable LinuxCNC **v2.9.10** (tag commit `86cdca76fa2a36274c432caa21952b23c267989a`) with development **`06864e23559e70463fc7112d5ce77138bcbc288c`**. Read actual `interp_convert.cc`, `emccanon.cc`, `emctaskmain.cc`, `taskintf.cc`, `motion/command.c`, `motion/control.c`, `motion.h`, `tp.c`, stable/development G-code docs, and upstream `tests/interp/g76/expected`. Previous [TAP-124/125](4400_LINUXCNC_TAP_124_G331_I_RETRACT_PREFLIGHT_CSS_RADIUS_VERSION_SOURCE_AUDIT_2026-11-01.md) addressed rigid-tap preflight and TP reversal; [SPINDLE-22](4400_LINUXCNC_SPINDLE_22_MULTISPINDLE_ATSPEED_INDEX_HANDSHAKE_SOURCE_AUDIT_2026-10-31.md) addressed selected-index versus all-spindle at-speed. [FEED-JOG-01](4400_LINUXCNC_FEED_HOLD_INHIBIT_JOG_STOP_SAFETY_AUTHORITY_SOURCE_AUDIT_2026-10-27.md) already establishes TP's synchronized feed-inhibit exception. Do not re-label those as discoveries here.

**Incremental question:** Which of G33/G33.1/G76 actually emits a spindle override control, how does that cross the Task boundary, and which spindles' override values are frozen or disabled? The development manual already documents the intended G33 suspension, G33.1 retention, and G76 capped lock; **that policy itself is not a new undocumented discovery**. The novel implementation consequence is that the motion-side mode remains **global** even though the interpreter/canonical command selects a spindle, and the G76 lock captures **every** configured spindle's scale.

### Canonical → Task → motion: the selector does not survive

In development, `suspend_speed_override`, `restore_speed_override` and `lock_speed_override` pass `settings->active_spindle` into canonical functions ([interp_convert.cc 5316–5342](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/rs274ngc/interp_convert.cc#L5316-L5342)). `emccanon.cc::SPEED_OVERRIDE_` places both `mode` and `spindle` in `EMC_TRAJ_SET_SO_ENABLE` ([3283–3305](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/task/emccanon.cc#L3283-L3305)). But `emctaskmain.cc` [1909–1910](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/task/emctaskmain.cc#L1909-L1910) passes **only mode** to `emcTrajSetSOEnable`; `taskintf.cc` [1333–1338](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/task/taskintf.cc#L1333-L1338) sends `EMCMOT_SS_ENABLE` without a spindle selector; `motion/command.c` [1408–1426](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/motion/command.c#L1408-L1426) changes **one global** `enables_new` bitmask. This Task selector loss is **already OVERRIDE-95**, reused here to establish its new effect during synchronized operations.

For a two-spindle machine with both speed overrides enabled, **G33 $1** in development emits `DISABLE_SPEED_OVERRIDE(1)` then `ENABLE_SPEED_OVERRIDE(1)`; the global SS_ENABLED bit is cleared then restored, so *both* spindle override multipliers can be bypassed during the G33 segment, not just spindle 1's. This is a **conditional SOURCE-DERIVED prediction**, not an observed two-spindle speed trace. If spindle 1's interpreter setting is already OFF, restore emits DISABLE instead; the other spindle's global motion setting can remain OFF despite its interpreter setting being ON. This follows the existing selector-loss mechanism and is not an independent defect proof.

### Development G76 lock: global latch and capped scales

`motion.h` [432–436](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/motion/motion.h#L432-L436) defines `SS_ENABLED=0x01` and `SS_LOCKED=0x10`. `EMCMOT_SS_ENABLE(LOCK)` **sets SS_LOCKED** but does not force SS_ENABLED ON. `control.c::process_inputs` [424–441](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/motion/control.c#L424-L441) detects the rising LOCK bit in the **effective** (queued in coordinated mode) flags and loops through **all** `numSpindles`, latching `locked_spindle_scale[s] = min(current_scale[s],1.0)`. Subsequent [494–507](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/motion/control.c#L494-L507) applies the locked scale only if SS_ENABLED is also present. This is realtime servo-side state, not interpreter bookkeeping.

**Frozen numerical discriminator (two spindles, default SS_ENABLED, G76 selects spindle 1):** spindle-0 operator scale 0.80 and spindle-1 scale 1.20; on first effective lock transition, the array becomes **[0.80, 1.00]**. The lock applies to both output scale calculations, despite the canonical selector being 1. The development manual's 100% cap is already documented, but **cross-spindle latching** is a distinct source-level implementation consequence. If `M51 P0` previously cleared SS_ENABLED, LOCK alone gives a bitmask containing 0x10 but does **not** apply a locked multiplier; the previously established inhibit-bitmask issue remains in effect. Exact queue boundaries and physical spindle speeds remain UNKNOWN.

### Feed-inhibit versus spindle-inhibit are different in synchronized motion

In both versions `tp.c::tpGetFeedScale` [225–246](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/emc/tp/tp.c#L225-L246) returns **1.0 for TC_SYNC_POSITION** after pause/abort checks, ignoring `net_feed_scale` during a position-synchronized move. This was already source-confirmed by FEED-JOG-01; it implements the documented delayed **feed**-inhibit behavior. Separately, `control.c` applies the **spindle** inhibit via `enables & bool(spindle_inhibit)`, with no corresponding TP position-sync bypass in that spindle scale path. Thus for SS_ENABLED=1 a TRUE spindle inhibit still forces requested spindle speed to zero during a G33.1/G76 synchronized segment, whereas development G33's temporary SS_ENABLED=0 also bypasses that inhibit expression. The spindle-speed-command consequence is **INFERENCE from source**, not an observed stop, encoder response, or safe-state claim.

**Do not propose `if (inhibit)` as a blanket fix** without keeping TP's synchronized feed-inhibit exception and checking spindle-command semantics during G33/G33.1/G76. Do not mistake an asserted `spindle.N.on` for measured RPM; OVERRIDE-94 already traced that separation.
