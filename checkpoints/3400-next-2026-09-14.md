## Breadth conclusions

1. Conventional gantry routers are well served by existing LinuxCNC primitives rather than a dedicated router process component.
2. Public modern configs already demonstrate XYYZ gantry squaring, Mesa Ethernet motion, ATC spindles, rack toolchangers, fixed tool setters, work probes, Modbus VFDs, air-pressure monitoring and actuated dust shoes.
3. Industrial woodworking centers are the uniquely deep 3400 branch: drill banks, horizontal drills, multiple routing heads, aggregate saws, distributed pneumatics/I/O, vacuum pods and full-machine tool/head offsets.
4. Tool identity, mechanical toolchange state and tool-length offset state must remain separate.
5. Vacuum/dust/pneumatic state must be treated as production state with explicit manual/automatic authority and recovery, not merely spare outputs.
6. Commercial woodworking software shows a feature/workpiece-oriented workflow with drilling, routing, saw, clamp/pod and nesting concepts. LinuxCNC should own real machine state and trajectory while CAM/post carries manufacturing intent.

## Discovery targets

- **FreeCAD CAM** — open-source CAM integrated with FreeCAD. Inspect its LinuxCNC postprocessor, operation model, tool-controller model, probing/tool-length possibilities, nesting/woodworking suitability and extension points. Determine how much of a LinuxCNC router/woodworking workflow could remain inside an open-source CAD/CAM stack and what would need custom woodworking-specific operations or post extensions. Preserve license/provenance and inspect source rather than treating generated G-code behavior as a black box.
- **Open-source nesting engines** — study embeddable irregular 2D nesting engines such as Deepnest/deepnest-next and other source-available nesting libraries. Compare API/library boundaries, offline/local operation, DXF/SVG/polygon support, licensing and suitability for a future LinuxCNC-integrated workflow.

## 3400 research topic — CAM and nesting inside LinuxCNC UI

Study the feasibility and architecture of a LinuxCNC QtVCP-based screen exposing a native-feeling **CAM / Nesting** workspace rather than forcing the operator to leave LinuxCNC for routine router or sheet-nesting work.

The curriculum should primarily **study and document this concept**. It must not turn 3400 into a software-product implementation project. However, small bounded prototypes or throwaway experiments are allowed when they materially improve understanding or make the AI more capable of implementing the concept later.

Study the desired operator flow conceptually:

1. Import one or more part files or select existing job geometry.
2. Set quantity, material/sheet size, grain/rotation constraints, spacing and reusable remnant/stock where applicable.
3. Run automatic nesting and allow manual move/rotate/re-nest adjustments.
4. Assign or confirm tools, feeds/speeds, depths, tabs/bridges, drilling, pockets, contours and woodworking-specific features.
5. Generate LinuxCNC-targeted G-code locally.
6. Validate/post-process the program, show tool/operation summary and preview the final LinuxCNC path.
7. Load the generated program directly into the running LinuxCNC UI for operator review and execution.

Research questions:

- Can QtVCP/PyQt cleanly host the operator surface while keeping nesting/CAM computation in ordinary userspace rather than realtime HAL?
- Can FreeCAD CAM be driven programmatically/headlessly enough to provide toolpath generation and LinuxCNC postprocessing without embedding the full FreeCAD desktop UI?
- Which open-source nesting engines expose sufficiently clean callable APIs or library boundaries for future embedding?
- What internal job/geometry interface would keep the nesting engine replaceable?
- What machine profile is needed to describe tools/heads, spindle limits, drill banks/aggregates, usable work envelope, vacuum/clamp restrictions and LinuxCNC post requirements?
- Can the handoff to LinuxCNC remain ordinary inspectable G-code plus durable job metadata so the CAM engine is not needed while the machine is executing?
- What licensing and packaging constraints would affect redistribution with LinuxCNC-oriented UI projects?

Compare at least these two architecture patterns on paper:

1. **Library/service architecture:** QtVCP native UI -> local nesting/CAM engine -> LinuxCNC post -> preview/load.
2. **Embedded external application:** QtVCP embeds or launches an existing CAM application.

Prefer evidence from existing APIs, source code, integrations and documented extension points. If source/API evidence leaves an important practical uncertainty, a deliberately small learning prototype may be used. Examples include: calling a nesting engine on a few polygons; driving FreeCAD CAM headlessly for one simple profile; producing LinuxCNC-posted G-code from a minimal job; or proving a QtVCP/PyQt panel can invoke a local planning service and receive a result. Such prototypes are evidence-gathering exercises only: they should be minimal, isolated, disposable if appropriate, and must not expand into a maintained production application. Any full implementation belongs in a separate product/development project after the curriculum has documented the architecture, candidate engines, constraints and unresolved risks.
