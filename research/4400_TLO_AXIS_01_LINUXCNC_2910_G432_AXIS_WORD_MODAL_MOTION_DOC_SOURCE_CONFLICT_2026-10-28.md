## Narrow engineering question and novelty

## Source-derived causal trace (NOT TEST-CONFIRMED)
1. Assume a normal CNC program/MDI context has previously selected **G0** (or G1) and no new motion word appears on a `G43.2 Z...` line.
2. `enhance_block` sees a Z word. G43.2 permits it as an offset operand **but unlike G43.1 does not suppress inherited `motion_to_be`**. If the modal motion is G0, `motion_to_be` becomes G0.
3. `convert_tool_length_offset` **adds** the Z operand to the current tool offset and adjusts the interpreter current Z to keep its model of the existing physical position consistent.
4. The same block's `convert_motion` can then process the Z operand as a **G0 endpoint**, emitting an ordinary traverse via `convert_straight`.
5. Therefore **SOURCE-CONFIRMED**: the inspected code contains a path that generates a normal motion command for G43.2 axis-word input under inherited G0/G1. **INFERENCE**: this can produce an unexpected nonzero move in a particular initial coordinate state. **UNKNOWN / NOT RUN**: exact displacement, simulator trace, actual machine behavior, and whether any additional downstream rejection occurs. This is a **DOC-CONFIRMED versus SOURCE-CONFIRMED conflict**, not a proven physical collision.
6. Distinguish **G43.2 Hn** (no axis word; this inherited-motion path does not arise), **G43.1 axes** (explicitly exempted from inherited motion in `enhance_block`), and **G43.2 axes with G80/no modal motion** (different path). These distinctions do **not** make G80, G49, H-word syntax, ordinary soft limits or a UI indicator into personnel-safety functions.

## Practical human-factors design
- For production, prefer a clearly separated **“measure/enter offset”** action and **“move”** action with visible applied offset, tool identity, active modal motion, machine position, and clearance preview. Make the reviewed safe workflow easier than an undocumented shortcut.
- Where additive wear offsets are required, review H-word or explicitly version-verified nonmoving procedures; do **not** assume an axis-word G43.2 is nonmoving just because the manual says so. Do not advise testing the disputed command on a live machine.
- Distinguish REQUESTED, OBSERVED, SAFETY-PERMITTED and PHYSICALLY VERIFIED states. On missing tool/guard/stop evidence, display **UNKNOWN / HOLD**, not a green check.
- Ordinary travel limits can reject out-of-range motion but cannot prove that an in-range position clears fixtures, tooling or people. Safety-related stopping, protective guarding and energy removal belong outside normal LinuxCNC/FPGA control.
- For hazardous machine access, retain guard, physical energy isolation and independently qualified stop/hold/restart behavior. No personnel-exposed operation below the minimum safe-to-operate threshold.

## Endpoint discriminator — G90 versus G91 (static source, no runtime)
The next function in the same chain, [`Interp::find_ends` L154–375](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/rs274ngc/interp_find.cc#L154-L375), blob `4c7255662357f1e570cbad49e80bc8322929a177`, makes the possible motion consequential: under **G90**, a present Z word becomes the **absolute program endpoint** (`*pz = block->z_number`, around L290), whereas under **G91** it is **added to the interpreter's current Z** (around L363). `convert_tool_length_offset` has already changed the current-coordinate model to preserve the original physical pose after adding the offset. The same numeric word can therefore serve both as **compensation** and as a **motion operand**. In a nondegenerate coordinate state the source path is capable of requesting a different endpoint; this remains a **static source prediction**, not an executed displacement, physical motion, or measured stopping result. A discriminating isolated simulation must preserve both G90 and G91 cases and compare emitted canonical commands with the pre-change physical pose. This is an important reason not to “fix” the discrepancy by simply choosing a smaller offset value or relying on soft limits.

## Adversarial countercheck — explicit motion word with G43.1 (same source, not tested)

The other branch of [`enhance_block` L175–195](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/rs274ngc/interp_internal.cc#L175-L195) assigns `motion_to_be = mode1` when a G0/G1 word **is explicitly present**. Add a disconnected-simulation negative-control case with explicit G0+G43.1 and preserve any actual error, emitted canonical command, and position trace; do not extrapolate the inherited-motion G43.1 exemption to explicit-motion lines.
