# 4400 G53-G91-01 — G53 machine-coordinate retract rejects incremental distance mode in LinuxCNC v2.9.10

**2026-10-29 UTC | Tagged LinuxCNC source/doc discrepancy, not a machine test | NON-GRADUATED**

## Narrow question and predecessor check
A CNC macro is in G91 incremental mode and tries to issue a G53 machine-coordinate retreat without explicitly selecting G90. Will the interpreter accept the command merely because G53's endpoint interpretation is absolute? **No in tagged v2.9.10: the interpreter rejects G53 when G91 is explicit or currently modal.**

This is **not** a new discovery that G53 is nonmodal, that G53 G0 XYZ is a simultaneous rapid, or that ordinary G-code is not a personnel safety function. [G28/G30-01](4400_G28_G30_01_LINUXCNC_2910_PERSISTENT_RAPID_REFERENCE_AND_WAYPOINT_HAZARD_SOURCE_AUDIT_2026-10-28.md) already traced `find_ends` G53 and suggested explicit machine-coordinate waypoints; [PATH-BLEND-01](4400_PATH_BLEND_01_LINUXCNC_2910_G64_G0_CLEARANCE_AND_STOP_MODE_SOURCE_AUDIT_2026-10-28.md) already explained rapid trajectory clearance and G64/G61. **Incremental source delta:** the G53 documentation error list omits a **third** source-enforced error: incremental mode. A script's intended retreat can fail at the interpreter before any new machine-coordinate motion, with possible downstream program-abort/recovery implications.

## Conditional failure path and useful discriminator
| Command context | Tagged source result | Safety significance |
|---|---|---|
| G91 already modal; `G53 G0 X...` with no G90 on block | `check_g_codes` rejects incremental mode | **SOURCE-CONFIRMED error path**; do not assume retreat executed or machine is physically safe |
| `G53 G91 G0 X...` | Explicit block G91 rejects | G53 is not an override for distance-mode validation |
| G91 previously modal; block explicitly includes G90 and G53/G0 | The cited incremental guard does **not** reject on this basis | Other validation/limits and physical trajectory still apply; **not runtime tested** |
| G90 modal; `G53 X...` with G0 already modal | Source check accepts G0/G1 inheritance and G53 conversion in this respect | Does not imply safe axis order, collision-free path or safety-rated motion |
| A later line omits G53 | G53 is nonmodal (DOC-CONFIRMED) | Next line uses current work-coordinate interpretation; operator must not infer G53 persists |

**INFERENCE:** If a macro treats an interpreter error as a successful “clearance achieved” or a technician manually continues after abort without re-establishing position/guard/energy state, a tool or ram may remain in the hazardous region. This is a **conditional program-recovery hazard**, not a source-confirmed automatic continuation or measured physical incident. An interpreter error normally indicates the requested line was not accepted; exact downstream abort/Task status and machine response were **not independently traced here**.

## Practical operator/macro review
For an ordinary CNC program that uses machine-coordinate waypoints, a reviewer should check explicit **G90**, explicit **G53 on each line**, the intended **G0/G1** mode, cutter compensation state, selected home/reference trust, actual tooling/fixture envelope, planned axis sequence and feed/path blending. Prefer separate documented clearance legs if required by the machine risk analysis; do not copy `X0 Y0 Z0` as a universal safe location. Make a failed retract **visible and non-bypassable in the normal recovery workflow** rather than suggesting the operator repeatedly press Cycle Start. These are ordinary-process design controls, not safety-rated functions.

**Independent personnel safety** remains owned by qualified safety controller, guard/protective devices and physical energy-removal/holding mechanisms. G53, G90, a soft limit, homed bit, LinuxCNC program error, FPGA status or HMI “safe” bit cannot prove Y1/Y2 gravity restraint or personnel clearance. Do not run a press brake to demonstrate this source-only issue.
