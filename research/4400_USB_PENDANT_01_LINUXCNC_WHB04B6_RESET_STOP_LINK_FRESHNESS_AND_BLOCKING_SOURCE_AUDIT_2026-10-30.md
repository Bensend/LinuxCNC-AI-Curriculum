# 4400-USB-PENDANT-01 — LinuxCNC XHC-WHB04B-6: RESET is machine-enable, STOP requests ordinary Task abort, USB presence is not protective radio supervision
**2026-10-30 | 4000/4400 safety course | SOURCE/DOC-CONFIRMED normal-control semantics | NON-GRADUATED | NO MACHINE RELEASE**

## Engineering question and novelty
Can a builder rely on the inexpensive XHC-WHB04B-6 wireless USB handwheel's **RESET**, **STOP**, or `whb.pendant.is-connected` signal as a personnel-protective E-stop, safe stop, or radio-link safety watchdog? **No such safety claim is established.** This audit identifies the actual ordinary-control implementation and an important documentation/source mismatch.

**Predecessor comparison:** [RAD-01](../safety-course/4400_RAD_01_WIRELESS_PENDANT_STOP_LINK_LOSS_AND_RESTART_MODULE_2026-10-24.md) concerns separately documented industrial safety-radio products and their selected configurations; [SIM-LOOP-01](4400_ESTOP_SIM_LOOP_01_OFFICIAL_STEPPER_EXAMPLE_EXTERNAL_ESTOP_FEEDBACK_COPY_RISK_SOURCE_AUDIT_2026-10-30.md) concerns example HAL E-stop feedback. Neither proves the LinuxCNC USB pendant's exact button implementation, radio freshness or same-loop blocking. This is a **new exact upstream-source mechanism and transfer**, not a new scored competency. Full canonical learner index and safety research plan were checked for pendant/HID/USB/WHB04B/RESET synonyms before selection.

### Downstream Task abort correction (adversarial source review)
An initial shorthand description of the STOP button as “program stop only” was **too narrow**. Stable v2.9.10 `src/emc/task/emctaskmain.cc` blob `7292a172023a5b42b023447c2458cb766c93fc9b`, `EMC_TASK_ABORT_TYPE` around lines **2108–2121**, calls `emcTaskAbort`, `emcMotionAbort`, `emcTaskStateRestore`, `emcIoAbort`, `emcSpindleAbort` for each configured spindle, `mdi_execute_abort` and `emcAbortCleanup`. **SOURCE-CONFIRMED:** ordinary STOP has a broader Task/motion/IO/spindle abort path than the man-page label alone suggests. **UNKNOWN:** actual physical deceleration, contactor state, energy isolation, hydraulic load holding and timing on any selected machine. These remain independent safety-function questions. [Pinned Task source](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/emc/task/emctaskmain.cc#L2108-L2121). This correction is recorded rather than quietly erasing the original over-narrow inference.

### Synchronous input-processing wait budget (source arithmetic, **not** physical stopping time)
The default `Profiles::halRequestSlowProfile` in stable `hal.h` around lines 70–88 configures **10 ms request hold**, up to **60 × 5 ms = 300 ms mode-feedback wait**, and **10 ms request spacing**. If a START press enters `Hal::requestAutoMode` with a mode transition and then `toggleStartResumeProgram`, `Hal::checkState` can add up to **500 × 1 ms = 500 ms** of ordinary program-state polling. These source-level nominal wait budgets sum to approximately **820 ms** on the relevant control path, excluding scheduling/USB overhead and contingent on mode and feedback branches; **they are not measured response times, hard real-time limits or safety stop times**. `Usb::onUsbDataReceived` calls `XhcWhb04b6Component::onInputDataReceived`, which calls `mPendant.processEvent` synchronously from the libusb event-processing loop. A blocking START handler can therefore delay subsequent ordinary pendant input handling on that loop. This is another reason the pendant STOP key must not be assigned personnel-safety authority. [Pinned profile](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/hal/user_comps/xhc-whb04b-6/hal.h#L49-L90), [callback](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/hal/user_comps/xhc-whb04b-6/xhc-whb04b6.cc#L156-L219).

### State-machine / failure-path trace
1. `pendant.cc` decodes a wireless input packet into a button press/release event; the user-space component invokes the corresponding HAL helper.
2. The **RESET** event can request machine ON when ordinary `isMachineOn` is false. Independent safety permissives must remain outside this command path. Neither RESET nor the subsequent LinuxCNC machine-ON state is evidence that a guard is closed, the area is clear or an independent safety reset has been deliberately accepted.
3. The **STOP** event requests ordinary `EMC_TASK_ABORT` through HALUI. The downstream Task handler calls motion, IO and spindle abort helpers, so it is **not accurate** to say the command only stops G-code execution. Nevertheless no independent safety contactor, certified STO path, safety hydraulic valve, physical standstill or gravity-load holding is proved by this command.
4. The USB receiver may remain enumerated while the remote is asleep or radio traffic is absent. `is-connected` is set on successful USB initialization, while `is-sleeping` is updated from packets. A timeout merely resubmits USB transfer in the inspected branch. **Do not equate USB enumeration with remote safety link supervision.**
5. **Startup readiness trap:** by default the component can announce `hal_ready` before a USB receiver has been found. The `Usb::init` path uses `libusb_open_device_with_vid_pid` and waits; no RF safety condition is proven by the readiness handshake. A machine must not make its only accessible emergency stop dependent on that receiver. `-t` may alter normal startup readiness but does not convert the pendant into a safety device.
6. If ordinary LinuxCNC/HAL, the pendant process, USB receiver or radio fails, the physical safety function must still be effective through an **independent** protective path. Whether any particular machine has that path is **UNKNOWN**.


### Downstream HALUI/NML trace (additional pinned stable source)
LinuxCNC v2.9.10 `src/emc/usr_intf/halui.cc` blob `6aa51870512c9d29919452aaec0377338e350a04` independently clarifies the **ordinary control command** produced after the pendant's HAL output is actually connected:
- `halui.machine.on/off` inputs are registered around lines 761–767. `check_bit_changed` around 1591–1599 returns true on a **rising edge**, and the poller around 1652–1663 sends `sendMachineOn/Off` only on that edge. Those functions construct `EMC_TASK_SET_STATE` with `EMC_TASK_STATE_ON/OFF` around 953–966.
- The *separate* `halui.estop.activate/reset` inputs trigger `EMC_TASK_STATE_ESTOP` / `EMC_TASK_STATE_ESTOP_RESET` around 969–982. The WHB04B-6 `setReset` method does **not** drive those pins.
- `halui.program.stop` around 1722–1723 invokes `sendAbort`, which sends `EMC_TASK_ABORT` around 1266–1271. Its Task handler has wider ordinary-control effects (motion, IO and spindle abort), **not** a physical safety final-element guarantee. The example HAL file explicitly connects the pendant's program-stop and machine-on/off outputs; other installations must be checked for actual connections.
- **SOURCE-CONFIRMED command dispatch**, **UNKNOWN** whether Task accepts a given machine-ON request in the current E-stop/guard state or what selected machine hardware does. Do not infer that an ordinary machine-on request bypasses independent safety.

[Pinned HALUI source](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/emc/usr_intf/halui.cc). This closes the source-level command-type distinction without requiring a simulator or hazardous machine operation.

### Conditional integration trap: raw RESET button wired to HALUI E-stop
The component registers a separate raw `whb.button.reset` output and `Hal::setReset` sets that raw pin **in addition** to the ordinary `whb.halui.machine.on/off` command. **If** an integrator follows the stale `hal.h` comment and connects the raw button to `halui.estop.activate` while retaining the shipped example's machine-on/off connections, one button press can present **both** a normal machine-state request and a software E-stop request. The HALUI poller processes the rising-edge machine-on/off checks before the E-stop checks (stable `halui.cc` 1652–1663), but downstream Task acceptance and actual machine behavior are **UNKNOWN** and cannot be inferred from this static ordering. This hypothetical conflicting command wiring is a **SOURCE-CONFIRMED conditional integration hazard**, not an observed installation or a bypass of an independent physical safety circuit. **Do not recommend this wiring as a fix.** Preserve separate, deliberately designed normal controls and an independent physical E-stop/rearm path.

## Practical safer-by-default architecture
**Normal control:** LinuxCNC + XHC USB pendant may provide jog, ordinary Task abort, machine-on/off requests, status and operator convenience. Keep these features convenient, but label the buttons accurately; do not mark a software STOP or RESET as a certified E-stop. A cheap handwheel can remain useful without being safety hardware.

**Monitoring/diagnostics:** USB connected/sleeping, process health and HAL command state are diagnostic aids only. If used to disable normal jogging on lost remote input, use explicit freshness and restart handling, but do **not** credit them toward a personnel-safety performance level without qualified architecture and evidence.

**Safety-related control:** A selected independent safety relay/PLC, properly rated and configured devices, and deliberate restart logic own the personnel-protective decision. The safety function must remain effective if the pendant, host PC, USB stack, HAL, or normal FPGA freezes. If a wireless **safety** pendant is genuinely required, choose a manufacturer-documented safety-rated radio system with its own stop, link-loss and rearm contract; do not retrofit the ordinary HID link into safety authority by naming a bit `estop`.

**Physical final elements:** Identify actual contactors, drive safety inputs, valves, brakes and mechanical restraints. STOP request ≠ stopped motor; motor off ≠ gravity load held; controller disabled ≠ hazardous energy isolated. Validate stopping/holding, stored-energy release, guard access and maintenance isolation for the **selected machine**.

**Human factors:** Put an accessible, hardwired independent E-stop and straightforward guard/reset workflow where the operator actually stands; don't require carrying a wireless pendant to reach a protective stop. Make ordinary stop convenient, but make the independent E-stop visually and physically unmistakable. If a shop frequently defeats a guard or uses the pendant's RESET as a workaround, treat that as a design/usability defect and fix the workflow, not merely the operator training.
