## Source trace: scale instead of kerf offset
`GcodeBuilder.stream` selects supported DXF entities from `doc.modelspace()`, groups them into components, computes endpoints, and if `params.kerf>0` calls `apply_kerf(raw_entities, entity_endpoints, params.kerf, cut_type)` **before** re-reading transformed endpoints and generating NC. `raw_entities` are the original DXF objects, not cloned geometry. `_distance_left_to_right` uses the horizontal **endpoint span** `d=max(x)-min(x)`, not bounding extents of curves or actual offset distances. For outer cuts it uses `factor=(d+2*kerf)/d`; inner uses `factor=(d-2*kerf)/d`, with `factor<=0` rejected and `d<=0` **silently returned without compensation**. `ezdxf.transform.scale_uniform` applies `Matrix44.scale(f,f,f)` about the **global origin**, in place.

**A uniform scale is not a constant-distance contour offset.** It scales both X and Y relative to global (0,0); for noncircular shapes it does not maintain a constant perpendicular clearance along every segment, and a translated contour moves. The same numerical `kerf` applied to a part at different sheet locations can change its absolute position and edge clearances. This is SOURCE-CONFIRMED semantics, not a runtime cut measurement.

## Frozen numeric discriminators (source-derived, not executed)
1. **Translated 10×10 rectangle:** vertices (100,100), (110,100), (110,110), (100,110), outer `kerf=1`. Horizontal span d=10, factor=1.2. The source maps the X/Y bounding box **[100,110]×[100,110] → [120,132]×[120,132]**, centroid (105,105)→(126,126). A true symmetric 1-unit planar offset would preserve center (105,105) and produce bounds [99,111]×[99,111]. Even if kerf means full width instead of offset radius, **global centroid movement** is still incorrect for a constant-distance offset. Distinguish parameter semantics from geometry.
2. **Single CIRCLE:** `geometry/endpoints.py` returns the same leftmost point `(cx-r,cy)` as start and end. For a circle-only component, d=0 and `apply_kerf` returns **without changing radius**, even when kerf>0. This is conditional on the inspected single-circle path; not all multi-entity components have d=0.
3. **Same drawing built twice:** because scaling mutates the original DXF entities, the rectangle above is now 12 wide and centered at (126,126) after build 1. Build 2 with the same `doc` computes d=12 and factor=(12+2)/12=7/6, yielding width **14**, centroid **(147,147)** and bbox **[140,154]×[140,154]**. These values are arithmetic predictions assuming the same component survives both passes. The original drawing is not an immutable source for reproducible NC unless copied. **Important correction:** the second center is 126×7/6=147, not 140; the second bbox is 120×7/6=140 to 132×7/6=154.
4. **Vertical line:** both endpoints have identical x, d=0, so the kerf path silently skips. A real toolpath offset must consider segment orientation and process strategy, not only X span.

## Existing upstream tests and gap
PathForge `tests/kerf/test_compensation.py` explicitly tests that an origin-anchored 10×10 square scales to width 11 for `kerf=0.5` and width 9 for inner cuts, and tests that a vertical line with d=0 returns without error. Those tests establish the **project's intended current scaling behavior**, not geometric kerf correctness for translated contours, single circles, or repeat conversions. Their expected output was inspected, **NOT RUN**. The new [three-case review-only pytest](../examples/4000_cam_kerf_170/test_pathforge_kerf_geometry_review_only.py) precommits invariants for translated center, circle compensation and input immutability. Against the pinned implementation, failures are predicted from source, not observed.

## LinuxCNC-first integration decision
For QtPlasmaC, the documented **native** `G41.1 D#<_hal[plasmac.kerf-width]>` / `G42.1` is an interpreter-level cutter compensation path; source explicitly divides D by 2, and `G40` cancels it. But QtPlasmaC documentation warns that cutter compensation disables G-code/velocity THC and overcut. **Therefore do not automatically “fix” PathForge by inserting G41.1 into a plasma post.** If THC/overcut is required, a separate geometry-preserving offline offset/nesting workflow may be necessary, with explicit lead-in, winding, inside/outside, holes, collision/spacing, tool diameter/kerf provenance and source-to-NC comparison. A global scale is not that workflow. For routers/mills, the same geometric issue applies, but G41.1 use still depends on machine setup and lead-in constraints.
