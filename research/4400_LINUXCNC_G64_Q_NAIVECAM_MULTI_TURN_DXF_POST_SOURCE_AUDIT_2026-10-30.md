## End-to-end execution path
1. **Interpreter/userspace:** `Interp::convert_control_mode` (`interp_convert.cc`, stable lines 1633–1670) translates `G64 P... Q...` into `CANON_CONTINUOUS` with P blend tolerance and a **separate** naive-CAM Q tolerance. In stable v2.9.10, omitted Q inherits an explicitly supplied P; when both omitted, Q=0. `G64 P0` is not a positive path tolerance. The interpreter rejects control-mode changes while cutter compensation is active.
2. **Canonical/userspace, not realtime TP:** `SET_MOTION_CONTROL_MODE` (`emccanon.cc`, ~1193) calls `flush_segments()` and enqueues `EMC_TRAJ_SET_TERM_COND` for the realtime trajectory planner. **Separately**, `SET_NAIVECAM_TOLERANCE` (~1220) only stores Q in `canon.naivecamTolerance`; Q is not itself a TP safety/accuracy limit.
3. **Linear feed queue:** `STRAIGHT_FEED` (~1084) transforms program units/offsets and calls `see_segment` (~1007). `linkable` (~967) requires continuous mode, nonzero Q, unchanged A/B/C/U/V/W, no zero displacement, and a bounded queue. It tests **every buffered intermediate XYZ point** against the chord from the last emitted canonical endpoint to the proposed endpoint using clamped projection and `D <= Q`. On failure `see_segment` flushes; otherwise points are accumulated.
4. **Emission/identity:** `flush_segments` (~888) emits **one** `EMC_TRAJ_LINEAR_MOVE` with the **last queued point's line number and StateTag**, updates canonical endpoint, and clears the queue. Intermediate G1 points/individual line identities are not emitted as separate canonical moves. This does not by itself prove how every GUI displays active lines.
5. **Flush boundaries:** `STRAIGHT_TRAVERSE` (G0), `SET_FEED_RATE` when rate changes, `SET_FEED_MODE`, `DWELL`, `SET_MOTION_OUTPUT_BIT` (M62), `SET_AUX_OUTPUT_BIT`, mode changes and `FINISH` flush the buffer. Thus **G0 rapids are not merged by this G1 Q detector** (though they still have separate TP corner blending as PATH-BLEND-01 documents). M62's flush prevents silently merging a feed segment across that canonical output boundary; it does not make the output safety-rated.
6. **Arc shortcut:** `Interp::convert_arc2` (~566–605) obtains signed `turn` from `arc_data_ijk/r` (whose assignment is `+/- p_number`), then calls `ARC_FEED(..., turn,...)`. In `emccanon.cc`, stable `ARC_FEED` (~1480–1527) checks G17 XY + continuous mode; `chord_deviation` (~1269–1292) computes sagitta using **start/end angles and only the sign of rotation**, ignoring `abs(rotation)`. If sagitta < Q, the arc is replaced by two `see_segment` linear-feed points (midpoint/end), including interpolation of Z and other axes, instead of a circular TP move. Subsequent Q line simplification may merge these points further.

## Material failure path: multi-turn helical bore
The upstream [LinuxCNC issue #222](https://github.com/LinuxCNC/linuxcnc/issues/222), opened 2017-01-09 and **still open at the 2026-10-30 inspection**, reports a 15-turn helical bore becoming a straight plunge with `G64 P0.005 Q0.001`, while `Q0` avoids that symptom. **COMMUNITY-REPORTED observed result**, not a run performed here. The source independently establishes the mechanism: the signed turn count survives `arc_data_ijk`/interpreter dispatch, but `chord_deviation` tests only the short projected endpoint sweep; for a near-closed multi-turn helix, its computed sagitta can be below Q even though the requested path includes many revolutions. **SOURCE-CONFIRMED conditional replacement path**, physical tool movement/selected machine **UNKNOWN**. The official G-code reference explicitly warns that a small-pitch helix may be converted to a line and links issue #222 (**DOC-CONFIRMED**).

The arc conversion decision is based on projected XY chord geometry, not on the full 3D helix, cutter engagement, stock, or process feature identity. Do not conclude that `P` alone bounds deviation from the **original DXF/CAM geometry** after Q simplification; P is the planner's tolerance on the geometry it receives, while Q may already have replaced source segments. Nor does any software tolerance bound physical following error or collision clearance.

## Exact development-version differences (not silently portable)
- The inspected development `linkable` chord test and `chord_deviation` function retain the relevant turn-magnitude behavior; `ARC_FEED` additionally excludes active `G68` tilted work planes via `!canon.g68Active`. Do not call this a stable regression or assert a physical result from static inspection.
- Development `rs274ngc_pre.cc` reads `[RS274NGC] G64_DEFAULT_TOLERANCE` and **`G64_DEFAULT_NAIVETOLERANCE`**; matching development INI documentation uses exactly those names. When no explicit P/Q is supplied, development `convert_control_mode` can use those INI defaults. These exact settings were **not found** in inspected stable v2.9.10 `rs274ngc_pre.cc`; do not copy a development INI assumption into a stable post. An explicitly supplied P with omitted Q still makes Q=P.
- Development `convert_control_mode` also has an optional `G64 R` planner-selection/aggressiveness path; v2.9.10 does not share that interface. No claim is made about its runtime quality or compatibility.

## Practical CAD/CAM/DXF implications
- **Mills:** multi-turn G2/G3 helices, small holes and dense contours require explicit post review. A CAM-generated helix is a feature with turn count/pitch, not merely two XY endpoints.
- **Plasma/routers:** imported DXF polylines, bulges and tessellated curves should be normalized with explicit units, contour topology, winding, entity identity and tolerance *before* nesting/postprocessing. Q simplification can remove intermediate contour points; do not use it to conceal open contours, self-intersections or wrong kerf/lead-in decisions. QtPlasmaC process codes and material/THC ownership require a separate post contract; this audit does not validate them.
- **Press brakes:** bend-line DXF entities remain geometric evidence, not automatic bend semantics. Backgauge G0 moves are not merged by naive-CAM G1 detection, but their corner blending remains subject to the separate PATH-BLEND-01 concern. Do not turn a CAM post into safety authority.
- **Diagnostics:** merged feeds carry the last segment's source tag/line; compare emitted canonical move list and original CAM feature IDs, not only the GUI's current-line indication.
