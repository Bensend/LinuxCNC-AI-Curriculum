## Bounded question
If an R-format arc's center becomes non-finite, does the LinuxCNC Task interface reliably reject it as an error, or can a motion command be **dropped with a success return** while the canonical interpreter position advances? The inspected stable and development sources reveal a **conditional drop-with-zero-status path**. Whether a particular malformed G-code actually reaches this path depends on floating-point behavior and earlier interpreter/canonical handling; **not demonstrated by execution**.

## Conditional source-to-motion trace
1. `G21 G17 G90 G91.1 F100; G0 X0 Y0; G2 X0.001 Y0 R0` is a **disconnected-only theoretical discriminator**. With h=0.0005 mm and fixed `RADIUS_TOLERANCE_MM=0.00127`, `arc_data_r` does not reject `h-abs(R)>tolerance`; it next divides by `abs(R)=0`. Depending on C++ floating-point behavior, a NaN center may result, or a trap/error may occur earlier. This is NOT a claim that LinuxCNC actually accepts or executes this program.
2. If `convert_arc2` returns success with non-finite center, `ARC_FEED` receives that center. Its geometry/velocity calculations can propagate NaN, and its enqueue condition `if (vel && a_max)` is **not a finite-value predicate**. Whether this particular input reaches `tag_and_send` is **UNKNOWN**. The function calls `canonUpdateEndPoint` after the branch, independent of Task's later success.
3. If Task receives a circular command with NaN center, the compiled `ISNAN_TRAP` guard in `emcTrajCircularMove` returns **0** without sending `EMCMOT_SET_CIRCLE`. The Task dispatch path propagates that zero and does not classify it as a command error. This specific conditional suppression/return value is **SOURCE-CONFIRMED** in both inspected revisions.
4. Therefore **a position/accounting divergence is plausible**: canonical position can advance even when Task suppresses a motion command. This is a conditional architectural risk, **not TEST-CONFIRMED machine motion or a proven crash**. Other state-machine checks, interpreter aborts and realtime safety responses remain unverified. The Task guard also tests only `isnan`, not `isfinite`, and omits velocity/acceleration fields.

## Implementation question and narrow review-only correction concept
Do **not** “fix” the issue by merely returning a different status in Task: prevention belongs at several boundaries. The R constructor should reject **zero/non-finite radius before division**; canonical queue creation should reject non-finite center/derived motion parameters before updating accepted position; Task should treat a non-finite circular command as a **reported error** rather than silently succeeding. Exact error propagation and rollback semantics require upstream compatibility review. No upstream patch or production change was applied.
