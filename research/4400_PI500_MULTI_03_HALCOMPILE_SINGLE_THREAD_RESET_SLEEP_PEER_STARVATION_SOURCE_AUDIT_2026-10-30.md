# 4400-PI500-MULTI-03 — One PI500 slave's reset or missing address delays every other slave in the same userspace driver

**2026-10-30 | LinuxCNC original source + halcompile generator cross-trace | NON-GRADUATED | NO RUNTIME OR MACHINE TEST**

## Question and nonduplication

The existing [PI500-VFD-01](4400_PI500_VFD_01_LINUXCNC_PIN_REMOTE_TRIP_CLAIM_VS_COMMENTED_OUT_SOURCE_PATH_AUDIT_2026-10-30.md) establishes the missing `enable=0` trip; [PI500-OEM-COMM-02](4400_PI500_OEM_COMM_TIMEOUT_02_SOURCE_OEM_CROSS_LAYER_WATCHDOG_AUDIT_2026-10-30.md) distinguishes a frozen HAL heartbeat from the drive's communication timeout; [VFD-EXIT-01](4400_VFD_EXIT_01_LINUXCNC_2910_SHUTDOWN_HAL_MODBUS_LAST_COMMAND_VS_INDEPENDENT_STOP_SOURCE_AUDIT_2026-10-29.md) treats process exit. **New exact-source question:** can a fault or incomplete configuration of **one** PI500 instance prevent normal polling/command service for other instances that share this driver process? The earlier reports do not trace the generated `FOR_ALL_INSTS` macro or the shared blocking `sleep(1)` paths. This is a **new causal cross-instance scheduling mechanism**, not a new scored safety qualification.

## Immutable source chain

1. **SOURCE-CONFIRMED** [LinuxCNC `pi500_vfd.comp` at `e1c6a557c0e1c61961f17ee35a1ba188e7db275f`](https://github.com/LinuxCNC/linuxcnc/blob/e1c6a557c0e1c61961f17ee35a1ba188e7db275f/src/hal/user_comps/pi500_vfd/pi500_vfd.comp), Git blob `92cc57bdf5214bbb3fb92103837539e42a76d452`. Declares `option userspace yes` and `option userinit yes`; one global `modbus_t *ctx`; `user_mainloop()` contains `while(1) { FOR_ALL_INSTS() { ... } }`. Each instance selects its `mbslaveaddr` on that shared Modbus context before sequential reads/writes.
2. **SOURCE-CONFIRMED** [`halcompile.g` at the same LinuxCNC commit](https://github.com/LinuxCNC/linuxcnc/blob/e1c6a557c0e1c61961f17ee35a1ba188e7db275f/src/hal/utils/halcompile.g), Git blob `a610bba80794cc33b5fc524fb80e094fa2900a76`, generated-main lines ~850–915: generated `main()` calls `userinit`, then **one** `user_mainloop()`. Generator lines ~976–983 define nonsingleton `FOR_ALL_INSTS()` as a C `for` traversal from `__comp_first_inst` through `_next`, not independent per-slave threads. The PI500 component does not declare singleton. The source also supports `count=` / `names=` userspace instance arguments; no actual installation using multiple instances is claimed.
3. **SOURCE-CONFIRMED** in `pi500_vfd.comp`: if any instance has `mbslaveaddr == 0`, its iteration executes `sleep(1); continue;` **inside** `FOR_ALL_INSTS`. This blocks the single userspace loop for at least the requested one-second sleep interval before later instances can be serviced. Every outer loop revisits the condition while the address remains zero.
4. **SOURCE-CONFIRMED** `pi500_reset(ctx)` writes holding register `0x2000=7`, then **unconditionally calls `sleep(1)`**, even if the write returned an error. The `status.alarm && enable` branch calls `pi500_reset` every pass in which the last polled alarm is true and enable remains high. After a successful reset write it can immediately enter normal frequency/RUN logic based on the **pre-reset** polled status; on failure it logs and skips the remaining instance work. Other instances in the same process cannot be serviced during this sleep.
5. **VERSION CROSS-CHECK:** LinuxCNC stable tag `v2.9.10` `pi500_vfd.comp` Git blob `b77f6e0241d3bf9db44edd97ddbb229af184dd18` also contains the same shared `FOR_ALL_INSTS` loop, both `sleep(1)` sites, and the automatic `pi500_reset` branch. The inspected development/default-branch blob is different but preserves this mechanism. This does **not** establish any installed binary or drive behavior.

## Failure-path and observable-contract analysis (static, not simulated)

| One instance's condition | Exact source action | Other instances' consequence | What remains UNKNOWN |
|---|---|---|---|
| Slave address left zero | `sleep(1)` before `continue` | All peers in same `user_mainloop` receive no polling or new commands during that sleep; repeated each pass while zero | Actual count/order, configured addresses, HAL consumers and physical drives |
| Alarm remains reported; `enable=1` | Attempt reset, then `sleep(1)` regardless of Modbus write success | All peers delayed by the reset sleep on each such attempt; status/command freshness not guaranteed | Whether drive clears alarm, responds after one second, or resumes motion |
| Multiple alarmed enabled slaves | Each may invoke its own blocking reset in sequence | Delays can accumulate in a shared traversal; **no fixed aggregate worst-case latency** is established | Number of slaves, serial timeouts, scheduler and OS timing |
| A slave's serial read stalls | Synchronous `modbus_read_registers` on the shared context | Peers wait until the call returns | Actual libmodbus timeout/configuration and latency |
| Reset succeeds while `run=1` | Source can proceed to normal RUN write using status sampled before reset | Peer service still delayed; reset and fresh normal start are not separate source events | Whether VFD accepts command, spindle response, and safe rearm |

**Important nuance:** a delay in *normal Modbus service* is not proof that any spindle continues, stops, restarts, or becomes physically unsafe. Nor does a stopped `watchdog_out` for a peer prove an independent watchdog or final element exists. HAL pins and userspace Modbus are **ordinary control and diagnostics**, not personnel-protective authority.

## Reviewable corrective architecture (INFERENCE / design proposal, not implemented)

- Specify per-instance normal-control states: `UNCONFIGURED`, `POLLING`, `FAULT_REPORTED`, `RESET_REQUESTED`, `RESET_WAIT`, `REVALIDATE`, `RUN_ELIGIBLE`; define separate **communication freshness** and **command acknowledgment**. These are conceptual states, not existing LinuxCNC pins.
- Replace the address-zero blocking sleep with **nonblocking per-instance eligibility** or bounded scheduling. If a drive genuinely requires one second of bus silence after reset, determine from the **exact OEM model/firmware** whether other slaves may communicate during that interval; do not assume a per-slave cooldown is protocol-safe. A global bus quiet requirement, if documented, must be modeled explicitly and its peer-service consequence exposed.
- Require an explicit normal fault-reset request/event rather than endlessly resetting because `enable` stays high; after reset, **re-poll fresh status** before considering a normal RUN request. Define fresh-start policy separately from safety rearm. Treat any continued RUN request after reconnect as a design-review question, not a known OEM behavior.
- Add a **bounded source-level acceptance fixture proposal**: with two simulated logical instances, verify that an unconfigured instance does not block the other's normal polling; a faulted instance does not cause unbounded peer starvation; failed reset does not trigger normal RUN; stale feedback is distinguishable from fresh; and all paths prohibit RUN when ordinary `enable=0`. This fixture is **NOT RUN**. Freeze the oracle and verify local runner isolation before any justified compute; no GitHub-hosted runners.
- Preserve independent E-stop/guard/safety controller and appropriate physical torque-removal/holding/isolation. An improved driver scheduler is not a validated safety function.

## Same-session source follow-through — mixed-age and logically inconsistent status pins

The same pinned `user_mainloop` exposes an additional **source-level diagnostic coherence** problem. After a successful `pi500_getStatus`, the driver immediately updates `is_running`, `is_ready` and `is_alarm`. But `is_at_speed`, `motor_current`, `heatsink_temp` and `watchdog_out` are updated only at the end of the later `else` branch. Thus, on `!status.alarm && !enable`, the driver may publish **fresh run/alarm flags alongside retained old speed/current/temperature values**, then freeze the heartbeat. On a failed Modbus read, **all** pins can retain prior values because the loop continues before any updates. A HAL consumer must not infer a coherent fresh snapshot from individual pin values.

There is also a precise **conditional source counterexample** to the `is_at_speed` pin description (`1 when running at assigned frequency`): the assignment is `commanded_frequency > 0 && calculated_frequency == status.frequency`, with **no `status.running` requirement**. Therefore a logically supplied status with `running=false` and matching nonzero frequency yields `is_at_speed=true`. Whether the selected OEM drive ever reports that combination is **UNKNOWN**; no claim of observed false speed indication is made. This extends, rather than repeats, the earlier PI500-VFD-01 general stale-feedback warning with exact mixed-age and boolean predicates. **SOURCE-CONFIRMED static code; TEST-CONFIRMED none.**

**Maintainer review implication:** consider explicit per-instance `status_valid`/sample age and separate `command_valid`, update a coherent snapshot only after complete polling, and specify whether `is_at_speed` requires drive-reported running. These are ordinary diagnostic proposals, not personnel-safety validation.
