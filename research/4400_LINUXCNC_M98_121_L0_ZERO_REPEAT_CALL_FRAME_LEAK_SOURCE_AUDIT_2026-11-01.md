# M98-121 — Fanuc-style M98 L0 skips the subprogram but retains an entered call frame

**Status:** 4000 LinuxCNC interpreter implementation / 3100 mill, 3200 lathe and CAM-post transfer; NON-GRADUATED. **Audit date:** 2026-11-01. **Evidence:** SOURCE-CONFIRMED conditional call-frame path in pinned stable/development; DOC-CONFIRMED M98 L0 meaning; INFERENCE repeat threshold; TEST-CONFIRMED none.

## New question and provenance

LinuxCNC documents `M98 Pn L0` as a zero-repeat call that does **not** execute the numbered subprogram. Does it also leave the interpreter call stack unchanged? This is a distinct control-flow problem from CYCLE-119/120 G81 plane state, earlier M70/M73 modal restoration, and G76 threading. Historical PROGRESS search found no M98/M99 source audit; direct upstream source and existing test inspected.

Pinned stable v2.9.10 commit `86cdca76fa2a36274c432caa21952b23c267989a`, development commit `06864e23559e70463fc7112d5ce77138bcbc288c`. Stable [`interp_o_word.cc`](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/rs274ngc/interp_o_word.cc#L183-L282) blob `0cff00ad7316411a55b58d1be4449d04cab79922`; development [same control path](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/rs274ngc/interp_o_word.cc#L182-L283). Stable [`interp_read.cc`](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/rs274ngc/interp_read.cc#L1554-L1597) blob `93333860904996732f9fa96f239263c991b2dfd6`. Official [Fanuc-style numbered-program documentation](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/docs/src/gcode/o-code.adoc#L137-L211) explicitly states L0 does not execute the subprogram and `#1..#30` modifications are global.

## Call-frame trace

1. `read_o` recognizes `M98 Pn L0` as `M_98`, validates the P word and extracts the numbered subprogram name; `DISABLE_FANUC_STYLE_SUB` can reject the feature. This is not an ordinary M-code executed through HAL.
2. [`convert_control_functions`](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/rs274ngc/interp_o_word.cc#L849-L860) handles both `O_call` and `M_98` by **unconditionally entering a new context** while `call_state == CS_NORMAL`, then calling `execute_call`. There is no L0 guard before `enter_context`.
3. [`enter_context`](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/rs274ngc/interp_o_word.cc#L662-L681) increments `settings->call_level` and allocates/clears a new frame. `INTERP_SUB_ROUTINE_LEVELS` is **10** in [`interp_internal.hh`](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/rs274ngc/interp_internal.hh#L40-L60). Stable checks the limit **after** increment; [development](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/rs274ngc/interp_o_word.cc#L676-L705) checks **before** increment and also pushes a call-stack provenance node.
4. [`execute_call`](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/rs274ngc/interp_o_word.cc#L249-L283) initializes/decrements the M98 L-loop counter and, if `L==0`, **only logs** `"M98 L0 instruction; skipping call"`. It skips `control_back_to` (so the subprogram body is not entered), then exits the switch and returns `INTERP_OK`. It does **not** call `leave_context` or decrement `call_level`.
5. [`leave_context`](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/rs274ngc/interp_o_word.cc#L685-L711) decrements `call_level` on a normal return; [`execute_return`](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/rs274ngc/interp_o_word.cc#L391-L475) handles that return path. But an L0 block does not branch into the numbered subprogram and therefore has no matching `M99` for its newly entered frame. Development's `leave_context` additionally pops the provenance node; L0 does not reach it.

**Source conclusion:** each zero-repeat M98 call takes the *skip body* path while retaining an entered call frame in the inspected functions. This is not the same as a zero-effect operation. The later interpreter's reset/unwind behavior is not a substitute for restoring the call depth immediately after L0.

**Invocation boundary:** This audit's ten-L0 prediction concerns **automatic file execution**. Stable [`Interp::_execute`](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/rs274ngc/rs274ngc_pre.cc#L287-L341) also has a special MDI loop conditioned on `MDImode && _setup.call_level`; an L0 command that retains a frame could take a different read/execute path in MDI. No MDI behavior or error was reproduced, and the proposed test deliberately uses a standalone file rather than MDI.

## Frozen discriminator, not an executed test

For a **fresh** interpreter at call level 0, nine consecutive `M98 P1 L0` lines source-predict levels 1 through 9; the tenth attempts level 10 against `INTERP_SUB_ROUTINE_LEVELS=10` and should encounter `NCE_TOO_MANY_SUBROUTINE_LEVELS`. The numbered `O1 ... M99` definition can follow `M30` as documented; none of the L0 calls should execute its body. This is a prediction, **not** a reproduced error or observed log.

Stable's post-increment bounds check leaves `call_level` incremented at the error branch; development's pre-increment check avoids that particular out-of-range state. No claim is made about an actual crash, memory corruption, machine motion or installed version. The [upstream M98 loop test](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/tests/interp/m98m99/05-M98-loops/test.ngc) already contains **one** L0 between L10 and L2; its [expected output](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/tests/interp/m98m99/05-M98-loops/expected) verifies the zero-repeat body is not executed and later L2 works, **not** that call depth returns to zero or repeated L0 cannot exhaust nesting. Expected files were read as *test definitions*, not actual run evidence.

**Rejected alternative:** Negative L is **not** an additional M98 loophole in the inspected stable parser: [`read_l`](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/rs274ngc/interp_read.cc#L1007-L1021) requires an integer and rejects `value < 0` with `NCE_NEGATIVE_L_WORD_USED`. The distinct L0 problem survives because zero is allowed and enters the call path. This source check avoids conflating negative-repeat validation with zero-repeat frame lifetime.

## CAM-post and implementation implications

- For Fanuc-compatible postprocessors, avoid emitting `M98 L0` as a generic way to skip an optional operation until the actual installed interpreter has been checked. At post time, **omit the call entirely** when a calculated repeat count is zero; this preserves the documented no-execution semantics without relying on a potentially unbalanced call path.
- Keep `M98` numbered subprograms distinct from `O... call`; LinuxCNC documents different definition order, parameter scoping and return behavior. Do not use M99 in a main program without understanding its documented endless-program meaning.
- A narrowly scoped implementation correction would check L0 **before** `enter_context`, or immediately `leave_context` for L0 while preserving loop counter, file pointer and provenance semantics. This is a design candidate, **not a tested patch**. Check interactions with M73 auto-restore, nested M98 and development call-stack provenance before proposing upstream code.

The [practical M98 preflight guide](../guides/4000-linuxcnc-m98-zero-repeat-call-stack-cam-preflight-2026-11-01.md) defines one bounded canonical comparison and the existing upstream baseline. **No new workflow, large test suite or hardware action was created.**
