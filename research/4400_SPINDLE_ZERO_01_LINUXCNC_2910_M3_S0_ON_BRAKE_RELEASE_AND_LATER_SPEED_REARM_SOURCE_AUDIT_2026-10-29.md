# 4400-SPINDLE-ZERO-01 — Zero requested RPM does not mean spindle enable/brake-safe state
**2026-10-29 | pinned LinuxCNC v2.9.10 source trace | 4000 safety course | NON-GRADUATED | no runtime/physical test**

## Safety question and novelty
A machine executes `S0 M3` or runs `M3 S1000` with its ordinary speed override at zero. Is the spindle independently disabled and mechanically braked? **No such conclusion follows.** The official M-code manual says that at zero programmed speed (or zero override) the spindle will not turn, and may start later when the programmed speed/override increases. The pinned source explains a stronger **normal-control distinction**: spindle ON state is separate from commanded RPM, and the motion layer publishes `spindle.N.on` from that state rather than from `speed-out`. A zero-speed ON command also follows a branch that **requests brake release**. Actual spindle rotation, torque, brake hardware and electrical isolation are machine-specific and **UNKNOWN**.

**Novelty check:** direct full-index/progress/research scan for `M3 S0`, `M4 S0`, zero speed/override and latent spindle start found no exact-source branch. Existing [MON-02 at-speed default](4400_LINUXCNC_PINNED_SPINDLE_AT_SPEED_DEFAULT_TRUE_RAMPED_COMMAND_VS_SAFETY_MONITOR_SOURCE_TRACE_2026-10-25.md), [G95 speed feedback](4400_G95_SPEED_01_LINUXCNC_2910_SPINDLE_SELECTION_RPS_FEEDBACK_AND_FALSE_FEED_SOURCE_AUDIT_2026-10-29.md), [M70/M72 modal restore](4400_MODAL_RESTORE_01_LINUXCNC_2910_M70_M72_M73_SPINDLE_RESTART_AND_COOLANT_RESTORE_SOURCE_AUDIT_2026-10-28.md) and [M48/M49 override scope](4400_OVERRIDE_SCOPE_01_LINUXCNC_2910_M48_M49_M51_DOLLAR_SELECTION_SOURCE_DOC_CONFLICT_2026-10-29.md) cover different mechanisms. The new delta is **zero RPM with ON and brake-release state already requested**, including potential later speed change without another M3.

The M3 branch does not reject zero S.

- **SOURCE-CONFIRMED:** [`taskintf.cc` lines 1904–1933](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/task/taskintf.cc#L1904-L1933) sends motion command `EMCMOT_SPINDLE_ON`; explicit `emcSpindleOn` sets `state=1`, while the speed-change function also uses `EMCMOT_SPINDLE_ON` and carries speed. The latter reuses command structure state; do not infer every arbitrary command sequence without a runtime check.
- **SOURCE-CONFIRMED:** [`command.c` lines 1576–1622](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/motion/command.c#L1576-L1622) copies the requested state and speed separately; for nonzero ON state it sets spindle brake state to **0 (release requested)** even if speed is zero. [`control.c` lines 1891–1937](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/motion/control.c#L1891-L1937) computes output speed after override/limits but assigns `spindle.N.on` from `spindle_status.state != 0`, **not from speed != 0**. Forward/reverse direction outputs are separately derived from the actual speed command sign. Thus an ordinary zero-RPM command can coexist with an ON output and brake-release request.

## Normal-control state distinctions
| Observable | What source establishes | What it does NOT prove |
|---|---|---|
| `spindle.N.speed-out = 0` | zero commanded output RPM after normal scaling | physical zero speed, safe torque-off, electrical isolation or brake engaged |
| `spindle.N.on = 1` | ordinary spindle state ON | physical motor rotating; independent permission or guard closed |
| `spindle.N.brake = 0` | normal motion layer requests brake release | selected mechanical brake has actually released; physical load is held |
| `spindle.N.forward/reverse = 0` at speed zero | ordinary sign of command is zero | no future start when S or override increases |
| `M5` | normal spindle OFF command path sets state 0, speed 0 and brake 1 | STO, independent stop, safe standstill or isolation |

The two source snapshots agree on ON versus speed separation. They do **not** establish a machine's drive mapping or safety performance. A HAL connection from spindle-on to a VFD RUN input, for example, is a possible architecture to review, not an asserted installed circuit.

## Qualitative adversarial timeline (hypothetical)
1. Operator sees RPM 0 after `S0 M3`, assumes drive is disabled, and opens a service area. The source instead permits normal spindle-on state and brake-release request.
2. A later `S` word or speed-override increase raises the commanded RPM without a fresh M3 in the normal sequence. The manual expressly warns of this latent-start behavior. Whether a particular drive physically accelerates depends on wiring, limits and permissives.
3. A PLC/HMI may display only `speed-out=0` while ignoring `on`, `brake`, actual tachometer freshness, independent safety stop, guard state and mechanical energy. That is a human-factors failure mode to prevent, not a measured failure.
4. A separate safety function must ensure hazardous spindle motion cannot restart with personnel exposed. Maintenance requires qualified hazardous-energy isolation and appropriate verification, not S0 or override zero.

## Design and verification response
- **Easiest safe workflow:** show distinct **PROGRAMMED RPM**, **RUN REQUEST**, **MEASURED RPM (fresh/stale)**, **BRAKE REQUEST/FEEDBACK**, **PROTECTIVE STOP** and **ENERGY ISOLATED** states. Label `S0 M3` as **RUN REQUEST ACTIVE / ZERO SETPOINT**, not "OFF."
- **Ordinary controls:** define and verify HAL mappings for `spindle.on`, direction, speed, brake, override, VFD RUN and feedback; ensure an explicit ordinary M5/stop transition for routine shutdown. This is not a substitute for protective stopping.
- **Independent safety:** selected risk assessment must allocate guarding, STO/contactors where suitable, safe speed/standstill and mechanical holding as appropriate to actual machine hazards. Do not derive PL/SIL from LinuxCNC state pins.
- **Physical commissioning:** qualified evaluator verifies the exact drive/brake/guard/final-element chain under a separate safe procedure; no test is authorized by this source-only document.

## Scope and next work
No simulation is justified to rediscover the documented source separation. ## Additional official integration and upstream issue corroboration (2026-10-29)
**DOC-CONFIRMED original pinned source:** [LinuxCNC spindle HAL examples, v2.9.10 lines 50–78](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/docs/src/examples/spindle.adoc#L50-L78) explicitly connect `spindle.0.on` to `pwmgen.0.enable` and, in a separate example, to a parallel-port spindle-enable output. Thus a normal `spindle.on` signal **is actually proposed for enabling ordinary hardware**; its zero-RPM HIGH state is not merely an abstract UI discrepancy. These example connections are **not safety-rated** and do not establish selected-machine wiring.
**COMMUNITY-REPORTED upstream maintainer issue [LinuxCNC #2748, opened 2023-11-15, closed 2023-12-09](https://github.com/LinuxCNC/linuxcnc/issues/2748):** a pncconf stepgen spindle had enable wired to spindle-on, causing abrupt stepgen speed behavior when turning off or setting speed zero. A maintainer reported a configuration change to 2.9. This is a **different stepgen-ramping integration issue**, not confirmation or resolution of the source-level M3 S0 state separation, nor a recommendation to use machine-on as a personnel safety input. It demonstrates why ordinary HAL wiring must be reviewed as part of the selected control design.
