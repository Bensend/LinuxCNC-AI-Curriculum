## Trace A — correct ordering does not establish drive readiness

Both primary HALs schedule `lcec.read-all → cia402.N.read-all → motion-command-handler → motion-controller → cia402.N.write-all → lcec.write-all` in `servo-thread` (2026 HAL lines 11–20, CNC3 HAL 17–28). The generated HAL connects `joint.N.motor-pos-cmd` to `cia402.N.pos-cmd`, scaled `cia402.N.pos-fb` to `joint.N.motor-pos-fb`, `amp-enable-out` to `cia402.N.enable`, and `drv-fault` to `amp-fault-in`. CNC3 also connects a fourth CiA402 instance in velocity mode to `spindle.0.speed-out/speed-in` (HAL ~148–171). This is a consistent source-level signal graph, **not** proof of PDO correctness, actual OP state, drive enabling or motion.

Generated XML: EK1100 index 0; generic drives indices 1–3, VID `0x0766`, PID `0x0402`; outputs 0x6040/0x607A/0x6060 and inputs 0x6041/0x6064/0x606C/0x6061, all named consistently with HAL. These are **template mappings**. ESI, slave firmware, PDO assignment, Sync Managers and byte widths must be checked for each actual drive; substituting IDs is not merely a cosmetic operation.

## Trace B — two different R2M clock choices, neither verified

Generated XML sets `appTimePeriod=1000000`, `refClockSyncCycles=1`, `sync0Cycle=*1`, `sync0Shift=0` (XML 2,5). CNC3 sets the same period but `refClockSyncCycles=5`, `sync0Shift=-250000` and per-slave `watchdog` (XML 3,23–24). At maintained driver revision 56515f4, **positive** reference cycles mean R2M (host application time pushed to DC reference), while `-1` means M2R (servo thread follows reference). Current driver documentation recommends M2R for many DC servo systems. The two configs request R2M, not M2R; this is a **versioned configuration contrast, not a proven jitter or synchronization fault**. The 2024 phase shift and watchdog values must not be transplanted into a different drive without manufacturer and timing evidence.

The generated README targets LinuxCNC 2.9.8; the HAL omits `initf lcec.activate`. The maintained driver documents `initf` for 2.10+ and inline activation on 2.9. Thus its absence is **not** a 2.9 syntax error. Version, startup path, `pll-err`, `dc-sync-converged`, WKC and actual phase require separate verification.

## Trace C — generated Home All is not defined by ordinary sequence settings

Generated INI has `HOMEMOD=cia402_homecomp` (line 35) and `HOME_ABSOLUTE_ENCODER=2` on joints 0/1/2 (70,87,104), **without `HOME_SEQUENCE` anywhere**. Generated HAL connects `joint.N.request-custom-homing` → `cia402.N.home`, `cia402.N.stat-homing` → `joint.N.is-custom-homing`, and `stat-homed` → `custom-homing-finished`. Its README explicitly requires a separately installed custom homemod. The generated three files are **not self-contained**.

Under stock LinuxCNC Home All semantics, missing `HOME_SEQUENCE` excludes that joint, and an accepted `home(-1)` can clear already-homed joint 0 without rehoming it. See prior [HOMING-27](4400_LINUXCNC_HOMING_27_HOME_ALL_JOINT0_NO_REHOME_AND_UNSEQUENCED_JOINT_SOURCE_AUDIT_2026-10-31.md). **Conditional cross-config inference:** unless the installed custom homemod overrides this behavior, the generated INI does not define a Home All sequence for X/Y/Z. The actual installed `cia402_homecomp` binary is UNKNOWN. CNC3 explicitly supplies `HOME_SEQUENCE=0` on joints 0–2 (INI ~99/118/137), but also sets zero home search/latch speeds and `NO_FORCE_HOMING=1`; it is not evidence of a verified physical reference.
