## Call flow and state ownership
- `convert_motion → convert_g7x` is **userspace interpreter**, not the realtime motion planner. `switch_settings` saves and restores G90/G91 and G90.1/G91.1 modes, temporarily using absolute values for profile construction and restoring the A/C/U/W reader functions on scope exit.
- **Before scanning or validating the Q profile**, `convert_g7x` invokes `convert_straight(G_0, block, settings)` for the cycle's X/Z starting coordinates (with cutter compensation temporarily disabled). This is source-confirmed *canonical preliminary rapid construction*, consistent with the documented preliminary motion. If the subsequent Q subroutine fails, the earlier command may already have entered the interpreter/canonical queue; whether it physically executes before Task abort depends on lookahead, flushing, and machine state and is **UNKNOWN**. Do not teach this as proof of motion on error.
- It then invokes `read("O<q> CALL")`, scans blocks until the call level returns, dispatches O control functions, explicitly writes numbered and named parameter assignments into `settings`, and collects only G0/G1/G2/G3 motion as profile segments. A Q subroutine is therefore **not a pure immutable geometry file**: its parameter assignments are processed even though feed/speed commands are not executed as ordinary cutting commands. Persistent/global parameter effects need a standalone interpreter test; O-local scope is a separate question.
- `motion_machine` later converts generated line/rapid/arc geometry using ordinary `convert_straight` and `convert_arc`. G72 calls G71's generator after coordinate rotation, rather than using a completely independent planner. G71.1 excludes pocket cuts and G71.2 resumes after the first pocket by a distinct branch in `g7x::pocket`.

## Version-sensitive numerical difference
Stable `g7x::pocket` starts at `x=imag(pocket_starts.back())` and repeatedly subtracts `delta` using `x-=delta`. The pinned development revision instead saves `top`, maintains an integer `steps`, and computes `x=top-(++steps)*delta`, with an explicit comment that this avoids accumulating rounding. This reduces one source of floating-point error for many rough passes; it **does not establish** that either revision's generated path is geometrically correct in all cases. Development also adds a last-segment recursion stop and tolerance-aware comparisons in the pocket traversal, relevant to the upstream [g71-endless-loop2 fixture](https://github.com/LinuxCNC/linuxcnc/blob/537cf2d765c96b6e75ae1db44e1dc0b9dba906a1/tests/interp/g71-endless-loop2/g71-endless-loop2.ngc), blob `3d0be1ff6cd185e26e95469f0c91c0f9128fd180`; the fixture's presence is not a test run by this curriculum.

## Source-derived acceptance questions (NOT RUN)
1. **P1 preliminary command:** G71 Q with a nonzero X/Z starting offset and a missing Q subroutine. Capture canonical preliminary move emission and Task handling separately; distinguish queued command from actual machine displacement.
2. **P2 profile assignments:** assign `#100=123` inside Q and read it after G71 in a software-only interpreter. Contrast `#1` (local) and a feed/S word. Freeze whether the named/numbered assignment persists; the direct `settings->parameters` write is source evidence, not an observed post-call value.
3. **P3 rough-pass drift:** choose many fine I increments and compare generated X pass levels against the exact sequence `top-n*delta` in both revisions. Record maximum absolute error, duplicates, and termination. Do not infer a physical tolerance from float differences alone.
4. **P4 G71.1/G71.2:** use the pinned upstream [g71-with-g70 fixture](https://github.com/LinuxCNC/linuxcnc/blob/537cf2d765c96b6e75ae1db44e1dc0b9dba906a1/tests/interp/g71-with-g70/g71-with-g70.ngc), blob `e89298f436b4bbc8248f05f52b1f9db4caab196b`, to compare no-pocket/pocket/finish geometry and tool offsets. Capture full canonical path and the interpreter result; do not use GUI preview alone as an oracle.
5. **P5 invalid profile:** inject an arc or nonmonotonic contour error and determine whether an earlier preliminary command was flushed, canceled, or executed. A motion-logger acknowledgment alone is not enough.

## Implementation guidance
Keep the lathe post's Q profile limited to explicit, geometrically checked G0/G1/G2/G3 plus justified A/C corner features. Use a bounded profile generator that rejects non-finite arc centers, impossible R geometry, invalid monotonicity, unexpected parameter writes, and unit/diameter-mode ambiguity **before** producing a machine program. Do not assume a Q profile is a standalone ordinary G-code execution trace. When verifying, separate (1) interpreter-generated canonical geometry, (2) Task queue handling, (3) realtime motion, and (4) physical spindle/tool response.
