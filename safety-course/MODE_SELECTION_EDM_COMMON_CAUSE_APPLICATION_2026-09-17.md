# Safety Course — Mode-Selection and EDM Common-Cause Application

Date: 2026-09-17

## Scope

Apply the commissioning/common-cause method to two concrete professional safety subsystems for which current manufacturer evidence exposes enough behavior to make a useful trace: (1) safely evaluated operating-mode selection, and (2) external-device monitoring (EDM) of downstream contactors. This is an implementation-pattern study, not a claim that the cited devices or numerical PL/SIL values apply to any OpenPressBrake machine.

Evidence labels: `DOC-CONFIRMED`, `INFERENCE`, `UNKNOWN`.

## Professional implementation A — mode selection

### Evidence

`DOC-CONFIRMED` — Pilz states that when a machine has multiple operating modes/control sequences requiring different safety levels, each selector position may exclusively enable one mode; operating the selector alone may not initiate machine operation; and the selected mode overrides other control functions except emergency stop/off. Pilz further explains that a standard controller cannot safely evaluate the selector where safe evaluation is required.

`DOC-CONFIRMED` — Pilz PIT m4SEU exposes monitored mode-of-safe-operation outputs (MSO1...MSO5) and ties mode selection to permission/transponder behavior.

`DOC-CONFIRMED` — Pilz PNOZ s30 provides an instructive selector-encoding example: its 1-from-4 selection mode accepts only one-hot patterns; short circuits, cross-shorts, open circuits, or input drift that produce another pattern cause an error and outputs switch off. This is evidence for a fault-detecting selector architecture, not a universal required encoding.

### Control trace

Authorized deliberate mode request -> safely evaluated selector/permission -> mutually exclusive valid mode state -> safety logic enables only the safety-function set permitted for that mode -> final safety outputs/final elements remain subject to their own monitoring -> changing mode does not itself start hazardous motion.

### Common-cause/adversarial analysis

| Question | Classification | Finding |
|---|---|---|
| Can ordinary CNC/HMI software alone select a less-protective safety mode? | CLOSED FROM EVIDENCE | Professional pattern requires safety evaluation where mode changes alter safety functions; ordinary controller cannot simply substitute for that safety evaluation. |
| Can two nominal selector bits be defeated by one short/common wiring fault? | CLOSED FROM EVIDENCE (pattern) | PNOZ s30 one-hot mode detects invalid patterns caused by shorts/cross-shorts/open circuits/drift and removes outputs. |
| Does selecting SETUP automatically command motion? | CLOSED FROM EVIDENCE | No: selector operation alone must not initiate machine operation. |
| Is authorization/manipulation resistance part of the architecture? | CLOSED FROM EVIDENCE (example) | PITmode/PIT m4SEU uses permission/transponder concepts; Pilz recommends restricting mode selection to appropriately qualified employees. |
| Exact safe mode set for a press brake? | UNKNOWN | Must come from machine risk assessment, C-standard/OEM architecture, protective-device functions and validated machine design. Do not invent it. |
| Exact reduced speed/force/pressure values? | UNKNOWN | Machine-specific requirement; no value is inferred here. |

### Failure lesson

Redundant inputs are weak if both are generated by the same ordinary software state or can be driven into another valid mode by one common wiring/configuration error. A stronger architecture makes invalid combinations fail safe, restricts mode authority, separates mode selection from START, and validates the actual safety functions active in every permitted mode.

## Professional implementation B — EDM/contactors

### Evidence

`DOC-CONFIRMED` — SICK UE440/UE470 EDM cyclically checks contactors after safety-output switch-off and before restart. A fused contact can hold the assigned OSSD off; the documentation assigns separate EDM inputs to corresponding outputs and says EDM and the safety controller should be wired in the same control cabinet.

`DOC-CONFIRMED` — SICK M4000 documentation shows EDM implemented using positively guided N/C auxiliary contacts of both downstream contactors. After the protective device responds, those contacts must indicate that the contactors reached the de-energized position; otherwise restart is prevented.

`DOC-CONFIRMED` — Current Flexi Soft Safety Designer documentation detects impossible/timed EDM feedback sequences and warns that misuse of the EDM Error reset can cause undesired switch-on with a defective contactor; it instructs that Error reset be activated only when Control is 0.

### Control trace

Protective-device/safety demand -> safety outputs OFF -> K1/K2 coils de-energize -> power contacts physically open -> positively guided auxiliary contacts change to de-energized feedback state -> EDM observes expected state within its configured/device timing -> only after demand clearing and required reset/restart sequence may outputs be re-enabled.

### Common-cause/adversarial analysis

| Question | Classification | Finding |
|---|---|---|
| Does output-OFF alone prove contactors opened? | CLOSED FROM EVIDENCE | No. EDM exists specifically to monitor downstream device state. |
| Can a welded/fused contactor block restart? | CLOSED FROM EVIDENCE | Yes, in the documented EDM implementations. |
| Can feedback wiring be a common-cause path? | INFERENCE requiring design review | If multiple feedback channels share a vulnerable supply/return/connector or are combined so one wiring fault can manufacture the expected state, nominally redundant contactors can lose diagnostic independence. Review the actual schematic and fault exclusions. |
| Is an EDM auxiliary contact proof that hazardous energy is absent? | CLOSED FROM EVIDENCE / bounded | It proves the monitored contactor state relationship, not absence of all hazardous energy. Upstream supply, stored electrical energy, hydraulics, gravity and other energy paths require independent tracing. |
| Can a reset path undermine EDM? | CLOSED FROM EVIDENCE (Flexi Soft case) | Manufacturer warning shows an improperly used EDM Error reset can create undesired switch-on; reset conditions therefore belong in validation, not only logic review. |
| Exact contactor feedback topology for OpenPressBrake? | UNKNOWN | Requires final safety schematic, selected components and machine energy architecture. |

## Cross-cause scenario: mode + feedback

A particularly dangerous architecture would allow one ordinary PLC/HAL/FPGA configuration object to both (a) choose the safety mode and (b) synthesize or mask final-element feedback. One software/configuration defect could then select a less-protective mode and make the system believe its final elements are healthy.

`INFERENCE` — Keep normal-control mode requests and diagnostics informational/request-only at the safety boundary. Safety mode selection/evaluation and physical final-element feedback must retain independent safety authority appropriate to the actual machine design. Never make an FPGA `mode_ok` or `contactor_ok` bit the sole personnel-safety proof merely because it simplifies integration.

## Commissioning application

For each machine mode, validation must record:

1. exact selector input pattern and authorization state;
2. safety functions that must remain active;
3. protective devices intentionally changed/disabled and the independent measures replacing their risk reduction;
4. proof that mode selection alone cannot start motion;
5. invalid selector combinations and expected safe response;
6. each final element controlled in that mode;
7. physical feedback source for each monitored final element;
8. single open/short/cross-short/stuck-feedback tests justified by the architecture;
9. reset/restart behavior after EDM discrepancy;
10. proof that LinuxCNC/FPGA reboot or communication recovery cannot silently change safety mode or manufacture EDM health.

Any item not established from the actual machine design remains `UNKNOWN`; it is not filled with a generic value from these examples.

## Minimum-operate gate impact

The existing qualitative minimum-operate gate survives this application but needs two explicit questions before compression into a field card:

- **MODE INTEGRITY:** Can one ordinary-control, selector-wiring, permission or configuration fault silently place the machine in a less-protective mode or enable a safety function set different from the indicated mode?
- **FEEDBACK INTEGRITY:** Can one feedback wiring/configuration fault falsely prove that multiple final elements reached their safe state?

If either answer is unresolved for a personnel-exposed operating state, that state is `NOT CLEARED`. Bounded isolated/remote testing may still be used only under the course's existing hazard-control rules.

## Open items

- Apply these questions to a complete modern press-brake electrical/hydraulic/safeguarding drawing set when a sufficiently inspectable public set is found.
- Determine whether the eventual OpenPressBrake safety architecture needs a dedicated safely evaluated mode selector, keyed permission system, or a simpler fixed-mode architecture. Do not decide before the machine safety-function specification exists.
