# 4400-SPINDLE-COMP-ZERO-03 — Optional HAL spindle component's simulated zero-speed and unwritten brake output
**2026-10-30 | pinned LinuxCNC v2.9.10 and development source | NON-GRADUATED | NO MACHINE RELEASE**

## Scope and novelty
This is the **optional `src/hal/components/spindle.comp` component**, **not** the normal `motion` component's spindle pins. The component's own description warns that its name and pins resemble those from motion and that readers usually want `motion(9)` instead. Earlier [SPINDLE-ZERO-01](4400_SPINDLE_ZERO_01_LINUXCNC_2910_M3_S0_ON_BRAKE_RELEASE_AND_LATER_SPEED_REARM_SOURCE_AUDIT_2026-10-29.md) and [SPINDLE-STATE-02](4400_SPINDLE_STATE_02_LINUXCNC_2910_SHARED_MOTION_COMMAND_STATE_CROSS_SPINDLE_ZERO_SPEED_REARM_SOURCE_AUDIT_2026-10-29.md) address **normal motion/Task command state**; they do **not** inspect this separate HAL component's `zero-speed` and `brake` outputs. This is a distinct source-path/semantic collision, not a new scored safety competency.

## Two important source-level distinctions

**1. `zero-speed` can be a simulation/tolerance predicate, not observed physical standstill.** If `simulate-encoder=1`, the component uses its internally modeled `spindle_rpm`, not a physical encoder. Even with `simulate-encoder=0`, the predicate compares the sampled `actual-speed` (converted RPS→RPM) against a **configurable, default 20-RPM band**, not against exactly zero. A stale/broken encoder, wrong gear scaling, tolerance selection or disconnected signal cannot be ruled out by this single pin. The value is calculated before the modeled speed update in the same function call; no physical reaction time follows.

**2. `brake` is declared but no assignment appears in this component's update or setup logic.** A full-file source scan of both pinned versions finds `pin out ... brake "TRUE when decelerating"` but **no** `brake = ...` in stable and **no** `brake_set(...)` in development, nor another brake write in the component. This supports the narrow **SOURCE-CONFIRMED absence-of-writer** finding. A runtime/default-value verdict is **not TEST-CONFIRMED**, and this finding does not apply automatically to the **different `spindle.N.brake` pin generated by the normal motion component**. Never use the optional component's documented brake label as proof of mechanical brake application, deceleration or standstill.

| Scenario | Source-supported observation | Safety decision |

| `simulate-encoder=0`, encoder reports 15 RPM, default tolerance 20 RPM | `zero-speed` condition is true | Nonzero measured speed can satisfy predicate; not a safe-access witness |
| Encoder stops reporting while rotor continues | Software can see a plausible zero sample | Sensor/CCF/freshness and physical protection remain UNKNOWN |
| HMI displays `brake` from optional `spindle.comp` | Output declared, no writer found in two pinned versions | Do not label “brake physically engaged” |
| HMI displays normal `motion` spindle brake | Different source path and command semantics | Still only ordinary request/status, not physical brake feedback |
| Worker opens guard because “zero-speed” is green | No independent safety-related stop/standstill/hold established | **Not authorized**; redesign access/guard and status boundary |

## Human factors and practical architecture
Use unambiguous names: **“simulated RPM”**, **“encoder RPM (freshness/validity)”**, **“within configurable zero-speed band”**, **“normal brake command”**, **“safety-rated standstill/guard unlock”**, and **“maintenance isolation verified”**. A green `zero-speed` or `brake` bit should never silently unlock a guard or justify hand access. Keep normal LinuxCNC/FPGA diagnostics separate from selected independent safety logic and physical energy-removal/holding mechanisms. A guard whose nuisance trips encourage bridging a status pin requires a usability/architecture fix, not bypass instructions.

For a mill/lathe, verify selected spindle inertia, brake, drive STO, guard locking, stop-time and access risk through qualified engineering. For OpenPressBrake, this optional spindle component is **not evidence of installation**; the Y1/Y2 gravity/hydraulic HOLD remains unchanged. No selected machine, PL/SIL, stopping distance, test or physical witness is inferred.

## Same-session adversarial source review — reverse indication during commanded stop
A separate direct source check found a **conditional reverse-output discrepancy** in this same optional component, present in both pinned revisions. In the `cmdspeed == 0` branch, the source assigns `forward = (curspeed > 0) && forward` and then `reverse = (curspeed < 0) && forward` (stable [L265–272](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/hal/components/spindle.comp#L265-L272); development [L255–262](https://github.com/LinuxCNC/linuxcnc/blob/24e84c4506b41634240f7087f0295e361a954886/src/hal/components/spindle.comp#L255-L262)). **SOURCE-CONFIRMED:** the reverse expression depends on the **forward** pin, not the reverse pin. In the paper state `curspeed < 0`, `cmdspeed=0`, `forward=false`, the computed `reverse` is false even while the internal modeled/measured RPM remains negative. The prior nonzero reverse-running branch sets `forward=false`, making this a credible transition during a reverse stop. This does **not** prove a physical spindle reverses, stops early, or fails to stop; downstream HAL mapping and drive behavior are UNKNOWN. Treat `reverse` as ordinary control/indication, never a safety-rated motion witness.

**Source-review action:** a maintainer should verify whether the intended stop behavior is to preserve the prior reverse output during deceleration and whether the expression is a typographical error. Do not propose a blind one-character patch without checking supported hardware and direction-output semantics. No simulation is needed to establish the Boolean source path; any runtime verification, if later justified, must use an isolated local self-hosted environment and cannot prove physical safety.

## Cross-layer comparison — source-only RPM predicate versus a safety-rated monitoring architecture
The existing [Pilz PNOZ s30 OEM investigation](4400_MON_01_PILZ_2025_SHEARPIN_PULSE_COUNT_FILTER_AND_TOLERANCE_TIMING_ADDENDUM_2026-10-30.md) documents manufacturer-defined encoder coupling, two-sensor plausibility, speed/filter/tolerance conditions, output switching and the separate need for physical stopping. This is **DOC-CONFIRMED for that specific monitor**, not evidence it is installed. The optional LinuxCNC `spindle.comp` `zero-speed` predicate has no equivalent demonstrated sensor-independence, diagnostic coverage, safety reaction or final-element validation. Even a correctly configured safety monitor does not by itself remove energy or guarantee a stopped spindle: the selected machine's independent safety architecture, guard release and physical witness remain separate. This contrast is a **transfer/integration lesson**, not a new machine-level PL/SIL claim.

## Independent contrast with **normal motion** spindle brake source (same-session source verification)
To avoid a false cross-component conclusion, inspected the **separate** LinuxCNC v2.9.10 motion source. [`src/emc/motion/command.c` L1618/L1649/L1778/L1798](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/emc/motion/command.c#L1610-L1800) explicitly updates `emcmotStatus->spindle_status[n].brake` for normal motion commands; [`src/emc/motion/control.c` L1935–1936](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/emc/motion/control.c#L1935-L1936) publishes that ordinary brake state to a HAL spindle-brake pin. **SOURCE-CONFIRMED:** normal motion has an explicit software brake-state writer, unlike optional `spindle.comp` in the inspected source. Neither writer establishes that a mechanical brake physically engages or that access is safe. **Do not apply the optional component's missing-writer finding to normal motion's brake output.** This distinction is especially important because the optional component itself warns about nearly identical pin names.
