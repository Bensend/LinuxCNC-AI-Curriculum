## Laser L1 — current promoted breadth contracts

### Native LinuxCNC

- `laserpower.comp`: vector/raster modes, velocity scaling, min/max normalization and vector interpolation by distance-to-go.
- `raster.comp`: position-driven pixel stream, bidirectional sweep, interpolation, OFF sentinel, explicit faults/reset.
- M62/M63/M67 queued to next motion; no following motion means no queued state change. M64/M65/M68 immediate.
- shipped laser sim demonstrates one integration pattern, not a universal source interface.

### Real implementations

1. Historical Buildlog CO2: M3/M5 master permission, analog power, PPI/raster streaming, chiller/assist and overscan.
2. JTrantow diode/Fusion: CAM post emits M67 power, `motion.analog-out-00` drives Mesa 20 kHz PWM directly.
3. Sector67 Raycus C500 fiber, pinned repository revision `938b501bfd092505170af8146c1b77a8564754d1`: full config is inspectable and reports successful basic steel cutting.

### Sector67 source/config-confirmed call flows

Power:

`QtPlasmaC material cut_amps -> custom_filter rewrites M03 spindle speed -> spindle.0.speed-out-abs -> Mesa PWM -> external PWM-to-0-10 V converter -> Raycus analog power input`

Height:

`head capacitance -> BCL-AMP variable-frequency output -> Schmitt trigger -> HostMot2 encoder counter mode -> encoder velocity -> limit/scaling -> QtPlasmaC arc-voltage surface -> adapted height control`

Compatibility glue:

- capacitive threshold -> synthetic ohmic-probe;
- always-true synthetic Arc OK;
- these are software-interface adaptations, not physical plasma semantics.

Source/readiness boundary:

- Raycus has separate analog power, 24 V modulation and 24 V enable surfaces plus a 24 V READY output;
- if controller enable is asserted while the source powers up, this machine reports a source fault;
- READY is not integrated into machine-on qualification in the preserved config; startup correctness is procedural;
- therefore `machine on != source ready != laser enable != modulation/emission != numeric power request`.

Gas:

- current config is simply AUTO program-running -> gas solenoid, zero on-delay and one-second off-delay;
- project documentation itself calls this naive and discusses future gas qualification;
- do not promote it to a production gas-pressure/readiness contract.

Laser L1 remains open. Highest-value next evidence is a mature fiber implementation with integrated source READY/FAULT, gas pressure/selection, focus/pierce and abort/recovery, plus any public deployment using upstream `laserpower.power` rather than bypassing it.

## Waterjet W1 — current evidence-backed model

Real LinuxCNC evidence supports:

- distinct nozzle/water and abrasive channels;
- program/manual override authority must be explicitly arbitrated;
- nominal Z and cut-time correction authority can be separate;
- industrial servo interface must be verified from actual drive mode/feedback.

Vendor documentation has now sharpened, but not filled, the missing physical process schema:

- dual pressure / low-pressure pierce can exist;
- vacuum-assisted pierce can intentionally establish abrasive before water;
- abrasive availability, transfer and metering are distinct physical layers;
- clog recovery can involve divert/purge sequences;
- intensifier and direct-drive pump idle behavior differ.

Thus **never freeze a universal water-before-abrasive sequence**.

W1 still lacks real LinuxCNC evidence for pump/intensifier READY/FAULT, pressure qualification, high-pressure valve ownership, recipe-specific water/abrasive timing, clog recovery, automatic standoff and pause/abort reconciliation.
