## Newly established contracts

### Tool-change abort and acknowledgement ownership

1. The conventional `iocontrol.0` tool prepare/change handshake is level-based: request AND acknowledgement complete the transaction.
2. `emcIoAbort()` drops `tool-prepare` / `tool-change` and explicitly returns IO status to DONE so Task does not remain permanently blocked waiting for an acknowledgement that can no longer complete normally.
3. The upstream `tests/toolchanger/abort-during-change` regression independently confirms abort during prepare/change does not falsely install the unfinished tool and later motion/toolchange can proceed.
4. The basic four-pin handshake carries no per-request generation ID; external changer logic must make acknowledgements request-scoped. A stale held-high acknowledgement is therefore an integration hazard.
5. `tool-changed` must represent the actual final physical completion predicate required by the machine, not merely target-pocket equality.

### Real public lathe turret implementation

1. LinuxCNC issue #2025 provides an inspectable five-position lathe ATT using `carousel.comp` plus a velocity-mode stepgen.
2. The concrete chain is `tool-prep-pocket -> carousel.pocket-number`, `tool-change -> carousel.enable`, physical index/pulse sensing, `carousel.motor-vel -> stepgen`, then `carousel.ready -> tool-changed`.
3. The pinned `carousel.comp` state machine explicitly requires request release after completion before rearming another transaction.
4. The inspected changer uses index/pulse feedback plus a reverse-latch phase, so `ready` is a valid completion witness for that configured mechanism.
5. No separate hydraulic clamp/down/shot-pin witness is shown in that implementation. Therefore `carousel.ready` cannot be generalized as universal proof that every lathe turret is mechanically locked and safe to cut.
6. Field failure history in the issue demonstrates that GUI/tool identity can diverge from physical changer movement; GUI state is not a physical-completion witness.

### Spindle synchronization, pause and index failure

1. TP keeps at-speed readiness and index/phase acquisition as separate wait states.
2. A required position-synchronized move asserts the spindle index-enable handshake and remains waiting while that handshake is uncleared. Missing index does not silently start the synchronized cut.
3. No generic TP-local timeout was found in the inspected index-wait path; machine-specific timeout/recovery must not be invented as generic behavior.
4. Motion/encoder and TP exchange phase-acquisition state through an explicit index-enable handshake.
5. Ordinary pause does not feed-scale a current `TC_SYNC_POSITION` segment to zero mid-thread. LinuxCNC deliberately preserves spindle/axis phase through the active synchronized segment and applies pause at an appropriate boundary.
6. Abort is a different ownership/recovery class from ordinary pause/feed hold.
7. Upstream TP regression inputs include simple G33, multi-segment/blended G33, rigid tapping and at-speed programs. The inspected harness proves these programs are part of the execution corpus, but it does not by itself prove dedicated missing-index or cycle-specific pause fault injection.

### Lathe tool identity and offset semantics

1. A conventional fixed-station lathe turret is a LinuxCNC **nonrandom** changer even if it is physically circular.
2. Native LinuxCNC distinguishes tool number, hardware pocket/station, internal tooldata index, selected/prepared target, current tool in pocket 0, and active tool offset.
3. `Txxx` selection/preparation is distinct from `M6` physical change completion.
4. `G43` active axis/tool offsets are a separate authority from loaded-tool identity.
5. Native D-word semantics belong to cutter/nose compensation lookup (`G41/G42` family); do not assume commercial-control-style `T0101 = station 1 + wear register 1` without an explicit remap/application contract.
6. `M61` can change LinuxCNC's software current-tool identity without moving the changer; therefore it is not physical turret-position evidence.

### Spindle orient / C-axis / live-tooling ownership

1. Native M19 is a discrete orientation transaction with explicit target angle, direction/index mode, Q timeout, `orient`, `is-oriented`, `orient-fault` and `locked` surfaces. It is not a continuously coordinated C coordinate.
2. Pinned `orient.comp` implements position-command generation, optional index reacquisition and debounced in-position completion for an orient PID when the drive does not own orientation internally.
3. Discrete indexed live-tool operations may use M19 without a full C axis; continuous coordinated milling requires actual C-axis trajectory ownership.
4. A dual-role spindle/C-axis must arbitrate velocity command, C position command, encoder feedback, index-enable, PID/drive mode, reference state, brake/inhibit and stale command ownership during every transition.
5. LinuxCNC issue #3556 documented a real shared-index-enable ownership bug that could make G33 rapid instead of synchronizing on spindle/C-axis machines. PR #4200 fixed the cause by making idle homing stop clamping the shared `HAL_IO` signal.
6. The same hardware independently confirmed PR #4200 fixed the fault. The pinned revision is 638 commits ahead of the merge commit, so the old workaround of disconnecting joint index-enable is historical rather than a current generic requirement.
7. A current 2026 community C-axis implementation uses M19 to align the spindle before reconnecting C feedback/PID. Its field history also shows why M5/spindle inhibit is needed during ownership transitions: a latent M3/S command can unexpectedly become live when spindle ownership returns.
8. The durable architecture is an explicit ownership state machine: `SPINDLE_SPEED`, `ORIENT`, `C_AXIS`, plus machine-specific fault/reconcile/maintenance states as needed.

Reason: the open abort behavior already has an upstream purpose-built regression; the carousel question is better answered by a real lathe configuration plus inspectable component source; pause/index behavior is explicit in pinned TP/Motion source and represented in upstream synchronized-motion programs; the C-axis ownership pass has unusually strong evidence from native docs/source plus a reproduced upstream bug, merged root-cause fix, same-hardware retest and current field implementation.

Candidate future labs only if later source/config work leaves a material gap:

- stale `tool-changed` held across a new request;
- spindle position freezes/jumps after initial index acquisition;
- compare ordinary pause, feed-inhibit and abort in one synchronized-motion trace;
- bumpless spindle-to-C command/feedback transfer;
- stale M3/S reactivation during a C/spindle ownership transition;
- drive-mode acknowledgement failure or abort midway through ownership transfer.

## Do not infer

- Do not treat a GUI/current-tool number as proof of physical turret position.
- Do not treat `carousel.ready` as universal proof of clamp/down/lock state.
- Do not make a stale level acknowledgement valid merely because a new request happens to be high.
- Do not equate spindle at-speed with phase/index synchronization.
- Do not stop a position-synchronized thread with ordinary pause semantics that destroy phase.
- Do not interpret M61 as a physical tool-change operation.
- Do not import proprietary/commercial T-code wear-register conventions into native LinuxCNC without an explicit implementation contract.
- Do not describe the pre-PR-4200 shared-index workaround as required behavior at the current pinned revision.
- Do not enable a C position loop and spindle velocity loop against the same actuator simultaneously.
- Do not re-enable spindle ownership with latent M3/S authority unless transition logic has explicitly neutralized/reconciled it.
