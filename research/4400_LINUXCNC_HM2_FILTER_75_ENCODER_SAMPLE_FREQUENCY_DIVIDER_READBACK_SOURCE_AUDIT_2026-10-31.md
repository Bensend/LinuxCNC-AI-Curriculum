## Exact execution path
1. `hm2_encoder_parse_md` creates one **HAL_IN u32** global `sample-frequency` (or `muxed-sample-frequency`) at lines 464–473 and initializes it to 25,000,000 (ordinary) or 8,000,000 (muxed) at lines 702–706. It does not impose a runtime input range there.
2. `hm2_encoder_write` compares the HAL input against `written_sample_frequency`; on change it enters `hm2_encoder_force_write`. The force path calls `hm2_encoder_set_filter_rate_and_skew` after writing control/timestamp registers. The latter is reached during initialization as well as subsequent reconfiguration. **No validation of zero or range occurs before its first division.**
3. `hm2_encoder_set_filter_rate_and_skew` uses unsigned 32-bit `q = clock_frequency / requested_frequency` (integer truncation). If `q == 1`, it writes `filter_rate = 0xFFF`; otherwise `filter_rate = q - 2` (unsigned). It then **overwrites the HAL input pin** with `clock_frequency / (filter_rate + 2)`, merges optional muxed skew bits, writes the register, and stores this overwritten pin as its software `written_sample_frequency` shadow.
4. The firmware regmap specifies a **12-bit QFilterRate**, normally `ClockLow / (QFilterRate+2)`, but says **a divisor with its MSb set means divide-by-one**. Thus the special `0xFFF` request means *full clock* at the FPGA, while the driver computes its readback using the ordinary divisor formula `4097`.
5. The `llio->write` return value is not examined in `hm2_encoder_set_filter_rate_and_skew`; the shadow is updated regardless. A changed HAL readback is not an independent acknowledgment of FPGA register acceptance.

## Bounded arithmetic examples (illustrative ClockLow = 33,000,000 Hz)
These are **arithmetic predictions, not test observations**. Exact board clock and firmware must be read from the actual module descriptor.

| Requested HAL u32 (Hz) | q = floor(clock/request) | Driver register | Driver's HAL readback | Regmap-implied filter clock | Meaning |
|---:|---:|---:|---:|---:|---|
| 1,000,000 | 33 | 31 | 1,000,000 Hz | 1,000,000 Hz | ordinary valid example |
| 16,500,000 | 2 | 0 | 16,500,000 Hz | 16,500,000 Hz | ordinary valid example |
| 25,000,000 | 1 | 0xFFF | **8,054 Hz** (floor(33,000,000/4097)) | **33,000,000 Hz** (MSb override) | **readback not actual sample rate** |
| 8,054 | 4097 | 0xFFF | 8,054 Hz | **33,000,000 Hz** (MSb override) | **low-frequency request can select full clock** |
| 0 | — | — | — | — | **first integer division by zero** |
| 33,000,001 | 0 | 0xFFFFFFFE (unsigned wrap) | — | — | `filter_rate + 2` wraps to zero; **second integer division by zero before register write** |

The `q==1` readback mismatch is particularly misleading because `HAL_IN` is mutated by the driver itself: the visible pin can say ~8 kHz while the firmware register requests full clock. For `q` whose `q-2` sets the 12-bit register's MSb, the firmware's divide-by-one rule creates additional nonmonotonic regions; **do not assume an arbitrary small positive input is representable**. Avoid asserting exact installed-hardware frequency from a historical regmap alone.

## Real machine integration: Smithy 1240 HostMot2 5I20 raw-register override
The upstream [`configs/by_machine/smithy/1240combined.hal`](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/configs/by_machine/smithy/1240combined.hal#L1-L18), blob `e636353f82d783073a42927943bb4249402ace1b`, loads `hm2_pci` with `num_encoders=1 ... enable_raw`, then configures `hm2_5i20.0.raw.write_address = 13312` (0x3400 QFilterRate), `raw.write_data = 8`, and `raw.write_strobe = 1`. Its comment describes 33 MHz/(8+2) = **3.3 MHz**. The spindle encoder is used for `spindle.0.revs`, `spindle.0.index-enable`, PID velocity feedback and at-speed comparison (lines 62–86). This is a **real published configuration**, not proof it is currently installed or successfully operated.

The ordering matters: [`hostmot2.c::hm2_write` lines 152–173](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/hal/drivers/mesa-hostmot2/hostmot2.c#L152-L173), blob `75619ae3f6925087a6693c5421bbf629f4459d94`, invokes **`hm2_encoder_write` before `hm2_raw_write`**. [`raw.c::hm2_raw_write` lines 127–139](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/hal/drivers/mesa-hostmot2/raw.c#L127-L139), blob `20e90988588c0363921a512095aa0f1f4e2d43a4`, issues the raw write only when the strobe is TRUE, then **clears the strobe**. Thus on a write iteration where both paths address the same QFilterRate register, the raw write wins last; on later iterations with no rearmed raw strobe, a changed encoder sample-frequency may overwrite the earlier raw value. The driver's HAL `sample-frequency` and shadow are **not** updated by a raw register write. No HAL-visible proof of the effective FPGA divider is supplied by that software pin alone.

**Machine-specific bandwidth estimate (NOT a measured limit):** the Smithy HAL sets `encoder.00.scale = 2880` counts/revolution (lines 79–81). With raw QFilterRate 8 and an **assumed actual 33 MHz clock**, the regmap's 3.3 MHz sampling and default `.filter=TRUE` (15 samples/transition) imply an approximate 110 kHz quadrature line-cycle rate or **440,000 counts/s**, equivalent to **~9,167 rpm at 2,880 counts/rev**. This follows the archived regmap's idealized count-rate example and assumes encoder wiring, input noise, clock, signal duty/phase and FPGA version are suitable. It is a **source-derived planning upper bound, not a spindle-speed rating or verified margin**. If the driver later overwrites the raw setting, recompute the bound from the effective register, not the stale HAL input.

**Development parity:** pinned development `537cf2d765c96b6e75ae1db44e1dc0b9dba906a1` retains this ordering in [`hostmot2.c` lines 169–177](https://github.com/LinuxCNC/linuxcnc/blob/537cf2d765c96b6e75ae1db44e1dc0b9dba906a1/src/hal/drivers/mesa-hostmot2/hostmot2.c#L169-L177) (blob `f83e48fad84639eb1c095335ce908b4d408a4d38`) and the one-shot strobe clear in [`raw.c` lines 113–125](https://github.com/LinuxCNC/linuxcnc/blob/537cf2d765c96b6e75ae1db44e1dc0b9dba906a1/src/hal/drivers/mesa-hostmot2/raw.c#L113-L125) (blob `7ff03639ee26fe9d9bdcb57d3421bd1969f69bcd`). The source change is HAL accessor style, not a different last-writer contract. The Smithy HAL itself is pinned from stable; do not assert it is used by any development machine.

**Integration discriminator:** capture `raw.write_strobe` before/after the first `hm2.write`, the HAL sample-frequency pin, the actual register writes in order and the installed bitstream/clock. Do **not** infer the effective encoder sample rate from either the HAL pin or the raw HAL comment in isolation. The actual startup order and physical encoder behavior have not been reproduced; this is a source-confirmed *conditional write-order mechanism*. This is an integration extension of earlier [SSERIAL-56](4400_LINUXCNC_SSERIAL_56_REAL_8I20_7I77_HAL_ORDER_FRESHNESS_SOURCE_AUDIT_2026-10-31.md), which already studied the Smithy BLDC/Smart Serial execution order but **not** its encoder QFilterRate raw override.

## Consequence / failure boundaries
- **SOURCE-CONFIRMED:** zero input and greater-than-clock input reach C integer division by zero in both inspected revisions. The specific realtime exception, LinuxCNC fault propagation, kernel/user RT behavior and machine response are **UNKNOWN** without isolated execution; no claim of observed crash.
- **SOURCE-CONFIRMED in archived firmware RTL and regmap:** special `0xFFF` arithmetic readback disagrees with the regmap's divide-by-one behavior; application to an installed Mesa image remains **UNKNOWN until firmware/image verified**.
- **SOURCE-CONFIRMED:** a register write result is ignored and software shadow updated; readback and `written_sample_frequency` are not hardware acknowledgments.
- **DOC-CONFIRMED:** reducing sample rate increases digital noise filtering but reduces permissible encoder transition rate, and muxed mode also changes multiplex timing. This can affect feedback integrity and following-error diagnostics, but no physical failure is established.
- Distinguish this global filter input from per-channel `.filter`, index/probe latch, timestamp divisor and DPLL sample timer. The latter are separate paths.

**Low-level acknowledgment scope:** [`hostmot2-lowlevel.h` callback contract](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/hal/drivers/mesa-hostmot2/hostmot2-lowlevel.h#L68-L79) states `llio->write` returns TRUE on success and FALSE on failure and sets `io_error`. The caller here ignores that immediate result. Even a TRUE return is a low-level transfer/queue result, **not an independently read-back FPGA register**; exact physical acknowledgment depends on the transport and subsequent readback. A hardened driver should distinguish requested, queued/accepted, and confirmed hardware state.

## Review-only hardening design (NOT a patch; not compiled)
Guard `requested == 0` **before division**; compute quotient in a type with explicit bounds; handle `q <= 1` by programming the documented divide-by-one code **and publishing the actual clock**, not `clock/4097`; constrain the ordinary `q-2` to values with the register's MSb clear; reject or explicitly clamp unrepresentable low frequencies rather than silently wrapping; keep the muxed skew field separate; check `llio->write` status before updating the software write shadow, but do **not** label that shadow hardware-confirmed without an independent register/transport oracle. Verify exact FPGA implementation/clock before choosing policy or submitting upstream.
