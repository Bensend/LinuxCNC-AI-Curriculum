# 4400-ADAPTIVE-REVERSE-01 — M52 can request reverse trajectory, not merely slow feed

**2026-10-29 | source-only 4000 safety transfer | NON-GRADUATED**

## Question, scope, and predecessor
Could a builder wire `motion.adaptive-feed` as a one-direction speed-trim input, then unintentionally command **reverse execution of the queued path** when the signal becomes negative? What happens during a sign change? The existing [FEED-JOG-01](4400_LINUXCNC_FEED_HOLD_INHIBIT_JOG_STOP_SAFETY_AUTHORITY_SOURCE_AUDIT_2026-10-27.md) addresses feed-hold/inhibit, M53, and jog paths. [OVERRIDE-SCOPE-01](4400_OVERRIDE_SCOPE_01_LINUXCNC_2910_M48_M49_M51_DOLLAR_SELECTION_SOURCE_DOC_CONFLICT_2026-10-29.md) addresses M48/M49/M51 spindle selection. Neither traces the **negative M52 adaptive-feed direction transition**. This is an exact source-path extension, not a new personnel-safety function or a scored competency.

## Conditional normal-control failure path (INFERENCE, not tested)
- An ordinary process controller intended to request a smaller **positive** feed factor writes a negative value due to sign convention, fault, or an unreviewed control change.
- If `M52` is active, LinuxCNC's source does **not** clamp negatives to zero. It interprets the sign as a request to reverse the trajectory; while the planner reports moving, the source requests zero adaptive scale until direction change is allowed.
- Once the planner's internal motion criterion permits it, a negative input can select reverse traversal of queued motion. This can re-enter a previously traversed workpiece/tool region. The precise physical path, acceleration, reversal, limit behavior and response to a fault are **UNKNOWN** without a selected configuration and qualified evidence.
- A normal HMI may show feed override at 0/disabled or feed-hold active; neither display by itself establishes independent protective stop, physical standstill, collision clearance or gravity-load holding.

This is not an assertion that a machine reverses immediately or violates its normal planner constraints. It is also not a recommendation to use M52 as a safety-reverse, safe stop, or safety-speed function. An isolated source review is sufficient for the key command-semantics distinction; live machine experimentation would add unacceptable exposure without a qualified test plan.

## Practical safer-by-default integration
Use an **explicitly documented positive-only** adaptive-feed source when reverse is not an intended process capability; validate the producer's units, sign, stale/fault handling and enable ownership in ordinary controls. For an intentional reversible plasma/EDM process, show **FORWARD / DECELERATING / REVERSE REQUESTED / REVERSE ACTIVE / UNKNOWN** rather than labeling a negative input merely as a slower feed. Do not hide the M52 mode or use normal `tp-reverse` telemetry as personnel-safety permission. Guards, access, independent safety stops and physical energy isolation remain separately engineered.

## Same-session source-depth: M52 P0 does not itself command forward direction

A second inspection found an important distinct state-transition question: **does disabling adaptive feed automatically reset a previously selected reverse trajectory direction?**

- [`command.c` lines 1279–1290](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/emc/motion/command.c#L1279-L1290) handles the adaptive-enable command by setting or clearing `AF_ENABLED` in `enables_new`. It does **not** call `tpSetRunDir(..., FORWARD)`. Exact source blob `0b79061d39be915bbea548b2c33bb794d31ab302`.
- [`control.c` lines 380–407](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/emc/motion/control.c#L380-L407) calls `tpSetRunDir` **only inside the enabled adaptive-feed branch**. When adaptive feed is disabled, this branch is skipped; there is no unconditional forward-direction reset here.
- [`tp.c` lines 456–472](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/emc/tp/tp.c#L456-L472) explicitly resets `reverse_run=0` in `tpClear`, and [lines 2774–2783](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/emc/tp/tp.c#L2774-L2783) do so in completed abort handling. **SOURCE-CONFIRMED:** these are actual reset paths, distinct from M52 P0's adaptive-enable flag change.

**Narrow conclusion:** The M52 P0 implementation is **not by itself an explicit forward-direction command**. Whether a particular M52 P0 block can execute with a reverse-active queue, whether program completion invokes a queue clear first, and any subsequent physical movement depend on Task/queue state not fully traced here; **UNKNOWN / NOT RUN**. Do not claim that M52 P0 necessarily leaves a machine reversing, nor that it always returns it to forward. The practical review should record both `AF_ENABLED` and `tp-reverse` as **different normal-control state variables**, and require a source/qualified-runtime check before relying on a transition sequence for process correctness. Neither is personnel-safety authority.

## Normal status witness: `motion.tp-reverse` reports planner direction, not physical axis motion

The [`motion.c` HAL export](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/emc/motion/motion.c#L472-L480) creates `motion.tp-reverse` as a bit **output**. [`control.c` lines 2160–2168](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/emc/motion/control.c#L2160-L2168) copies `coord_tp.reverse_run` to `emcmotStatus->reverse_run`, and [lines 1941–1945](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/emc/motion/control.c#L1941-L1945) publishes that status to the HAL output. **SOURCE-CONFIRMED:** this pin is a useful ordinary planner-direction diagnostic, not a feedback sensor measuring actual axis direction, safe standstill, or protective state. It can help discriminate **M52 requested sign** from **TP-selected direction**, but neither proves the machine has physically stopped or that its travel path is clear. A selected-machine trace would need time-correlated axis feedback and independent protective evidence; none was collected.

## Initial value is not a fault-safe sensor contract

[`motion.c` lines 607–612](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/emc/motion/motion.c#L607-L612) initializes the ordinary HAL `motion.adaptive-feed` input to **1.0**, not 0. **SOURCE-CONFIRMED initial pin value**. This does not establish what a disconnected, stale, NaN, faulty or externally overwritten input does during a particular runtime. In particular, `M52 P1` plus an unwired default should **not** be represented as a personnel-safety hold or a verified process interlock. A safer ordinary process controller must explicitly own input provenance, freshness and failure behavior, and the independently engineered protective function must not depend on that normal pin.
