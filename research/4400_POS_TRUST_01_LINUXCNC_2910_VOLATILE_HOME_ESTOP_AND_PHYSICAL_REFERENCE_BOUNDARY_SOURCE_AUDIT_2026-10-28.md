# 4400-POS-TRUST-01 — LinuxCNC v2.9.10 volatile home, E-stop state and physical position-trust boundary
**2026-10-28 | pinned source/doc reconciliation | SOURCE-CONFIRMED + DOC-CONFIRMED; NOT RUNTIME OR PHYSICAL TEST**

## Question and novelty
After an ordinary LinuxCNC Machine OFF or E-stop, does the UI's `homed` status prove that a gravity-loaded or mechanically displaced joint still has a trustworthy physical reference? Can `VOLATILE_HOME` be treated as an independent safety function? Prior 4400 lessons trace E-stop software state and reset, but a repository search before this lesson found no direct `VOLATILE_HOME`, `HOME_ABSOLUTE_ENCODER`, or `clearHomes` trace. This follows [LIM-01's shared hard-limit/override study](4400_LIM_01_LINUXCNC_2910_SHARED_HARD_LIMIT_OVERRIDE_DIRECTION_AND_STATUS_SCOPE_SOURCE_AUDIT_2026-10-28.md), without reopening graduated 3000 work.

## Pinned v2.9.10 evidence
1. **SOURCE-CONFIRMED — Task requests selective unhome.** [`src/emc/task/emctask.cc` blob `ef96ceb4de247a96a1ff64309850383864d05179`, lines 303–372](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/emc/task/emctask.cc#L303-L372) calls `emcJointUnhome(-2)` on `EMC_TASK_STATE_OFF` and `EMC_TASK_STATE_ESTOP` after abort/disable actions. [`src/emc/task/emctaskmain.cc` blob `7292a172023a5b42b023447c2458cb766c93fc9b`, lines 3411–3426](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/emc/task/emctaskmain.cc#L3411-L3426) also requests `-2` when an auxiliary E-stop is active while trajectory remains enabled. These are **ordinary software state requests**, not evidence that an independent safety circuit acted or that physical motion ceased.
2. **SOURCE-CONFIRMED — `-2` means flagged joints only.** [`src/emc/motion/homing.c` blob `13f74f43a1169606e87c7bd8d48f44a2cad6fa74`, lines 283–326](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/emc/motion/homing.c#L283-L326): `-1` unhomes all active joints; `-2` clears `H[jno].homed` only for active joints with `H[jno].volatile_home`. [Same blob, lines 615–628](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/emc/motion/homing.c#L615-L628) stores the per-joint flag from the configuration. A joint not flagged volatile is not automatically invalidated by this specific `-2` operation.
3. **SOURCE-CONFIRMED — all-or-none precheck and failure path.** Before changing any homed flags, `set_all_unhomed` checks active joints for ongoing homing or not-in-position, and checks extra joints for disabled motion; it **returns without clearing any** if a precondition fails. [`src/emc/motion/command.c` blob `0b79061d39be915bbea548b2c33bb794d31ab302`, lines 1393–1409](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/emc/motion/command.c#L1393-L1409) additionally restricts unhome dispatch to FREE or DISABLED motion states. This is a conditional source path, **not an observed E-stop bug**; asynchronous command ordering, flags and timing require evidence before predicting a specific machine's outcome. It disproves the blanket assertion “every E-stop always clears every joint's homed status.”
4. **SOURCE-CONFIRMED — absolute encoder homing is a software mapping.** [`homing.c`, lines 1118–1145](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/emc/motion/homing.c#L1118-L1145) sets internal position and motor offset for an absolute-encoder homing path; the `HOME_NO_FINAL_MOVE` option can mark homed without a final move. This code does **not** verify encoder installation, coupling, retained count, correct scaling, actual ram support, or independent safe-state proof.
5. **DOC-CONFIRMED — configuration intent and edition-scope discrepancy.** [`docs/src/config/ini-homing.adoc` blob `1793d78d3f450c2a66bd96f54923a1be61b0a937`, lines 319–326](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/docs/src/config/ini-homing.adoc#L319-L326) describes `VOLATILE_HOME` for joints that may lose position when drive power is off. [`docs/src/config/ini-config.adoc` blob `e3d691253f7ff94f235d9735a67f06730ece7a38`, lines 1120–1125](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/docs/src/config/ini-config.adoc#L1120-L1125) explicitly includes machine OFF **or E-stop**. The first page is narrower wording, not a reason to discard the source-confirmed E-stop call.
6. **DOC-CONFIRMED — `HOME_ABSOLUTE_ENCODER` is conditional.** [`ini-homing.adoc`, lines 231–244](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/docs/src/config/ini-homing.adoc#L231-L244) distinguishes modes 0/1/2 and notes `HOME_IS_SHARED` is ignored for absolute-encoder homing. The presence of an absolute encoder or a `homed` bit does not certify retained reference integrity after power loss.
7. **SOURCE-CONFIRMED — `clearHomes` is not a general safety monitor.** [`src/emc/motion/command.c`, lines 275–304](https://github.com/LinuxCNC/linuxcnc/blob/v2.9.10/src/emc/motion/command.c#L275-L304) contains a kinematics-specific homing-flag clearing path for inverse-only kinematics after joint-mode motion. It is not a universal displacement detector.

## Adversarial state cases (paper only)
| Situation | What pinned source actually supports | What remains UNKNOWN |
|---|---|---|
| Machine OFF with `VOLATILE_HOME=1` on one joint | Task issues `-2`; if accepted and preconditions pass, that joint's `homed` flag clears. | Actual post-disable motion, holding brake, limit/encoder integrity and independent safety. |
| Machine OFF with `VOLATILE_HOME=0` | `-2` does not select that joint for invalidation. | Whether position was physically retained; unchanged `homed` is not a physical witness. |
| E-stop while a joint is still not-in-position in the motion state | The all-or-none `set_all_unhomed` precheck has an early-return path. | Whether this path is reached in a particular asynchronous run; no live behavior or bug reproduced. |
| Absolute encoder `HOME_ABSOLUTE_ENCODER=2` | Homing can map internal reference and complete without a final move. | Actual absolute sensor validity, coupling, drift, support, or safe-to-move authorization. |
| `homed=1` after any reset | Only the software's current reference state is represented. | Collision envelope, gravity-load holding, guards, stop distance, stored energy, deliberate restart. |

## Safety architecture and human factors (INFERENCE)
- Keep **position/reference trust** distinct from **normal control enable**, **safety stop**, **physical gravity holding**, **guard/occupancy**, **energy isolation**, and **fresh deliberate start**. Never use a LinuxCNC `homed` bit alone to allow personnel into a ram/robot/spindle hazard.
- For machines that can drift with power removed, define a documented, easily executed **reference-requalification** path that avoids routine guard removal or ambiguous limit override. If a position must be reacquired near a crush zone, a qualified independent safety/setup architecture and positive restraint are prerequisites, not optional GUI conveniences.
- Show operator-facing states separately: `reference unknown`, `reference established`, `safety system healthy`, `physical load held`, `safe access permitted`, `ordinary cycle armed`. A machine with a green reference indicator may still be unsafe.
- Prefer hardware/sensor layouts whose direction and position can be checked without putting a person into a pinch zone. Any repetitive need to defeat a guard or ignore a limit is a design usability defect to fix.
- Do not infer from these source paths that `VOLATILE_HOME` is a safety-rated diagnostic, achieves any PL/SIL, or is a suitable proof of Y1/Y2 restraint.
