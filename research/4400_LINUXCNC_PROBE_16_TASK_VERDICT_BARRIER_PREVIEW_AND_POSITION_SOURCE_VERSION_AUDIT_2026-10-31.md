## Question and revisions

Compared LinuxCNC **stable v2.9.10** with development commit [`24e84c4506b41634240f7087f0295e361a954886`](https://github.com/LinuxCNC/linuxcnc/tree/24e84c4506b41634240f7087f0295e361a954886). The development fix provenance is explicit: [5832f878, 2026-10-13](https://github.com/LinuxCNC/linuxcnc/commit/5832f8781a9f9dff58973a6e5d3cc3a7ac6fb18c), [36bd00ec, 2026-10-18](https://github.com/LinuxCNC/linuxcnc/commit/36bd00ecf849cb448c37ce4de4228320972b249f), and [dfc6bc0e, 2026-10-18](https://github.com/LinuxCNC/linuxcnc/commit/dfc6bc0feb2d1f47057eb12140ed3a8362d17e43). ## End-to-end execution and status barrier

1. **SOURCE-CONFIRMED, both revisions:** `src/emc/rs274ngc/interp_convert.cc::convert_probe` calls `TURN_PROBE_ON`, `STRAIGHT_PROBE`, `TURN_PROBE_OFF`, then sets `probe_flag`. `src/emc/task/emccanon.cc::TURN_PROBE_ON` enqueues `EMC_TRAJ_CLEAR_PROBE_TRIPPED_FLAG`; `TURN_PROBE_OFF` is a no-op. The clear prevents treating a previous successful probe's `probeTripped=1` as this attempt's result, provided the queued command is processed. Development `interp_convert.cc` lines 4688–4720; `emccanon.cc` lines 3398–3406.
2. **SOURCE-CONFIRMED:** `src/emc/rs274ngc/interp_execute.cc` lines 318–320 returns `INTERP_EXECUTE_FINISH`. `src/emc/task/emctaskmain.cc::readahead_reading` lines 600–620 queues a plan synchronization command and holds further read-ahead; `emcTaskCheckPreconditions` around 1558/1626 requires motion+I/O completion for the probe and synchronization. The interpreter's `rs274ngc_pre.cc::read_inputs` lines 1487–1493 requires an empty queue, calls `set_probe_data`, then clears `probe_flag` before reading the next line. This is **not** a simple same-line interpreter assignment.
3. **SOURCE-CONFIRMED, both revisions:** `src/emc/motion/control.c::process_probe_inputs` development lines 752–789 and stable lines ~678–715 writes `probedPos=carte_pos_fb` both on a matching input **level** (success, `probeTripped=1`, trajectory abort) and on end-of-travel without a match (no-error variants `probeTripped=0`). The latter is posted only when the planner is in position and queue depth is zero. The result is a **servo-latched feedback position**, not a separate timestamped hardware encoder-latch event.
4. **Version-sensitive race:** v2.9.10 `src/emc/task/taskintf.cc::emcTrajUpdate` lines 1607–1614 marks trajectory DONE when `inpos && queue==0`, **without checking `probing`**. The 2026-10-13 development change [5832f878](https://github.com/LinuxCNC/linuxcnc/commit/5832f8781a9f9dff58973a6e5d3cc3a7ac6fb18c) adds `&& !emcmotStatus.probing`: the maintainer explicitly documents the no-contact verdict arriving one servo cycle after planner idle and a possible prematurely completed MDI command. This is **SOURCE-CONFIRMED timing-window structure and maintainer explanation**, not our reproduction of a wrong result.
5. **Separate command-echo race:** development [36bd00ec](https://github.com/LinuxCNC/linuxcnc/commit/36bd00ecf849cb448c37ce4de4228320972b249f) records `commandHeartbeat` when the motion command is echoed and forces motion EXEC until the controller heartbeat advances beyond it. Its commit message describes G38 SYNCH reading too soon or `Queue is not empty after probing`; [dfc6bc0e](https://github.com/LinuxCNC/linuxcnc/commit/dfc6bc0feb2d1f47057eb12140ed3a8362d17e43) separately preserves EXEC on failed status reads when the cached DONE predates a command. Development `taskintf.cc` lines 2090–2195. Stable `emctaskmain.cc` lines 507–513 clears the read-ahead wait using only empty interp list, no pending command and Task DONE; development adds motion queue=0 and I/O DONE for program read-ahead (lines 543–563). **Do not conflate** these three distinct gates.
6. **External evidence classification:** [upstream issue #3650](https://github.com/LinuxCNC/linuxcnc/issues/3650), opened **2025-11-28**, reports repeated `Queue is not empty after probing` on v2.9.7; **COMMUNITY-REPORTED**, not proof of a particular mechanism on every installation. [Issue #4669](https://github.com/LinuxCNC/linuxcnc/issues/4669), opened **2026-10-11**, reports timing-sensitive upstream tests; the 5832f878 commit explicitly cites it. Maintainer commit descriptions and source diffs corroborate the race class but do **not** establish that this curriculum ran a test.

## Result coordinates and preview: three different propositions

- **SOURCE-CONFIRMED:** development `src/emc/task/taskintf.cc::emcTrajUpdate` lines 1690–1732 maps `traj.position=carte_pos_cmd`, `traj.actualPosition=carte_pos_fb`, `traj.probedPosition=probedPos`, and `traj.probe_tripped=probeTripped`. `src/emc/task/emccanon.cc::GET_EXTERNAL_PROBE_POSITION` lines 3657–3706 transforms the latter into program coordinates; `GET_EXTERNAL_PROBE_TRIPPED_VALUE` reads Task's status. `src/emc/rs274ngc/interp_internal.cc::set_probe_data` lines 438–491 assigns `#5061–#5069` and `#5070` after the queue barrier. **A failed no-error probe still writes a position**, but it is the feedback position at the no-contact end verdict, **not** a contact measurement. Treat `#506x` as invalid for calibration unless `#5070` and a plausible physical transition are established. Actual following error, units/offset conversion and exact endpoint discrepancy are machine-dependent.
- **DOC-CONFIRMED, idealized wording:** pinned [G38 documentation](https://github.com/LinuxCNC/linuxcnc/blob/24e84c4506b41634240f7087f0295e361a954886/docs/src/gcode/g-code.adoc#L1390-L1452) says failed probe `#5061–#5069` are the *programmed point*. The implementation copies `carte_pos_fb` at the end-of-travel verdict; the documented programmed point is **not a guarantee of bitwise equality to actual feedback**. Preserve this documentation/source precision distinction rather than asserting an unmeasured discrepancy.
- **SOURCE+DOC-CONFIRMED preview difference:** `src/emc/rs274ngc/gcodemodule.cc` development line 746 and stable equivalent return **0** from `GET_EXTERNAL_PROBE_TRIPPED_VALUE()` in the non-Task interpreter. [G-code overview](https://github.com/LinuxCNC/linuxcnc/blob/24e84c4506b41634240f7087f0295e361a954886/docs/src/gcode/overview.adoc#L615-L619) explicitly warns `#5070` always fails in Axis preview. Consequently a conditional toolpath based on `#5070` can preview a different branch than the real Task interpreter. Do **not** force `#5070=1` in machine execution merely to make the preview look right.
