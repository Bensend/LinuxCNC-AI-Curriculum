## Development execution and failure path

1. **Interpreter request is optimistic until resynchronization.** `convert_kins_switch` validates nonnegative P and, when module type information is available, rejects an unprovided type *before* sending it. It then calls `SELECT_KINS_TYPE` and immediately writes `settings->kins_type`. The named parameter `#<_kins_type>` reads that interpreter field. **SOURCE-CONFIRMED:** at this stage the value means the interpreter's selected/requested type, not a physically verified type. Invalid P generally cannot exercise the realtime rejection branch through ordinary G12.1 when module metadata is available; a failed forward solve, a custom module or a race is a more relevant conditional failure hypothesis.
2. **Realtime acknowledgement precedes outcome.** `command.c` stores requested type and increments `emcmotConfig->switchkins_seq`. During `emcmotController`, `handle_kinematicsSwitch` copies the request sequence into `emcmotStatus->switchkins_seq` **before** calling `kinematicsSwitch` or `kinematicsForward`. If the module refuses the type, it reports an error, sets `EMCMOT_MOTION_ERROR_BIT`, and returns with old active type. If the new type's forward solve fails at the current joint commands, it calls `kinematicsSwitch(old)`, reports error, sets motion error, and returns without updating Cartesian command or planner pose. The switchkins module itself rejects invalid type *before* modifying its active type.
3. **Status contains two different facts.** In `emcMotionUpdate`, a changed `switchkins_seq` sets `traj.switchkins_changed=true`, while `traj.switchkins_type` is separately copied from realtime's **actual active type**. `emcTrajUpdate` maps the motion-error bit to `traj.status=RCS_STATUS::ERROR`; `emcMotionUpdate` promotes that to `motion.status=ERROR`. It also forwards the realtime error text to the operator. **SOURCE-CONFIRMED:** a single updated Task snapshot can therefore contain **acknowledged sequence + unchanged active type + motion ERROR**.
4. **Task wait does not validate the switch result.** `emcTaskExecute`'s `WAITING_FOR_KINS_SWITCH` branch checks only `traj.switchkins_changed`, clears it, calls `emcTaskPlanSynch()`, and sets `execState=DONE`. It neither compares requested/active types nor checks `motion.status` in that branch, unlike `WAITING_FOR_MOTION` and `WAITING_FOR_MOTION_AND_IO`. The `emcTaskPlanSynch()` return value is not checked there; the function itself calls `emcTaskAbort()` if `interp.synch()` returns `INTERP_ERROR`. **SOURCE-CONFIRMED:** the wait's local DONE transition is an acknowledgement of processing, not a success verdict.
5. **Task's outer loop separately catches the fault.** The main Task cycle runs `emcTaskPlan()`, then `emcTaskExecute()`, **then** `emcMotionUpdate()`. After the update, the subordinate-error block tests `motion.status==ERROR` and, absent the distinct soft-limit branch, aborts motion/IO/spindle, closes/resets the plan, clears pending and interpreter queues, sets interpreter IDLE, and queues a synchronization command. The final published `emcStatus->status` / `task.status` is ERROR when motion status is ERROR. **SOURCE-CONFIRMED:** the ordinary non-soft-limit failure path is not allowed to remain a successful completed program merely because the wait consumed the sequence.
6. **Timing nuance.** Because the executor runs **before** the current cycle's motion-status refresh, it may act on a sequence/fault pair captured on the preceding Task cycle; a subsequent same-cycle subordinate-error check can still abort. If the sequence and fault are not sampled together, the exact ordering of transient GUI-visible states depends on servo/Task timing, asynchronous command delivery, and error-flag lifetime. No physical or runtime timing was measured. Motion's `set_operating_mode` has paths that clear motion errors on enable/mode transitions; do not claim every error bit persists for a fixed number of cycles without a frozen experiment.

## Interpreter resynchronization: a two-stage identity

`GET_EXTERNAL_KINS_TYPE()` in `emccanon.cc` returns `emcStatus->motion.traj.switchkins_type`, explicitly commenting that motion may differ from the last G-code request. `rs274ngc_pre.cc` copies that value into `_setup.kins_type` on interpreter synchronization. Therefore `#<_kins_type>` can represent the requested value immediately after conversion but the actual motion-published type **after a successful resynchronization**. The [Puma M429 example](https://github.com/LinuxCNC/linuxcnc/blob/24e84c4506b41634240f7087f0295e361a954886/configs/sim/axis/vismach/puma/remap_subs/429remap.ngc) tests `#<_kins_type>` after G12.1, but that example is not an independent physical confirmation: the Task error/abort path must still be respected. **INFERENCE:** treating an immediate interpreter parameter as a safety or machine-success acknowledgement would conflate command intent with outcome.

## Stable v2.9.10 is materially different

In stable `control.c::handle_kinematicsSwitch` ~297–348, the input is the **HAL `motion.switchkins-type` pin**, not a G12.1/Task sequence command. The code assigns the global `switchkins_type` to the requested value **before** invoking `kinematicsSwitch`. On module rejection it sets the motion-error flag and returns; it does not restore the prior global variable in that branch. It also calls `kinematicsForward` without checking its return code and updates the trajectory planner pose afterward. The inspected stable interpreter, Task, Task interface and switchkins documentation have no G12.1/G13.1 or `WAITING_FOR_KINS_SWITCH` path. **SOURCE-CONFIRMED version delta:** development's prevalidation, rollback and request/actual status separation cannot be claimed for v2.9.10. This is a source-level correctness concern for nontrivial kinematics, **not** proof of an observed physical jump.

## Practical troubleshooting contract (no machine operation)

- Identify exact LinuxCNC revision and loaded kinematics module. Do **not** paste development G12.1 examples into v2.9.10 configurations.
- For development, distinguish `requested P`, `traj.switchkins_seq`, `traj.switchkins_changed`, `traj.switchkins_type`, `motion.status`, `task.status`, and operator error text. A sequence edge without matching active type is **not** successful selection.
- Distinguish `#<_kins_type>` as interpreter state from `motion.kins-type` / Task-reported actual type. Re-read after synchronization and honor an ERROR/abort.
- Do not infer axis clearance, collision safety, or actual joint motion from any software status. Machine-specific joint limits, offsets and tool clearance require independent design review; personnel safety remains outside ordinary LinuxCNC/FPGA.
- A bounded future test, only if still necessary, should use an isolated local simulation with a deterministic kinematics module whose forward solve intentionally fails at a known pose, recording per-cycle sequence, actual type, error bit, Task exec state and interpreter resync. Freeze the oracle and prohibit physical outputs **before** any run; only `[self-hosted, openpressbrake]`, never hosted Actions. No lab was justified/executed in this source-only session.

## Evidence ledger and unresolved questions

- **SOURCE-CONFIRMED:** development seq echo before attempt; rollback on forward failure; independent active-type and error status; wait's sequence-only DONE; outer-loop motion-error abort; interpreter's pre-/post-sync identity; stable HAL-only implementation with unchecked forward return.
- **DOC-CONFIRMED:** [development switchkins manual](https://github.com/LinuxCNC/linuxcnc/blob/24e84c4506b41634240f7087f0295e361a954886/docs/src/motion/switchkins.adoc) states G12.1/G13.1 synchronize interpreter/motion and deprecates direct HAL switching.
- **INFERENCE:** a GUI/PLC that treats sequence change as completion can misreport success; the precise externally observable transient window is unmeasured.
- **UNKNOWN:** actual behavior of a particular failing kinematics module, exact servo-to-Task race timing, whether a particular abort/clear interleaving masks the bit, and any physical displacement.
- **TEST-CONFIRMED:** none. No simulator, Actions, build, machine operation, evaluator, or runtime.
