## Timing architecture: three distinct clocks/paths

1. **Bus master cycle**: `lcec.read-all` and `lcec.write-all` run in the fastest HAL thread. The source counts `master->next_tick` from activation, not from jittery application time. A Sync Unit with divider N and phase p is sent when `(tick-p) mod N == 0`; bus `read_master` processes the queued domain on the next bus tick. During startup before first master OP, the driver exchanges every domain every tick; steady-state division begins only afterward.
2. **Threaded unit cycle**: `lcec.<m>.syncunit.<name>.read` and `.write` must run in that order in **one** slower HAL thread whose period equals the Sync Unit's period. The unit thread consumes an RX seqlock image, executes slave `proc_read`, then later `proc_write` and publishes a double-buffered TX image. The bus thread remains nonblocking and copies a stable published TX image when the unit is due.
3. **EtherCAT DC phase**: `refClockSyncCycles=-1` selects M2R (host servo time pulled toward the reference DC clock), positive values select R2M, 0 disables reference sync. `dcConf` configures per-slave SYNC0/1 independently from domain exchange; `syncUnitPhase` determines which bus tick carries the frame. LinuxCNC **2.10+** `initf lcec.activate <bus-thread>` gives a clean activation grid; on 2.9 the API is absent and the driver falls back to inline activation in the first `write-all`. These modes are not interchangeable and no hardware sync has been measured here.

## Source-grounded findings and failure discriminators

**E1 — `fresh` means a new process image, not a validated new sensor measurement.** In a threaded unit, `lcec_read_sync_unit` sets `fresh=1` only when `lcec_su_rx_fetch` succeeds and `rx_gen` differs from `rx_gen_seen`. If the same generation is fetched again, `fresh=0` and `stale-count` increases after OP; however, provided the image is not torn and `gen!=0`, the code **still invokes every slave's `proc_read` callback**. A downstream consumer that watches only its sensor pin cannot tell a repeated image from a newly sampled one. WKC state is separately tracked and **not included in the `fresh` predicate**. Thus `fresh=1` is not proof of WKC-complete or physical sensor validity.

**E2 — output publication can be missed without blocking the bus.** At a scheduled send, `lcec_su_tx_take` returns >0 only for a stable new generation. Otherwise the bus resends the previous process image and increments `late-count` outside startup. After `LCEC_SU_STALL_SENDS=10` consecutive misses, it stops queueing that unit's domain until a new image is published. This is a communication/watchdog-enabling strategy, **not a guaranteed de-energization**: the slave's Sync Manager watchdog mode, drive behavior and output circuit are independent and must be verified. The counter increments at **unit send opportunities**, not at every faster bus tick.

**E3 — bus health, time lock and application freshness are different.** `lcec.<m>.wkc-state` reflects domain working counter completeness; `dc-sync-converged` is based on the DC monitor datagram; `pll-err`/`phase-locked` describe thread timing; `fresh`/`stale-count` describe input image generation; `late-count` describes missed output publication. None alone proves all others. With `initf_activated` in the inspected `lcec_write_master` path, `dc-phased` is set TRUE without separately validating slave DC convergence: do **not** use `dc-phased` alone as a slave-sync oracle. Disabling `dc-sync-monitor` leaves its last diagnostic values, so a cached `dc-sync-converged` can be stale if monitoring is disabled.

**E4 — phase changes the output deadline.** For the upstream example bus period 125,000 ns (8 kHz), motion Sync Unit divider 4 (500,000 ns), phase 0, its frame is sent at ticks 0,4,8,... and received on ticks 1,5,9,... . With the documented default unit-thread offset of one-quarter bus period (31,250 ns) after receipt, the nominal time to publish before next send is `(4-1)*125,000 - 31,250 = 343,750 ns` (343.75 µs), excluding runtime and bus jitter. A 500 µs unit-thread period **does not** mean it has 500 µs to finish after receiving fresh data. This is source/doc arithmetic, not measured latency.

## Source-to-config checklist

The upstream example runs `ecat-thread` at 125 µs, `servo-thread` at 500 µs, and `io-thread` at 1 ms; the `motion` unit has `*4`, the `io` unit `*8` with phase 2, and `serial` `*32` remains serviced by the bus thread. The generic drive/serial XML blocks intentionally omit real PDO maps; validate ESI, Sync Manager/watchdog, and driver-specific pins before treating this as machine-ready. For any real configuration, confirm `read` precedes consumers and `write` follows producers, matching period, faster bus-thread priority, `initf` version support, and a consistent `sync0Cycle`/Sync Unit period.
