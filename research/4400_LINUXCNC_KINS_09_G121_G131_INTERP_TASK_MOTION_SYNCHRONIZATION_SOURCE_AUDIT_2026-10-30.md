## Source-confirmed end-to-end path
1. **Interpreter validates/chooses type:** `G12.1` requires P; `convert_kins_switch` rounds P, checks nonnegative and availability when type information exists. `G13.1` selects the module's **flagged machine-frame** kinematics type, **not necessarily numerical type 0**. With no attached kinematics in a standalone interpreter, it falls back to 0. It calls `SELECT_KINS_TYPE(type)` and updates interpreter `settings->kins_type`.
2. **Look-ahead barrier:** the modal-0 conversion sets `settings->kinsSwitch_flag` except in abort/startup contexts. `interp_execute` returns `INTERP_EXECUTE_FINISH`. The source explicitly notes that an empty queue at read-ahead time does not establish future queue emptiness, so the barrier is requested for each switch. Abort/startup exceptions are deliberate and should not be generalized to normal program flow.
3. **Canonical flush and Task ordering:** `emccanon::SELECT_KINS_TYPE` flushes buffered segments, then appends `EMC_TRAJ_SELECT_KINS`. Task marks the command's precondition `WAITING_FOR_MOTION_AND_IO`, issues it via `emcSelectKinsType`, then enters `WAITING_FOR_KINS_SWITCH` postcondition. This is more than changing a HAL pin.
4. **Realtime command:** `motion/command.c` stores requested type and increments `emcmotConfig->switchkins_seq`. In `control.c::handle_kinematicsSwitch`, a new command sequence takes priority over a HAL-pin edge for that servo-cycle decision. A deprecated HAL-pin edge can still request a later change; the source warns that this bypasses interpreter knowledge and therefore undermines consistent limits/look-ahead.
5. **Physical-coordinate continuity check:** before accepting the new type, motion saves commanded joint positions, calls `kinematicsSwitch(requested_type)`, then evaluates `kinematicsForward` for those joints. If switching is unsupported or forward kinematics fails, it reports an error, sets the motion error flag and retains/restores the old type. On success it updates Cartesian commanded position and trajectory-planner position to the newly solved pose. This **does not prove that every switch is physically safe** or collision-free; it is a software continuity/validity mechanism.
6. **Acknowledgement nuance:** motion copies `emcmotConfig->switchkins_seq` to `emcmotStatus->switchkins_seq` **before** attempting the kinematics switch. Task interface sets `traj.switchkins_changed` when that sequence differs; `WAITING_FOR_KINS_SWITCH` clears it, calls `emcTaskPlanSynch` and marks the wait done. Thus the **sequence change is an observed request-processing/synchronization marker, not by itself proof that the requested kinematics became active**. The motion error path and actual `switchkins_type` must also be inspected. Whether a particular failure causes subsequent Task commands to proceed is UNKNOWN without a complete runtime/error-handling trace; do not claim it does.
