## Question, novelty and source selection
When a G10 L0 tool-table reload fails because the tool file is unavailable, does LinuxCNC preserve the previous in-memory tool table and report failure to Task? How did this change between stable 2.9 and development? 5. **Development Task regression candidate.** `src/emc/task/taskclass.cc` blob `2de1c714641330d77fa5eea4dcfcdd1c82e7c2f7` ~539–545 directly calls `tooldata_load(file)` and **discards its int return**, unconditionally calls `reload_tool_number`, and returns 0. Other methods in this class explicitly set `emcioStatus.status=RCS_STATUS::ERROR` on tooldata-save failure; this load method does not. **SOURCE-CONFIRMED loss of the local reload error**; Task-level success and user-visible behavior require runtime discrimination.
6. **Both versions reset before open.** `src/emc/tooldata/tooldata_common.cc::tooldata_load` stable blob `7b5a3e4ffdd8e9591ed382551bcd57a12a1af904` ~273; development blob `9f194abb12837847cfd6ece884d58621b9462529` ~281: in ordinary file mode, `tooldata_reset()` precedes `fopen(filename, "r")`; a failed `fopen` returns -1 **after the reset**. The NML and mmap implementations `tooldata_nml.cc::tooldata_reset` and `tooldata_mmap.cc::tooldata_reset` iterate through all `CANON_POCKETS_MAX` entries, assigning the initialized empty entry. **SOURCE-CONFIRMED transient table clear on failed open**, not a measured tool-table display or physical behavior. Database mode takes a different early branch: `tooldata_db_getall()` failure sets `db_mode=DB_NOTUSED` and returns -1 without entering the file reset branch.
7. **Malformed file is a separate non-atomicity.** Once open succeeds, the loop calls `tooldata_read_entry`; negative results print an unrecognized-line message, `continue`, and the overall function returns 0. Thus a partially invalid file may produce a **partially populated table with success return**. The review patch below addresses failed-open rollback and ignored return only, **not** all-or-nothing parsing/DB protocol validation.

## Same-session DB protocol follow-through — TOOL-RELOAD-172B/C (SOURCE only, NOT RUN)

**172B — failure point determines table survival.** Direct stable `src/emc/tooldata/tooldata_db.cc` blob `25edbec18f461a06168ce5bd1c7c166fdad249e4` and development blob `e9445f3d061cb169e0d445c7bfdbc58271af7d0c`, `tooldata_db_getall()` ~194–235: `!db_live` or failed `send_request("g\\n")` returns **before** `tooldata_reset()`; but after the request is sent, it **resets the entire table at line ~202**, then loops reading/parsing tool entries. A midstream `read_reply<0` or invalid `tooldata_read_entry` returns -1 **after reset and possibly partial repopulation**. `tooldata_load` then demotes `db_mode` to `DB_NOTUSED`; stable IO reports error, development Task discards the return. Thus the earlier statement that DB takes a separate early branch does **not** mean DB errors universally preserve the table. Freeze separate **E1** request-send failure and **E2** post-reset response/parse failure tests; different table outcomes are predicted. No runtime confirmation.

**172C — substring FINI prematurely terminates a valid tool response.** Official [tool database interface v2.1](https://github.com/LinuxCNC/linuxcnc/blob/67437d8865e431a9a33f74cee912dbf891d3b4c5/docs/src/tooldatabase/tooldatabase.adoc#L35-L45) specifies a **final response of `FINI`** after tool-data lines. Both stable and development `tooldata_db_getall` use `if (strstr(reply,"FINI")) break;` **before** `tooldata_read_entry(reply)`; a tool reply containing `FINISHED` in a comment (e.g. `T1 P1 Z0 ; FINISHED_SETUP`) is treated as end-of-table. The function then calls `tooldata_save` (return ignored) and returns **0**; that line and subsequent tools are not parsed. Development `read_reply` ~148 copies the entire received string into `reply` and strips only a final newline. The upstream `configs/sim/axis/db_demo/db.py::user_get_tool` ~539–550 demonstrates the supported `tool parameters ; comment` format (its stock generated comment does not contain FINI). **SOURCE-CONFIRMED predicate and source-derived example; whether a particular backend delivers exactly one reply per `read()` is UNKNOWN and requires a test.** [Review-only exact-sentinel patch](../examples/4000_tool_reload_172/development_db_fini_exact_review_only.patch) replaces substring with an anchored `FINI` token followed by end-of-string/whitespace; it is NOT APPLIED/BUILT/TESTED, and does not fix response framing or transactional reload. The example demonstrates a protocol parsing risk, not a confirmed installed-machine fault.

**172C reproducible source-level discriminator:** use a disposable DB_PROGRAM that returns `T1 P1 Z0 ; FINISHED_SETUP`, `T2 P2 Z2 ; NORMAL`, then `FINI` in distinct flushed responses; compare baseline vs exact-sentinel candidate, record actual byte reads and tool table. A pure arithmetic/string check that `strstr("T1 P1 Z0 ; FINISHED_SETUP","FINI")` is non-null is not a LinuxCNC runtime test. Never run on a connected machine. This strengthens the DB case E in the guide and does not alter graduation or compute status.

### 172D — upstream sentinel format counterexample to naive exact-match patch

**Critical source correction before runtime:** [`lib/python/tooldb.py`](https://github.com/LinuxCNC/linuxcnc/blob/67437d8865e431a9a33f74cee912dbf891d3b4c5/lib/python/tooldb.py#L57-L69) blob (read 2026-11-02) `get_cmd` emits `do_reply("FINI (get_cmd)")`, not bare `FINI`. `do_reply` writes a newline and flushes stdout. The official protocol text calls this a final `FINI` response but the bundled implementation appends diagnostic text. A naive `strcmp(reply,"FINI")==0` replacement would therefore **reject LinuxCNC's own bundled DB backend**, so that first review-only proposal was withdrawn and replaced before completion. The retained review patch now checks `FINI` **at the beginning of the reply** with a token boundary (NUL/space/tab/CR), accepting both `FINI` and `FINI (get_cmd)` while not accepting `T1 P1 ; FINISHED_SETUP`. This is source-context-validated only; behavior with pipe coalescing, partial reads, or unusual whitespace remains **UNKNOWN**.

**172D framing caveat:** `tooldata_db.cc::read_reply` ~148–176 calls `read(PARENT_READ_FD, buffer, sizeof(buffer)-1)` **once** and strips only one trailing newline; it does not retain surplus bytes or explicitly assemble one newline-delimited record. The bundled `tooldb.py::do_reply` flushes each record, but pipe read boundaries are not protocol message boundaries. A single read that includes two lines is a plausible conditional failure of both original and anchored-token versions. Do not claim it occurred without an actual isolated pipe test. Freeze a separate framing test with one write containing two tool rows and FINI; a production-grade parser would need buffering and record delimiting, not merely a better FINI predicate.

**Existing upstream test gap:** `tests/tooldb/db-g10-offset/{README,test-ui.py,db_test.py}` at development 67437d8 is an executable source oracle for G10 L1/L10/L11 offset persistence across DB restart, including one tool loaded in spindle; it does **not** test G10 L0 failed reload, partial DB get, FINI in a comment, or read framing. It is inspected, **NOT RUN**. Reuse this harness for a regression extension rather than constructing an unrelated simulator.
