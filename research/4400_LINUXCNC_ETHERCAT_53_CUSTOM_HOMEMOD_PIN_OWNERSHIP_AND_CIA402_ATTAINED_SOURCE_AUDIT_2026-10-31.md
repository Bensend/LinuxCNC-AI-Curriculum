## H1 — the stock upstream homemod template is NOT a drop-in for generated HAL

Both official stable and development `homecomp.comp` custom examples declare `joint.N.request-custom-homing` as **HAL_IN** and `joint.N.is-custom-homing` as **HAL_OUT**; neither exports `joint.N.custom-homing-finished`. The 2026 generator's HAL connects `cia402.N.stat-homing` (HAL_OUT) to `joint.N.is-custom-homing`, which would be **two output writers** with either stock example; its `custom-homing-finished` connection names a pin that the stock example never creates. This is a **SOURCE-CONFIRMED pin-direction and pin-inventory incompatibility**, conditional on attempting to substitute a stock example for the required third-party `cia402_homecomp`. It is **not** evidence that the generator's explicitly required external homemod has these directions.

Official development's custom template simply marks a requested joint homed immediately as a teaching demonstration (~353–360). It is not a verified drive-internal homing module. Never use it as a shortcut to make a generated machine config start.

## H2 — one candidate external homemod has a circular start gate in the generated wiring

The candidate `rodw-au` module *does* declare `request-custom-homing` as HAL_IO, `is-custom-homing` as HAL_IN, and `custom-homing-finished` as HAL_IN (~95–103). Those directions fit the generated HAL better. But its `do_homing` dispatch selects the custom state machine only when `customH[joint].is_custom_homing` is already TRUE (~302–307). The generator drives that pin from `cia402.stat-homing`, which becomes TRUE only after the drive reports homing mode. Meanwhile, the generator's `cia402.home` request is tied to `request-custom-homing`, and this candidate module **never asserts that request to 1**: its only high assignment is commented out at ~217; it writes zero at completion (~246). The maintained CiA402 component also **only clears** its `home` IO pin, not sets it. In the inspected three-file generated HAL there is no additional producer of the high request.

**Conditional source-level inference:** with exactly this candidate homemod, the generated HAL, initial home request 0 and no external HAL intervention, the drive-internal homing start is not reachable through the candidate's custom state machine: the selection gate requires a state that itself requires the unissued start request. An alternative homemod or external HAL writer could break the circle. No executable proof or installed binary evidence is available; preserve this as a falsifiable integration question, not a claimed machine malfunction.

## H3 — candidate completion criterion differs from maintained CiA402's

The candidate's `CUSTOM_RUNNING` checks **`Status.b.TargetReached`** and transitions to `CUSTOM_FINISH` on bit 10 alone (~232–239). Its header explicitly maps `TargetReached` to statusword bit 10, while bit 12 is a separate unnamed field. In `CUSTOM_FINISH`, it marks the LinuxCNC joint `homed=1` (~239–246). By contrast, maintained `cia402.c` in homing mode computes `stat-homed = bit10 && bit12` and separately exposes homing error bit13. Thus a synthetic statusword with bit10=1, bit12=0, bit13=0 would satisfy the candidate's **custom joint completion** criterion but not `cia402.stat-homed`. A statusword with bit10=1 and homing-error bit13=1 deserves separate testing too. The generated HAL wires `custom-homing-finished` from `cia402.stat-homed`, but the candidate's `CUSTOM_RUNNING` does **not** use that input as its completion predicate. This is a **source-confirmed mismatch in predicates**, not a reproduced false-home event.
