# 3200 — G76 pass-generation source trace

Date: 2026-09-14
LinuxCNC source revision: `f666f1a51ae7c4d991cc61233e785dcc53fbe98d`
Scope: pinned source analysis of LinuxCNC's lathe G76 threading cycle

## Source entry

At this revision, `Interp::convert_straight()` in `src/emc/rs274ngc/interp_convert.cc` dispatches G76 to `Interp::convert_threading_cycle()` after confirming the selected spindle is marked turning and rejecting rotary-axis motion in the same G76 block.

The actual cycle is generated in userspace by the interpreter as a sequence of traverse/feed canonical moves. G76 is therefore not a monolithic realtime "threading controller" hidden inside Motion. The interpreter expands one G76 block into a series of synchronized cutting passes plus unsynchronized positioning/retract moves, while Motion/TP executes each synchronized segment using the spindle-sync mechanism.

Evidence: `SOURCE-CONFIRMED`.

## Input validation and geometry semantics

`convert_threading_cycle()` rejects:

- cutter radius compensation being active;
- `I == 0`;
- `J <= 0`;
- `K <= J`.

When lathe diameter mode is active, I/J/K are divided by two internally before cycle geometry is generated. The sign of I distinguishes external threading versus boring/internal threading.

This is an important semantic boundary: program-level diameter-mode values are normalized to internal radial geometry before pass planning. A fresh AI must not compare raw programmed diameter-mode values directly to internal X-depth variables without accounting for that conversion.

## Pass-generation algorithm

The interpreter derives:

- `safe_x` from the cycle starting X;
- first-cut/start depth from `abs(I) + abs(J)`;
- final depth from `abs(K) + abs(I)`;
- thread height from `abs(K)`;
- pitch from P;
- compound-entry angle from Q;
- spring-cut count from H;
- degression from R, clamped to at least 1;
- taper distance from E;
- entry/exit taper flags from L.

The cut-depth sequence is generated by:

`depth = full_dia_depth + cut_increment * pow(pass, 1.0 / degression)`

until final depth, followed by at least one full-depth pass plus H additional spring passes.

Therefore R changes the progression law of successive cut depths; it is not merely a UI hint.

Evidence: `SOURCE-CONFIRMED`.

## One-pass call flow

The helper `threading_pass(...)` makes each physical pass.

Bounded flow for an ordinary non-tapered pass:

1. `STRAIGHT_TRAVERSE` back to the pass start region;
2. `STRAIGHT_TRAVERSE` in to the selected X cutting depth;
3. `DISABLE_FEED_OVERRIDE()`;
4. `START_SPEED_FEED_SYNCH(active_spindle, pitch, 0)`;
5. synchronized `STRAIGHT_FEED` along the thread to target Z;
6. `STOP_SPEED_FEED_SYNCH()`;
7. unsynchronized `STRAIGHT_TRAVERSE` out to clearance;
8. `ENABLE_FEED_OVERRIDE()`.

For entry/exit tapers, the helper changes synchronized pitch to a calculated `taper_pitch` while traversing the diagonal taper geometry, then switches back to normal pitch for the main threaded segment as needed.

This source explains a documented practical warning: unless exit tapering is requested, the cycle's exit is not spindle synchronized; after the synchronized cutting segment ends, the retract is a traverse. A relief region or stable spindle speed can therefore matter physically at thread exit.

Evidence: `SOURCE-CONFIRMED`, consistent with official G76 documentation.

## Feed/speed override ownership

Before generating the full pass set, `convert_threading_cycle()` calls `lock_speed_override(settings)`. Individual cutting passes disable feed override around synchronized cutting and restore it afterward. The speed override is restored after the cycle completes.

This distinguishes two concepts:

- maintaining spindle synchronization geometry during the cycle;
- ordinary operator feed/speed override authority.

The cycle deliberately constrains override behavior to protect thread geometry rather than blindly honoring arbitrary live override changes.

## Preflight capability check

Before executing passes, the interpreter builds representative move vectors and calls `check_spindle_sync_feed(...)` for the plain-thread pitch and, when applicable, taper pitch.

This is a useful preflight guard but not a proof that the physical machine will cut correctly. The source comments around this checking path explicitly warn that downstream planner limiting / inability of an axis to deliver the required motion can still produce a wrong thread.

Therefore:

`preflight accepted != physical thread integrity proven`

A correct machine must still have sufficient axis acceleration/velocity, valid spindle feedback, proper scaling, and stable mechanics.

## Synchronization episode boundary

Every pass invokes `START_SPEED_FEED_SYNCH(...)` again rather than carrying one opaque synchronization episode across all passes. This matches the visible behavior that the tool can wait/synchronize independently at the beginning of each pass.

The architecture is therefore approximately:

`G76 block -> userspace pass planner -> [position to pass start -> arm spindle sync -> synchronized cut -> disarm sync -> retract] x N -> final endpoint`

The realtime trajectory planner owns synchronization execution; the interpreter owns pass sequencing and cut-depth geometry.

## Adversarial checks

1. Is G76 one realtime Motion primitive? **No — the interpreter expands it into multiple canonical moves/passes.**
2. Does diameter mode simply change display? **No — I/J/K are normalized by dividing by two for internal radial pass geometry.**
3. Is every part of a threading pass spindle synchronized? **No — positioning and ordinary retract moves are traverses; the cutting/taper portions explicitly arm sync.**
4. Does R merely label the pass strategy? **No — it enters the actual depth progression exponent.**
5. Does preflight synchronized-feed acceptance guarantee a good physical thread? **No.**
6. Can feed override remain arbitrarily active during synchronized cutting? **No — the pass helper disables it around the synchronized cut.**
7. Does this source trace prove encoder/index fault recovery? **No.**

Result: **7/7 PASS** for the bounded claims.
