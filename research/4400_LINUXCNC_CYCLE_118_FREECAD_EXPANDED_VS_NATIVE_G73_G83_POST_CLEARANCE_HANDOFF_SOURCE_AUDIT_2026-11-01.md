# CYCLE-118 — FreeCAD CAM expanded vs native LinuxCNC G73/G83 produces different peck-clearance geometry
**Scope:** 3100 mill / 3400 router CAD/CAM handoff; 4000 LinuxCNC interpreter integration. **Pinned:** FreeCAD `24ea8589aa8676049f7fe53ca9d1d1c398c38d26` (2026-10-31 main) and LinuxCNC development `06864e23559e70463fc7112d5ce77138bcbc288c` (2026-11-01); stable v2.9.10 remains the reference in [CYCLE-115](4400_LINUXCNC_CYCLE_115_G73_G83_PECK_CLEARANCE_VERSION_AND_R_OVERSHOOT_SOURCE_AUDIT_2026-11-01.md). **Status:** SOURCE-CONFIRMED static / INFERENCE geometric comparison / TEST-CONFIRMED none / NON-GRADUATED.

## Why this is a distinct source boundary
FreeCAD's CAM operation creates machine-neutral `Path.Command` drilling cycles. The postprocessor can either emit a **native G73/G83** for LinuxCNC to expand, or translate the cycle into explicit G0/G1 segments **before** LinuxCNC sees it. The same source CAM operation can therefore acquire different intermediate rapid targets depending on a postprocessor setting and the installed LinuxCNC interpreter.

This is not a second copy of CYCLE-115's LinuxCNC default: it traces the **producer and consumer ownership split** and identifies an existing independent FreeCAD implementation and tests.

## Pinned FreeCAD call chain
1. [`Processor._expand_translate_drill_cycles`](https://github.com/FreeCAD/FreeCAD/blob/24ea8589aa8676049f7fe53ca9d1d1c398c38d26/src/Mod/CAM/Path/Post/Processor.py#L1558) explicitly checks `self.values["TRANSLATE_DRILL_CYCLES"]`. If false it leaves canned cycles intact; if true it applies [`DrillCycleExpander`](https://github.com/FreeCAD/FreeCAD/blob/24ea8589aa8676049f7fe53ca9d1d1c398c38d26/src/Mod/CAM/Path/Post/DrillCycleExpander.py#L44) to G73/G83 (also G81/G82) and replaces the Path command list with G0/G1 sequences.
2. [`DrillCycleExpander._expand_g73_g83`](https://github.com/FreeCAD/FreeCAD/blob/24ea8589aa8676049f7fe53ca9d1d1c398c38d26/src/Mod/CAM/Path/Post/DrillCycleExpander.py#L308) sets `clearance_amount = peck_depth * 0.05`. For G73 it rapids from each nonfinal peck bottom to `next_depth + 0.05*Q`; for G83 it returns to R then, before the next feed, rapids to `current_depth + 0.05*Q`. The code has no dependency on LinuxCNC's [RS274NGC] clearance defaults.
3. [`linuxcnc_post.py::_convert_drill_cycle`](https://github.com/FreeCAD/FreeCAD/blob/24ea8589aa8676049f7fe53ca9d1d1c398c38d26/src/Mod/CAM/Path/Post/scripts/linuxcnc_post.py#L252) has a special G74/G84 rigid-tapping branch but otherwise calls the [base `_convert_drill_cycle`](https://github.com/FreeCAD/FreeCAD/blob/24ea8589aa8676049f7fe53ca9d1d1c398c38d26/src/Mod/CAM/Path/Post/Processor.py#L3855), which formats the cycle as G-code rather than applying the expander at that stage. This does **not** prove the machine's `TRANSLATE_DRILL_CYCLES` setting; it must be inspected in the selected post/job.
4. The legacy [`UtilsParse.drill_translate`](https://github.com/FreeCAD/FreeCAD/blob/24ea8589aa8676049f7fe53ca9d1d1c398c38d26/src/Mod/CAM/Path/Post/UtilsParse.py#L412) is now a compatibility wrapper around `DrillCycleExpander`. The former distinct legacy behavior was reconciled in [FreeCAD PR #29357](https://github.com/FreeCAD/FreeCAD/pull/29357), merged **2026-05-03**, closing [issue #28984](https://github.com/FreeCAD/FreeCAD/issues/28984). Do not repeat the issue's pre-fix example as a claim about the pinned current revision.
5. FreeCAD already has [`TestDrillCycleExpander` G73/G83 cases](https://github.com/FreeCAD/FreeCAD/blob/24ea8589aa8676049f7fe53ca9d1d1c398c38d26/src/Mod/CAM/CAMTests/TestDrillCycleExpander.py#L204), including G98/G99 and peck geometry. These are inspectable **test sources**, not test executions in this session.

## Source-derived geometry contrast (G17, metric R=2, Q=0.5, first feed Z=1.5)
| Path ownership | Effective clearance c | First intermediate rapid | Meaning |
| --- | ---: | ---: | --- |
| FreeCAD `TRANSLATE_DRILL_CYCLES=true` | Q*0.05 = **0.025 mm** | Z=**1.525** | explicit G0/G1 output, LinuxCNC never expands G73/G83 |
| FreeCAD native G73/G83 → stable LinuxCNC v2.9.10 | **0.254 mm** | Z=**1.754** | controller expands canned cycle |
| FreeCAD native G73/G83 → development LinuxCNC, no D/INI override | **1.0 mm** | Z=**2.5** | controller expands canned cycle, above R |
| FreeCAD native → development with explicit D0.25 | **0.25 mm** | Z=**1.75** | D requires validated post support; not established for the stock FreeCAD post |

All rows are **source-derived predictions**. For G83, the interpreter/expander also visits R between pecks. For G73, it does not. A FreeCAD internal preview or expanded-post result therefore cannot validate the native LinuxCNC execution path unless the selected post actually emitted those explicit G0/G1 segments.

## Community and source provenance
[LinuxCNC issue #1788](https://github.com/LinuxCNC/linuxcnc/issues/1788), opened **2022-07-03** and closed **2026-10-04**, requested a configurable G73 retract distance. Its closing comment points to [LinuxCNC PR #2528](https://github.com/LinuxCNC/linuxcnc/pull/2528), merged **2026-01-20**, which added the optional D/INI mechanism to development. PR discussion in August 2023 explicitly raised the 0.050-inch/1-mm default versus historical 0.010-inch/0.254-mm behavior and mentioned FreeCAD's percentage-of-Q approach. This is **COMMUNITY-REPORTED historical design context**; actual present behavior is established from pinned source above. The issue's closing comment uses an INI option spelling that does not match the inspected `rs274ngc_pre.cc` lookup; the **source's** `G73_PECK_CLEARANCE/G83_PECK_CLEARANCE` names govern this audit.
