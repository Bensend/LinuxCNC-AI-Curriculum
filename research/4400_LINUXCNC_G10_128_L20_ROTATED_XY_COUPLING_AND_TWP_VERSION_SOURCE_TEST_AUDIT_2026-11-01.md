## End-to-end source path
1. `convert_modal_0(G_10)` routes L2/L20 to `convert_setup` (rather than `convert_setup_tool` for L1/L10/L11). **SOURCE-CONFIRMED.**
2. P0 resolves to `settings->origin_index`. `find_current_in_system(settings,p_int,...)` reconstructs current coordinates *as viewed from the selected fixture*, accounting for active G5x, rotation and axis offsets. This is not simply the current GUI DRO minus a fixed number. **SOURCE-CONFIRMED.**
3. L2 writes specified fixture X/Y directly. L20 uses the old target-fixture coordinates `(cx,cy)` and the requested values (defaulting omitted X/Y to cx/cy); both vectors are rotated by the selected fixture R. It writes **both** `parameters[5201+p*20]` and `parameters[5202+p*20]` even if only X or Y was specified. **SOURCE-CONFIRMED.**
4. For an active fixture, `convert_setup` recalculates the interpreter current point, emits `SET_G5X_OFFSET` and `SET_XY_ROTATION`; for an inactive fixture, it updates stored parameters without switching active G5x. The stored offsets are **unrotated machine-frame fixture origins**; an X-only target-coordinate edit may change both stored X and Y. **SOURCE-CONFIRMED.**
5. A subsequent `G90 G0` uses the **new fixture frame**; the original upstream probe routine deliberately places its retract after L20. Correctness requires reasoning about the new datum, not reusing an old DRO coordinate as though it were unchanged. **SOURCE-CONFIRMED order, INFERENCE machine-specific clearance.**

## Reproducible numerical oracle (not newly executed)
With G54, G20, no G92/G52/TLO, machine point at X0 Y0, zero G54 offsets, R45°, the upstream test issues `G10 L20 P1 X-1`. Define R(+45°) as the standard CCW rotation and old fixture coordinate C=(0,0), desired C'=(-1,0). The new **stored unrotated** origin is:
`O_new = O_old + R(45°)(C-C') = (sqrt(1/2),sqrt(1/2)) in`.
The pinned upstream expected log records `SET_G5X_OFFSET(1,0.7071,0.7071,...)` and the subsequent debug value `X=-1,Y=0`. Thus **one X-only L20 edit changes both stored X and Y offsets**. This is expected coordinate-frame coupling, **not** evidence of a bug. Later `G10 L20 P1 Y-1` in the upstream test produces `SET_G5X_OFFSET(1,0,1.4142,...)`. These are **upstream expected outputs**, not TEST-CONFIRMED observations from this run.

## Versioned rejection and other preflight boundaries
- Both inspected versions reject R on L20, and reject modifying the **active** coordinate system while cutter radius compensation is enabled. An inactive fixture is a different case. **SOURCE-CONFIRMED.**
- Development `convert_setup` checks `settings->g68_active` before L2/L20 processing and rejects G10 L20 while G68.2 is active. Stable v2.9.10 does not implement native G68.2. This is a **version-specific implementation contract**; do not blindly transfer a CAM probing macro between versions. **SOURCE-CONFIRMED.**
- Development adds wrapped-axis validation for U/V/W as well as A/B/C, and uses axis-specific conversion functions; stable uses linear conversion for U/V/W. The physical meaning depends on axis configuration. **SOURCE-CONFIRMED static**, no cross-version runtime claim.
- G10 L20 changes persistent coordinate-system parameters and may affect subsequent moves, but is **not itself a probe success or independent position-trust witness**. The probe example checks `#5070`; the source does not prove sensor accuracy, signal freshness, backlash, or workholding. **SOURCE/DOC-CONFIRMED + UNKNOWN physical.**
