# 4000-LC-QTPLASMAC-01 — M190/M66 material handoff from CAM post to QtPlasmaC userspace

## Bounded question and predecessor
What does a QtPlasmaC-compatible post's `M190 Pn; M66 P3 L3 Q1; F#<_hal[plasmac.cut-feed-rate]>` sequence actually guarantee, and what happens if material selection fails? This is a **userspace command/status contract**, not a guarantee that a torch has fired or that a physical material is correct. Existing [3300 CAM/nesting discovery](3300-plasma-cam-nesting-discovery-2026-09-14.md) and [shared DXF discovery](shared-dxf-cad-cam-discovery-2026-09-14.md) list M190 but do not trace its script, Qt handler and M66 timeout semantics. The completed 3300 course is not reopened.

## Source-grounded path and failure modes
1. **Post/preview:** QtPlasmaC docs specify the ordered material command, `M66` wait, feed-rate read and torch start. `qtplasmac_gcode.py` checks that an `M190` material number is syntactically valid and exists in its loaded material dictionary, and marks errors. This is **preflight**, not a proof that the material remains available or is physically appropriate when execution reaches the command.
2. **M190 script:** `materialNum = int(float(sys.argv[1]))` happens before its `try`. Within `try`, if requested material differs from `qtplasmac.material_change_number`, the script writes `material_change=1`, then the number. If already selected, it writes `material_change=3`. It polls `material_change` until neither 1 nor 3, with a **0.5 s script-side timeout** that sets `material_change_timeout=1`, then writes `material_change=0`. It **does not check subprocess return codes**, has a blanket `except: pass` around its transaction, and ends with `exit()`. Therefore failures **inside the try** can be silently swallowed with a normal process exit; an invalid initial argument can still raise before that handler. **SOURCE-CONFIRMED** error-reporting weakness, not proof of a real failed material selection.
3. **Qt handler:** input pins `material_change`, `material_change_number`, `material_change_timeout` are declared; number-change callback rejects missing material and otherwise selects the combo entry, marking `autoChange` when state is 1. `material_changed` writes `motion.digital-in-03` low then high around material application and sets state 2 on the automatic path. State 3 callback writes ready high then state 0; state 0 callback writes ready low. Timeout callback emits `OPERATOR_ERROR` and writes ready low. **The script/Qt callback scheduling and the exact ready-high observation window are not established from static source alone.** Do not invent deterministic success/failure timing.
4. **M66 wait:** official M-code docs say `M66 P3 L3 Q1` waits up to one second for digital input 3 HIGH; timeout stores **`#5399=-1`** and ends the wait. The official QtPlasmaC example does **not** inspect `#5399` before its feed-rate read and M3. Thus **M66 timeout by itself is not an interpreter error or a fail-closed postcondition**. Whether another QtPlasmaC layer inhibits torch motion on that condition is **UNKNOWN** without an execution/state trace. The official M66 docs warn these inputs are not timing-critical realtime monitors.
5. **Process authority:** a CAM post supplies a material ID and requested sequence; QtPlasmaC's userspace script/UI/HAL select and report material state; LinuxCNC Task/interpreter execute M66 and subsequent commands; `plasmac.comp` and machine wiring govern actual process actuation. No part of this is automatically personnel-safety-rated.

## Concrete integration lesson
A future nesting/postprocessor must not equate **`M190` script exit 0**, **`M66` wait returned**, **Qt material combo changed**, or **material number printed in preview** with a verified successful material/torch state. Preserve post-generated material ID, configuration/material-file revision, requested feed/kerf and part/nest identity; check program/filter diagnostics, the material-selection acknowledgement, and actual process-state evidence at the appropriate boundary. In particular, do not assume an unguarded `M66 P3 L3 Q1` aborts the program on timeout; `#5399` is the documented discriminator. A program-level explicit failure branch may be appropriate but must be validated against the actual QtPlasmaC version and existing protective process logic, not copied blindly.
