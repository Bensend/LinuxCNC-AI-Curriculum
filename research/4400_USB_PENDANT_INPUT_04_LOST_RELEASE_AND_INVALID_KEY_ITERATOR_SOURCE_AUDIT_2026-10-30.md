## SOURCE-CONFIRMED causal path A — a missing packet is not a release event
1. On a **received** packet of the expected size, `Usb::onUsbDataReceived` calls `mDataHandler.onInputDataReceived`; that invokes `mPendant.processEvent` and `ButtonsState::update`. The update emits `onButtonReleasedEvent(previous)` **only when the new meta-button differs**. `onButtonPressedEvent(feed_plus)` sets `whb.halui.feed-override.increase` true; release sets it false. Other momentary raw button/ordinary command pins have similar press/release paths.
2. A `LIBUSB_TRANSFER_TIMED_OUT` branch resubmits a transfer; it does **not** invoke `onInputDataReceived`, `ButtonsState::update`, or a synthetic `onButtonReleasedEvent`. No new packet means the previous meta-button and corresponding HAL_OUT value can remain latched. This is a **source-state possibility**, not a measured duration or assertion that a real RF failure necessarily takes this path.
3. On a USB no-device/error exit, stable `process()` marks only `is-connected=false` before closing/reconnecting. Its `initWhb()` sets running flags; it does not reinitialize `mPendant` or neutralize the previous button outputs. Development changes USB failure/close handling but likewise marks connection false without calling the pendant release path. A retained button state can therefore survive an ordinary reconnect until a new **different** key/neutral packet is processed.
4. **Important counterexample:** a correctly received `UsbEmptyPackage` at power-off contains zero button/selector codes and is still forwarded to `onInputDataReceived`; that path can release the old button and mark `is-sleeping=true`. The next sleep package is deliberately dropped. Do **not** claim that every normal sleep event leaves a held button or that all disconnects fail to clear it.
5. HALUI's feed/spindle override `check_bit_changed` consumer is **edge-sensitive**. A stuck high `whb.halui.feed-override.increase` does not, by itself, prove repeated override increments, a continuous jog, a running spindle or hazardous motion. It can instead prevent another rising-edge request until a release/low transition is observed. Wheel counts need subsequent packets to change; the shipped `jog-enable` wiring is ordinary motion authorization, not a safety deadman. Exact installed HAL, Task state and physical response are UNKNOWN.

## SOURCE-CONFIRMED causal path B — invalid primary key iterator is not repaired
At stable `pendant.cc` **903–907** (development **914–918**), `auto key = Buttons.codeMap.find(keyCode)`; on `key == end()` the diagnostic branch mistakenly assigns **`modifier = Buttons.codeMap.find(0)`** instead of repairing `key`. The function later dereferences `*key->second` unconditionally at stable **924** / development **935**. `ButtonsCode` explicitly maps zero to its `undefined` key. Therefore an unrecognized primary key that reaches this function leaves an **end iterator dereference: C++ undefined behavior**. A crash is possible, but **not TEST-CONFIRMED or guaranteed**. The `xhc-whb04b6.cc` packet handler normalizes certain key/modifier combinations but does not reject every nonzero unrecognized primary code; the application checksum warning is not an acceptance gate (USB-PENDANT-01). RF corruption, receiver firmware acceptance, real-world frequency and actual machine effect remain UNKNOWN.

[One-line stable-tag review patch](../patches/4400_USB_PENDANT_INPUT_04_invalid-primary-key-v2.9.10.patch) and [one-line development review patch](../patches/4400_USB_PENDANT_INPUT_04_invalid-primary-key-devel-2026-10-30.patch) change the wrong iterator assignment to `key = Buttons.codeMap.find(0)` in their **exact source contexts**. Both are draft maintainer artifacts, not applied upstream. They fix only the immediate end-iterator defect; they do **not** validate packet authenticity, solve missed releases, establish RF freshness or qualify safety. Bounded upstream issue searches for invalid key/stuck release returned no direct match; this is **not exhaustive duplicate clearance**.
