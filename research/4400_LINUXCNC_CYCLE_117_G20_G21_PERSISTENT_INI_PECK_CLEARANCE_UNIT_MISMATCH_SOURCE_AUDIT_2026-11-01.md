# CYCLE-117 — Development G20/G21 does not rescale persistent INI peck clearance
**Scope:** 4000 LinuxCNC interpreter/unit conversion; 3100 mill/3400 router CAM transfer. **Pinned:** stable v2.9.10 `86cdca76fa2a36274c432caa21952b23c267989a` and development `06864e23559e70463fc7112d5ce77138bcbc288c`; 2026-11-01. **Status:** SOURCE-CONFIRMED state transition, numeric INFERENCE; TEST-CONFIRMED none; NON-GRADUATED. This is an additional **unit-state mechanism**, not a second restatement of [CYCLE-115](4400_LINUXCNC_CYCLE_115_G73_G83_PECK_CLEARANCE_VERSION_AND_R_OVERSHOOT_SOURCE_AUDIT_2026-11-01.md) or [CYCLE-116](4400_LINUXCNC_CYCLE_116_DEVELOPMENT_NEGATIVE_D_RAPID_STOCK_AND_DEFAULT_DOC_CONFLICT_SOURCE_AUDIT_2026-11-01.md).

## Why a unit switch matters
Development [`Interp::init`](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/rs274ngc/rs274ngc_pre.cc#L832) sets `_setup.parameter_g73_peck_clearance` and `_setup.parameter_g83_peck_clearance` to **1.0** on a metric machine or **0.050** on an inch machine. [INI reads](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/rs274ngc/rs274ngc_pre.cc#L945) optionally override those numeric fields; [INI documentation](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/docs/src/config/ini-config.adoc#L642) calls them machine-unit distances.

The development [`convert_length_units`](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/rs274ngc/interp_convert.cc#L3478) executes `USE_LENGTH_UNITS`, changes `settings->length_units`, scales current/program positions, origins, G68 offsets, active tool offsets and feed-related state. **It does not scale either `parameter_g73_peck_clearance` or `parameter_g83_peck_clearance`.** Its own source comment warns that cycle parameters need testing. Development [`convert_cycle_g73`](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/rs274ngc/interp_cycles.cc#L202) and [`convert_cycle_g83`](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/rs274ngc/interp_cycles.cc#L140) later use those unscaled numbers directly in the **current** program-unit coordinate arithmetic, when D is omitted. [`cycle_traverse`](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/rs274ngc/interp_cycles.cc#L2240) emits the resulting canonical target.

This differs from stable v2.9.10: stable [G73](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/rs274ngc/interp_cycles.cc#L204) and [G83](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/rs274ngc/interp_cycles.cc#L140) start with an explicitly **inch** constant and multiply by 25.4 whenever the *current* `length_units` is metric, so switching G20/G21 keeps the physical default 0.010 inch / 0.254 mm.

## Frozen source-derived examples (not executed)
**Metric machine, development default, no INI override:** initialize with G21 and c=1.0 mm; then issue G20 on a separate block. The interpreter rescales current coordinates to inches, but c remains numeric **1.0**, now used as **1.0 inch** (25.4 mm) rather than 1.0 mm. For G17 G90 G99 G73 with R=0.2 in, Q=0.1 in, bottom Z=-0.2 in and current Z=0.5 in, first feed target is Z=0.1 in; intermediate rapid is **0.1 + 1.0 = 1.1 in**, which is **0.9 in above R**. G83 additionally rapids to R=0.2 before Z=1.1. The intended physical default c=1 mm would instead be 0.0393701 in, yielding a Z≈0.13937 in intermediate target.

**Inch machine, development default:** initialize with G20 and c=0.050 in; then issue G21. c stays numeric 0.050 and is used as **0.050 mm**, rather than the original physical 1.27 mm. With a small Q the actual geometry can differ in the opposite direction. These are *source-derived canonical predictions*, not measured motion.

**Development with explicit D:** `block->d_flag ? block->d_number_float : parameter` bypasses the persistent default; an explicit D parsed in the active program units avoids this particular **default-parameter** scaling path, but the separate D positivity gap in CYCLE-116 still requires post validation. An INI override also remains numerically unscaled across a later G20/G21 change in the inspected path.

## Evidence and boundaries
**SOURCE-CONFIRMED:** initialization and INI read, no peck-parameter scaling in `convert_length_units`, raw parameter use in both peck helpers, stable unit-aware fixed gap. **DOC-CONFIRMED:** development INI values described as machine units; G73/G83 G-code prose default discrepancy already recorded in CYCLE-116. **INFERENCE:** 25.4× physical interpretation shift and example canonical coordinates. **UNKNOWN:** actual installed controller, Task/motion processing, physical limits/collision, whether a separate uninspected remap changes the path. **TEST-CONFIRMED:** none.

**Practical rule:** a versioned CAM post should freeze one program-unit mode across peck cycles and require an explicit, validated positive D for development when mixed units are unavoidable; do not rely on a persistent INI default after a unit switch without verifying the interpreter. Stable does not admit D for G73/G83. A physical fixture/clearance review remains necessary.

**Minimal discriminating verification:** in a qualified disconnected development interpreter with metric startup, compare G73/G83 canonical intermediate targets before and after an explicit G20 switch, holding equivalent physical R/Q/depth. Record actual binary, INI, stdout/stderr, exit and canonical output; compare against the source-derived 1.0 inch versus expected 0.03937 inch gap. Reuse the existing [G81 G98/G99 fixtures](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/tests/interp/g81/g17/g98/test.sh#L1) only as a shared-macro baseline. Do not run on a physical machine or hosted runner. No experiment performed.
