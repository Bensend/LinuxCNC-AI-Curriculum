## Question, predecessor, and version boundary
The preceding [ezdxf DXF audit](4400_DXF_EZDXF_01_BULGE_INSERT_NONUNIFORM_MINSERT_SOURCE_AUDIT_2026-10-30.md) established what a geometry-capable DXF reader can preserve, but not what an actual CAM/post does. Here the bounded question is: **does a real open-source DXF→contour→G-code pipeline retain bulges, ellipses, block transforms and original feature identity, and what happens when the result reaches LinuxCNC?** This is a new downstream implementation trace, not a reopening of graduated 3300/3600 or a claim of a modern CAM benchmark.

Inspected the GitHub mirror [cnc-club/dxf2gcode](https://github.com/cnc-club/dxf2gcode/tree/dff70cbd1cc6548041d7c79c561afc8bdc1e3e4f) at **immutable commit `dff70cbd1cc6548041d7c79c561afc8bdc1e3e4f` (2016-02-01)**. LinuxCNC comparison uses **v2.9.10** commit `86cdca76fa2a36274c432caa21952b23c267989a`; [official 2.9 G2/G3 documentation](https://www.linuxcnc.org/docs/2.9/html/gcode/g-code.html) is the independent intended-behavior reference. **Execution contexts:** DXF2GCODE's import/shape/post steps are ordinary Python userspace operations; LinuxCNC `convert_arc` is the interpreter's userspace path, not the realtime servo thread. `ARC_FEED` is canonical motion submitted downstream only after the checked path succeeds. None of this is an independent machine safety function.

## Three concrete geometry boundaries

### 1. Bulge preserved at import; other transformations can still lose it
The source explicitly constructs `ArcGeo` for nonzero bulge, including closing-edge bulges. Its output is no longer a DXF LWPOLYLINE but a sequence of `LineGeo`/`ArcGeo` primitives. The post can emit G2/G3, **conditional on** radius limits, shape/compensation path, and formatting. This is more capable than a vertex-chord importer but does not prove an arbitrary original DXF shape reaches LinuxCNC unchanged.

### 2. Nonuniformly scaled circular block arc is not made elliptical
`GeoentInsert.Read` preserves separate X/Y scales; `Point.rot_sca_abs` applies them to arc center and endpoints. Yet `ArcGeo.make_abs_geo` constructs a new **circle** and `scaled_r` uses X scale alone. A 2:1 scale of a unit quarter-circle centered at (0,0), from (1,0) to (0,1), has transformed start (2,0), end (0,1), center (0,0): start radius **2**, end radius **1**. The output path's I/J offset comes from transformed center minus transformed start, so the **illustrative** center-format command `G3 X0 Y1 I-2 J0` after start `X2 Y0` has unequal radii. The LinuxCNC v2.9.10 `arc_data_ijk` code checks that discrepancy and, for ordinary/default tolerance settings, rejects it before `ARC_FEED`. **No actual DXF2GCODE execution, emitted file, LinuxCNC interpreter invocation or machine motion was performed**; the numeric example is a static counterexample derived from inspected algorithms, not a captured run. Nonuniform ellipse geometry must be converted with bounded error or rejected; a circular G2/G3 is not an ellipse.

This contrasts with the **separate** pinned ezdxf `virtual_block_reference_entities` path, which has an ellipse-conversion fallback. Do not transfer ezdxf's behavior to DXF2GCODE merely because both read DXF.

### 3. Large-radius arcs can become straight chords at the post
`ArcGeo.Write_GCode` explicitly invokes `lin_pol_xy(Ps,Pe)` if `r > PostPro.vars.General["max_arc_radius"]`; otherwise it selects G2/G3. The pinned default is **10000 in the configured drawing/post units**. This is a geometry change at **post time**, not a LinuxCNC G64 Q simplification. G64 in the default post has **no P or Q**; the [earlier G64 Q audit](4400_LINUXCNC_G64_Q_NAIVECAM_MULTI_TURN_DXF_POST_SOURCE_AUDIT_2026-10-30.md) describes an independent downstream optional simplification mechanism. An NC-file reviewer must inspect both the CAM post and LinuxCNC modal configuration.

## Provenance and nesting distinction
The `Shape.nr` in the post's comment is generated by the shape list, not the original DXF entity handle. `EntityContent` retains parent/block hierarchy in memory, but `GeoentInsert.Read` and other inspected entity readers do not retain group-5 source handles, and `exportShapes` emits layer/shape comments rather than a durable source-entity manifest. **SOURCE-CONFIRMED for this path**; whether a separate project file preserves additional identifiers is not established. Preserve original document hash, DXF handle, INSERT chain, geometry tolerance, and NC revision externally if part-to-toolpath traceability matters.

The source's `optimizeTSP` changes **cut order** (`LayerContent.exp_order`), not part placement or sheet geometry. It is not a nesting engine. Plasma nesting and press-brake bend-line classification must happen in separately reviewed stages. Default M3/M8 is a **milling-style** post, not a validated QtPlasmaC material-selection post: [M190/M66 investigation](4400_LINUXCNC_QTPLASMAC_M190_M66_MATERIAL_HANDOFF_SOURCE_AUDIT_2026-10-30.md) establishes a different material handoff. Do not use the default output as proof of QtPlasmaC readiness, torch actuation, toolpath collision avoidance or personnel safety.
