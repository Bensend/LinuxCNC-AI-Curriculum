## Source trace 1 — compatible dwell parameter
The generic FreeCAD `Processor._expand_spindle_wait` and `_expand_coolant_delay` construct `Path.Command("G4",{"P": seconds})`; `convert_command_to_gcode` routes dwell to `_convert_dwell`, then `_convert_move`. `Constants.GCODE_P_IS_DWELL` prevents unit conversion of the dwell P word. The LinuxCNC post's rigid-tapping special case also emits `G04 P...`. This directly contrasts with PathForge's `G04 X...`. **SOURCE-CONFIRMED** syntax/serialization path; the source tests asserting `G04 P0.50` are *test source expectations*, not executed results.

## Source trace 2 — blending policy is exposed, not inherently validated
`Linuxcnc.get_property_schema` defaults `blend_mode=BLEND`, `blend_tolerance=0.0`; `_get_blend_command` maps EXACT_PATH→G61, EXACT_STOP→G61.1, BLEND with positive tolerance→`G64 P{tolerance:.4f}`, zero→bare **G64**. `_expand_prefix` injects it after the preamble. Upstream FreeCAD source tests explicitly assert bare G64 for zero and G64 P0.0500 for 0.05. No Q naive-CAM simplification word is emitted by this method. Thus a successful export is **not** evidence of a machine-specific contour-deviation budget: select/verify the tolerance, LinuxCNC's actual modal/INI state, G64 Q behavior and NC geometry independently. The source's sanity check has `if blend_tolerance>0.1` followed by `elif blend_tolerance>0.5`; the latter is unreachable for positive tolerances >0.5. This is a **SOURCE-CONFIRMED warning-branch defect**, not a measured machining error.

## Source trace 3 — development-only tilted-work-plane compatibility
`Linuxcnc.PLANE_COMMAND=PlaneCommand.G68_2`. In `Processor._expand_workplane_frames`, a tilted operation with a machine declaring TWP can create plane declaration, alignment and cancellation postables; `TiltedWorkPlane.DIALECTS` maps declaration to `G68.2 X Y Z I J K`, alignment to `G53.1`, cancel to `G69`. The post itself calls [LinuxCNC PR #4374](https://github.com/LinuxCNC/linuxcnc/pull/4374) draft multi-axis work. At the pinned **stable v2.9.10** interpreter source, G68.2 is absent; at the pinned **development** source it is present. Even on development, the inspected five-axis example config **REMAPs G53.1**; do not assume that the alignment command is available with identical semantics on every machine. A 3-axis/untilted job does not automatically emit these TWP blocks. **SOURCE-CONFIRMED version/configuration compatibility boundary**, not a claim that all FreeCAD NC is rejected by stable LinuxCNC.

## Practical post acceptance and adversarial review
For each machine, record FreeCAD commit/post version, selected post properties, LinuxCNC commit/INI/remaps/kinematics, and generated NC hash. Inspect first and last modal blocks; require explicit G4 P for dwells, intentional G61/G61.1/G64 P/Q policy, and a documented machine-specific reason for any G68.2/G53.1/G69 use. For plasma, a mill-oriented M3/M5 and tool-change post is not automatically QtPlasmaC's M190/M66/torch sequence. For a press brake, toolpaths and TWP do not calculate bend tooling or backgauge targets. Distinguish post-output syntax checks from independent geometry verification and machine commissioning.

Answer by tracing the version-specific interpreter modal set and FreeCAD TWP generation, not by claiming all FreeCAD/LinuxCNC integrations fail.
