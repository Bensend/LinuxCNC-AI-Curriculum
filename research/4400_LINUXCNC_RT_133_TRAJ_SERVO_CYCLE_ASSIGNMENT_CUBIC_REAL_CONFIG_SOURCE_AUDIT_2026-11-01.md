# 4000-LC-RT-133 — TRAJ_PERIOD, SERVO_PERIOD and cubic interpolation: a real-config source trace
**Audit:** 2026-11-01. **Status:** SOURCE-CONFIRMED conditional, COMMUNITY-REPORTED corroboration, runtime NOT RUN, NON-GRADUATED. **Transfer:** 3100 mills, 3200 lathes, 3400 routers, 3500 unusual kinematics, 4000 motion implementation.

## Question, predecessor and provenance
What happens to trajectory-planner and cubic-interpolator cycle times when a HAL file explicitly loads a trajectory period greater than the servo period? **Do not claim discovery of a new upstream defect.** [LinuxCNC issue #3268](https://github.com/LinuxCNC/linuxcnc/issues/3268), opened **2025-01-11**, already describes the suspicious assignments and contains independent user instrumentation; it remained **open** when checked on 2026-11-01. The incremental contribution here is a full HAL scheduler → motion → cubic call trace, real shipped machine configuration, version comparison, first-cycle state arithmetic, and bounded verification contract. Direct historical PROGRESS and research-filename synonym scans found no prior curriculum audit of `emcmotSetCycleTime` or `traj_period_nsec`; TP-30/31/47/48/49/92 are related but distinct.

**Immutable source:** LinuxCNC stable v2.9.10 commit `86cdca76fa2a36274c432caa21952b23c267989a`, development `06864e23559e70463fc7112d5ce77138bcbc288c`. Stable [motion.c:init_threads / emcmotSetCycleTime](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/motion/motion.c#L978), [control.c:emcmotController](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/motion/control.c#L207), [coordinated TP/cubic path](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/motion/control.c#L1333), [cubic.c](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/kinematics/cubic.c#L131); development [motion.c same assignments](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/motion/motion.c#L1087) and [controller callback](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/motion/control.c#L239). Official [core-components manual](https://linuxcnc.org/docs/stable/html/config/core-components.html) documents periods and rounding. Historical [2009 commit 163d25e](https://github.com/LinuxCNC/linuxcnc/commit/163d25e235749a18d11609408adb5ea36de856b9) introduced the callback correction to address requested/actual servo-period velocity deviation; history is intent, not current runtime verification.

## Complete execution path
1. **HAL/INI:** `[EMCMOT]TRAJ_PERIOD` is only consumed if HAL `loadrt motmod ... traj_period_nsec=[EMCMOT]TRAJ_PERIOD` actually passes it. If omitted, `motion.c:init_threads` defaults traj to the *requested* servo period. Servo is rounded to an integer multiple of base. [Stable lines 989–1028](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/motion/motion.c#L989).
2. **HAL scheduler:** `hal_create_thread` quantizes effective thread period and `thread_task` calls each realtime function with `thread->period` (nominal), not the measured time between callbacks. [Stable](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/hal/hal_lib.c#L2025), [development](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/hal/hal_lib.c#L2211), [stable callback](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/hal/hal_lib.c#L2897).
3. **Controller first invocation:** `last_period=0` initially; first nonzero `period` triggers `emcmotSetCycleTime(period)`. [Stable](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/motion/control.c#L223), [development](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/motion/control.c#L239).
4. **Cycle assignment in BOTH inspected revisions:** `servo_mult=traj_period_nsec/nsec` (integer truncation); `if (servo_mult<0) servo_mult=1`; then **`setTrajCycleTime(nsec)`**, **`setServoCycleTime(nsec*servo_mult)`**. For ordinary positive values, a zero quotient is **not** caught. Both setter results are ignored. [Stable](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/motion/motion.c#L1065), [development](https://github.com/LinuxCNC/linuxcnc/blob/06864e23559e70463fc7112d5ce77138bcbc288c/src/emc/motion/motion.c#L1087).
5. **TP/cubic consumer:** `setTrajCycleTime` changes `tpSetCycleTime` and cubic interpolation rate; `setServoCycleTime` changes cubic interpolation rate and segment time. `cubicSetInterpolationRate(rate<=0)` returns -1 without changing its stored rate; caller ignores it. `cubicSetSegmentTime` recomputes `interpolationIncrement=segmentTime/storedRate`. [Stable setters](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/motion/motion.c#L1075), [cubic setters](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/kinematics/cubic.c#L131).
6. **Command path:** `control.c:get_pos_cmds` calls `tpRunCycle` while cubic needs a new point, runs inverse kinematics and `cubicAddPoint`, then `cubicInterpolate` once per servo invocation. Cubic velocity coefficients depend on segment time. [Control](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/motion/control.c#L1333), [cubic](https://github.com/LinuxCNC/linuxcnc/blob/86cdca76fa2a36274c432caa21952b23c267989a/src/emc/kinematics/cubic.c#L220). This is not proof of actual motor speed.

## Existing upstream corroboration and conflict
[Issue #3268](https://github.com/LinuxCNC/linuxcnc/issues/3268) reporter instrumented a separate explicitly wired servo=100 µs, traj=1 ms case and reported servoCycleTime=1 ms, TP cycle=100 µs, cubic rate=1, segment=1 ms, increment=1 ms (2025-01-12). This is **COMMUNITY-REPORTED**, not TEST-CONFIRMED here. An earlier `pentapod.ini` report was non-discriminating because its `core_sim.hal` **does not pass TRAJ_PERIOD** (developer comment 2025-01-11). The developer queried whether separate trajectory period remains meaningful; no accepted patch was established by this inspection. The official manual describes rounding traj to servo multiples, whereas the inspected source explicitly rounds servo to base and later divides integer traj/servo; **DOC/SOURCE mismatch**. The reporter's proposed setter swap is an **untested patch suggestion**.
